# issue: commit-order — jj 后端整副本提交下的"先开单再落代码"

- **domain**：design
- **关联**：relates-to `silent-flag-drop`（同属"提交边界"的边角）

## 背景

agent 访谈（2026-10-23）P5：jj 后端下 `kiln commit` = `jj commit`，一次提交**整个工作副本**；为了让 `ask` 提交只含 issue doc，得先把已经写好的代码 / `tools/` 临时挪到工作区外，提交完再挪回来（`browser-shot` 开单时实际这么干过）。

回头看，摩擦不是"缺 `--only`"，而是**动作顺序**：先写代码后开单，才需要靠"挪文件"来伪造一个只含 doc 的提交。反过来做（先写 doc、提交 `ask`，再落代码）不需要任何新能力。

## 问题

1. 要不要实现按路径提交（`--only <paths>` 或 `--path`）？jj 没有脚本化的 `split` / `squash --from` 组合能做到"只提交一部分工作副本"且语义稳定；git 后端有 index 但 jj 忽略它——两端语义不一致，代价大于收益。
2. 替代：把"先开单再落代码"写成一条工作流约定，放在用户与 agent 都看得到的地方。
3. 多产物（doc + 代码 + 预览件）怎么提交：预览件放被忽略的 `.kiln/` 之外，其余按动作顺序分次提交。

## 候选

| 方案 | 形态 | 评价 |
| --- | --- | --- |
| **A** 实现 `--only` | 两后端各自模拟路径提交 | jj 端无法可靠实现；git 端语义又不同——引入"看起来一样、实际不一样"的命令 |
| **B** 只文档化 | README「与 agent 协作」加一条 + 本 doc 的结论 | 零代码、零新契约；把顺序当成纪律而不是功能 |
| **C** A + B | 两者都做 | 仍旧要背 jj 的不一致 |

## 验收

- **E1**：README 的「与 agent 协作」一节有一条"先开单再落代码"的说明（含"jj 后端提交整个工作副本"这一事实）。
- **E2**：本 issue 的结论明确写出"不做 `--only`"及其理由，避免下一个人再提。
- **E3**：不改任何命令的实现；`kiln check` 与既有动作统计不变。

## 非目标

- 不做 `git stash` / 自动移文件的辅助命令；
- 不改 jj / git 的后端选择规则；
- 不把这条约定写进 `kiln -h`（帮助是命令面，工作流属于 README）。

## apply（2026-10-23）

采用 **B**，只文档化，零代码：

- `README.md` 的「与 agent 协作」加一条「**先开单再落代码**」：`ask` 动作只放 issue doc，提交后再写实现；并写明 jj 后端 `kiln commit` 提交整个工作副本，所以反过来做才需要挪文件。
- 未改任何命令实现；`kiln check` 与动作统计不变。

## 结论（已定）

**不做 `--only` / 路径级提交。** jj 没有脚本化的"只提交工作副本的一部分"且语义稳定的组合；git 端虽然靠 index 能做，两端语义就会不一致——一个"看起来一样、实际不一样"的命令，比没有这个命令更糟。

替代约定：**先开单再落代码**。`ask` 只含 `docs/<id>.md`，代码与测试在后续动作里落；这样每个动作的提交边界由顺序保证，而不由命令参数保证。多产物同理：预览件、临时脚本放被忽略的 `.kiln/`（整目录 `/*` 忽略），其余按动作顺序分次提交。

边界：这条约定是纪律，不是功能——`kiln commit` 不会检查你是否先开了单；漏做的后果只是开单提交里混进了代码，check 不管这个。
