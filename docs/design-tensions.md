# issue: design-tensions — 理念与实现的张力盘点（七条，逐条留证）

- **domain**：design
- **关联**：relates-to `evidence-fluidity` / `object-semantics`

## 背景

kiln 的理念目前**散落在四处**，而且没有一处是权威：

| 出处 | 它说了什么 |
| --- | --- |
| [README](../README.md) 新增的「设计：两个原子 + 涌现」 | 原子 issue / 原子 action / 复杂性是涌现的（**刚成文**） |
| [mvp-plan](mvp-plan.md) §1「设计原则（从讨论中提炼）」 | 无模式 / 不建文件 / 不区分变更类型 / 宽容输入严格输出 / Agent-native / LLM 先验优先 + 本轮新增的三条 |
| [evidence-fluidity](evidence-fluidity.md) | 用户给定的**三条理念原话**：issue 原子化 / action 原子化（无固定流程）/ 依据 Unix 哲学与"复杂性是涌现的" |
| [object-semantics](object-semantics.md) | "**issue 是原子的；组合靠关系，不靠 issue 内部再分线索**" |

一句话：**理念是存在的，但没有一处收口，也没有被当成判据使用过**。同时，最近几轮实践已经暴露出若干**理念与实现之间、理念与理念之间**的张力（见下），值得一并理清。

## 要回答的问题

1. **权威在哪**：理念要不要收成一处？README 一节（用户向）/ `docs/design.md` 独立文档（权威）/ mvp-plan §1（spec 向）——三者怎么分工？
2. **理念 vs 便利**：哪些是真理念（加功能时可以拿来否决），哪些只是顺手的约定（"宽容输入严格输出""不建文件"）？
3. **张力清单**：下面这些要逐条判"是理念的必然推论，还是可以改的实现细节"。
4. **可检验吗**：理念能不能落成**判据**，用于评审新功能？（例："加一个 `--flag` 时，先问它是哪条理念的推论"）

## 已知的张力（每条都有本仓实测或结论支撑）

| # | 张力 | 支撑 |
| --- | --- | --- |
| 1 | **原子（无序集合）vs 叙事（有开端与收束）** | `action 原子化` 说"没有固定流程、可任意顺序"，而 mvp-plan §2.1 把 issue 的**本质**写成"以 `ask` 开启…以终点收尾"。本轮结论：**起点是角色（只要求存在）、终点是位置（必须是最后一个）**，非对称来自"只追加"（`agent-ux-review`） |
| 2 | **"完成"是判定 vs 人的直觉是"结束"** | 实测：终点之后仍可提交动作，issue 会回到进行中；`status` 的 `✓` 与 `check` 的"完整"同源（`agent-ux-review`） |
| 3 | **无注册表 vs 写侧拒绝** | 唯一性靠"写侧归一化 + 起点重名拒绝"（`issue-uniqueness`），**拒绝需要读全史**——这与"不建索引"直接相抵（实现上 `findIssue` 每次 `ask` 都要扫 log） |
| 4 | **只追加 vs 可改写** | 提交信息是唯一存储 → 头部性质（第一个动作）**不可修**，尾部性质（最后一个动作）可修；而 jj 允许改写历史，"证据流体"（`evidence-fluidity`）与"记录"取向的张力也来自这里 |
| 5 | **无数据库 vs 别名/唯一性** | 业界靠"重定向表 / historical IDs"承受改名，kiln 没有 DB → 改名成本高于所有同类工具（`issue-uniqueness` collect §4） |
| 6 | **人读 slug vs 机器键** | 主流是两把键（`number`/`node_id`、`iid`/`id`），kiln 只有一把（`issue:` 的值）；于是"名字可读"与"能派生唯一"不可兼得（`issue-uniqueness` collect §5） |
| 7 | **"过滤器不是注册器" vs 一致性校验** | README 的定位句 vs `check` 的规则与写侧护栏——后者已经是"注册"的雏形；边界该划在哪？ |

## 候选（理念文档的落点）

| | 形态 | 代价 |
| --- | --- | --- |
| **A** | README 一节（现状，最简） | 用户向，但承载不了"张力与判据" |
| **B** | 独立 `docs/design.md` 作为权威，README 只放摘要 | 多一份需要维护的文档；好处是理念有了唯一出处 |
| **C** | mvp-plan §1 扩写 | spec 与理念混在一处，读者成本高 |
| **D（倾向）** | **分工**：`docs/design.md` 权威（理念 + 张力 + 判据）／README 留一屏摘要并指过去／mvp-plan §1 只留"加功能时的判据" | 要一次写清；之后每轮结论都该回看它是否被动摇 |

## 非目标

- **不动代码**，也不改任何已 `conclude` 的结论（`object-semantics` / `evidence-fluidity` / `issue-uniqueness` 等照旧）。
- 不重开"要不要 namespace / 要不要派生键"之类的已定裁决；本 issue 只做**整理与审视**，以及决定理念**放哪**。
- 不写成宣传文案——每条理念都要能指出它在实现里的**对应事实**。
