# issue: design-tensions — 理念与实现的张力盘点（七条，逐条留证）

- **domain**：design
- **关联**：relates-to `evidence-fluidity` / `object-semantics`

## 背景

kiln 的理念目前**散落在四处**，而且没有一处是权威：

| 出处 | 它说了什么 |
| --- | --- |
| [README](../README.md) 新增的「设计：两个原子 + 涌现」 | 原子 issue / 原子 action / 复杂性是涌现的（**刚成文**） |
| [mvp-plan](mvp-plan.md) §1「设计原则（从讨论中提炼）」 | 无模式 / 不建文件 / 不区分变更类型 / 宽容输入严格输出 / Agent-native / LLM 先验优先 + 本轮新增的三条 |
| [evidence-fluidity](evidence-fluidity.md) | 用户给定的**三条理念原话**：issue 原子化 / action 原子化（无固定流程）/ 依据 Unix 哲学与"复杂性是涌现的" |
| [object-semantics](object-semantics.md) | "**issue 是原子的；组合靠关系，不靠 issue 内部再分线索**" |

一句话：**理念是存在的，但没有一处收口，也没有被当成判据使用过**。同时，最近几轮实践已经暴露出若干**理念与实现之间、理念与理念之间**的张力（见下），值得一并理清。

## 要回答的问题

1. **权威在哪**：理念要不要收成一处？README 一节（用户向）/ `docs/design.md` 独立文档（权威）/ mvp-plan §1（spec 向）——三者怎么分工？
2. **理念 vs 便利**：哪些是真理念（加功能时可以拿来否决），哪些只是顺手的约定（"宽容输入严格输出""不建文件"）？
3. **张力清单**：下面这些要逐条判"是理念的必然推论，还是可以改的实现细节"。
4. **可检验吗**：理念能不能落成**判据**，用于评审新功能？（例："加一个 `--flag` 时，先问它是哪条理念的推论"）

## 已知的张力（每条都有本仓实测或结论支撑）

| # | 张力 | 支撑 |
| --- | --- | --- |
| 1 | **原子（无序集合）vs 叙事（有开端与收束）** | `action 原子化` 说"没有固定流程、可任意顺序"，而 mvp-plan §2.1 把 issue 的**本质**写成"以 `ask` 开启…以终点收尾"。本轮结论：**起点是角色（只要求存在）、终点是位置（必须是最后一个）**，非对称来自"只追加"（`agent-ux-review`） |
| 2 | **"完成"是判定 vs 人的直觉是"结束"** | 实测：终点之后仍可提交动作，issue 会回到进行中；`status` 的 `✓` 与 `check` 的"完整"同源（`agent-ux-review`） |
| 3 | **无注册表 vs 写侧拒绝** | 唯一性靠"写侧归一化 + 起点重名拒绝"（`issue-uniqueness`），**拒绝需要读全史**——这与"不建索引"直接相抵（实现上 `findIssue` 每次 `ask` 都要扫 log） |
| 4 | **只追加 vs 可改写** | 提交信息是唯一存储 → 头部性质（第一个动作）**不可修**，尾部性质（最后一个动作）可修；而 jj 允许改写历史，"证据流体"（`evidence-fluidity`）与"记录"取向的张力也来自这里 |
| 5 | **无数据库 vs 别名/唯一性** | 业界靠"重定向表 / historical IDs"承受改名，kiln 没有 DB → 改名成本高于所有同类工具（`issue-uniqueness` collect §4） |
| 6 | **人读 slug vs 机器键** | 主流是两把键（`number`/`node_id`、`iid`/`id`），kiln 只有一把（`issue:` 的值）；于是"名字可读"与"能派生唯一"不可兼得（`issue-uniqueness` collect §5） |
| 7 | **"过滤器不是注册器" vs 一致性校验** | README 的定位句 vs `check` 的规则与写侧护栏——后者已经是"注册"的雏形；边界该划在哪？ |

## 候选（理念文档的落点）

| | 形态 | 代价 |
| --- | --- | --- |
| **A** | README 一节（现状，最简） | 用户向，但承载不了"张力与判据" |
| **B** | 独立 `docs/design.md` 作为权威，README 只放摘要 | 多一份需要维护的文档；好处是理念有了唯一出处 |
| **C** | mvp-plan §1 扩写 | spec 与理念混在一处，读者成本高 |
| **D（倾向）** | **分工**：`docs/design.md` 权威（理念 + 张力 + 判据）／README 留一屏摘要并指过去／mvp-plan §1 只留"加功能时的判据" | 要一次写清；之后每轮结论都该回看它是否被动摇 |

## 非目标

- **不动代码**，也不改任何已 `conclude` 的结论（`object-semantics` / `evidence-fluidity` / `issue-uniqueness` 等照旧）。
- 不重开"要不要 namespace / 要不要派生键"之类的已定裁决；本 issue 只做**整理与审视**，以及决定理念**放哪**。
- 不写成宣传文案——每条理念都要能指出它在实现里的**对应事实**。

## hypothesize（2026-10-28）：D（轻量权威）+ 第 7 条裁定 + 5 条判据；`design.md` 是可改写的快照

### 0. 主张

- 新建 **`docs/design.md`** 作为理念的**唯一权威摘要**：两个原子 + 涌现 → 边界 → 七条张力裁定表 → 5 条判据。**不复制证据**，深度材料留在各 issue doc（链接过去）。
- README §设计 保留一屏摘要，加一句指向 `design.md`；mvp-plan §1 的原则表加一句"权威在 `design.md`"并链接。
- 第 7 条（过滤器 vs 校验）顺手裁定。
- **`design.md` 是当前快照，不是宪法**：涌现意味着结果无法提前规划；它随实践改写，改它走 issue → conclude → apply。

### 1. 为什么是 D（轻量版）

- **A**（只留 README 一节）：承载不了"张力表 + 判据"。
- **B**（独立长文）：等于把 359 行搬一份，证据会与 issue doc 漂移，维护成本高。
- **C**（mvp-plan §1 扩写）：spec 与理念混在一起，读者成本高。
- **D 轻量版**：权威在**摘要**，证据在 issue doc，链接指向、不复制——既有唯一出处，又不会长出第二份需要同步的长文。

### 2. 为什么 `design.md` 不能是"宪法"

- 理念本身是**涌现**出来的（用户原话）：先实践、再记录；"提前规划一套不可改的设计宪法"与涌现直接矛盾。
- 若把它当不可改：实践推翻理念时，要么违心遵守，要么绕开它——两者都比"改它"更坏。
- 具体机制：
  - 文档首行标注「**当前快照（日期），不是契约**」；
  - 末尾写清修改方式：开一条 issue → conclude（或 apply）→ 回来改这里；
  - 历史版本由 issue doc 留存——本仓的 issue 记录本身就是变更史；`design.md` 只呈现当前态（与 `evidence-fluidity` 一致）。

### 3. 第 7 条：过滤器 vs 校验

- kiln 是**过滤器 / 派生视图**，不是注册器：不做全局注册表、不建索引、不分配 id。
- 写侧只在**"沉默会污染记录"**时拦：起点动作、`--title`、`target ⊆ 改动`、重复标量。
- `check` 是**当前态的结构检查**：error 只限"无法解析成动作"，其余 warn。
- 一句话边界：**能由现存提交重算的一律不注册；不能重算、且错了会静默的才拦**。

### 4. 判据（评审新功能时问的 5 个问题）

1. 加这个 flag / 命令，它是哪条理念的推论？会不会让读侧多一层？
2. 会不会引入需要维护的全局状态（索引 / 注册表 / DB / 缓存）？
3. 会不会把一般视图变成审计（要求保证历史不可变 / 可举证）？
4. 写侧拦它，是因为"静默会污染记录"吗？读侧宽容够不够？
5. 能不能用现有的两个原子 + 9 条关系表达？加名字是否只是标签偏好？

### 5. 落点与工作量

- 新建 `docs/design.md`（目标 ~100 行）；README §设计 加指针与"快照"声明；mvp-plan §1 加一句权威指向。
- **不动代码**；`check` 不变。

### 6. 检验（apply 时核对）

- `design.md` 每条断言都有链接或事实支撑；不复制 issue doc 的证据。
- README / mvp-plan 只放指针，不重复内容。
- 文档首行与末尾都有"当前快照 / 如何修改"的说明。

### 7. 反方（保留）

1. **"多一份文档"**：摘要 + 链接，不复制；漂移时以 issue doc 为准，`design.md` 定期回看。
2. **"权威摘要仍会被当成宪法"**：文档自身声明 + 修改机制 + issue 历史三层兜底。
3. **"为什么不直接把 README 那屏扩成权威"**：README 是用户向的一屏，承载不了七条张力与判据。

## conclude（2026-10-28）：D 定稿——`docs/design.md` 是权威快照，不是契约

### 0. 裁决

- **落点 D（轻量权威）**：`docs/design.md` 是理念的唯一权威摘要；README §设计 保留一屏并指过去；mvp-plan §1 只留原则表 + 权威指针。
- **内容**：两个原子、复杂性账本（去掉 / 转移 / 新增 / 边界）、七条张力裁定表、5 条判据、维护方式。
- **第 7 条裁定**：kiln 是**过滤器 / 派生视图**，不是注册器——不做全局注册表、不建索引、不分配 id；写侧只在「沉默会污染记录」时拦；`check` 是当前态结构检查。边界句：**能由现存提交重算的一律不注册；不能重算、且错了会静默的才拦。**
- **快照声明**：`design.md` 首行写明「当前快照（日期），不是契约」；涌现意味着结果无法提前规划；修改走 issue → conclude / apply → 改文档；历史由 issue 记录留存。

### 1. 为什么这样落

- **摘要 + 链接，不复制证据**：权威在摘要，证据在 issue doc；避免长出第二份需要同步的长文。
- **可改**：与 `evidence-fluidity` 的「一般视图呈现当前态」一致——`design.md` 只呈现当前共识，被实践推翻就改它。
- **判据进文档**：5 条问题让理念第一次能被**当成判据**使用（原 ask 的第 4 问）。

### 2. 与既有裁决的关系

- `design-philosophy`：抽象机制与方法论仍在它的文档；`design.md` 只引结论，不复制。
- `relation-vocabulary` / `relation-revision` / `design-philosophy`：关系词表 **9 名固定**；`design.md` 写明。
- `evidence-fluidity`：一般视图当前态、改写不必声明；`design.md` 自身就是当前态文档。
- `action-granularity`：「工具不教用户」——`design.md` 只描述可解析的结构，不规定工作方式。

### 3. 明确不做

- 不改代码；不重开 namespace / 派生键等已定裁决。
- 不把 `design.md` 写成不可改的宪法；不复制 issue doc 的证据。

### 4. 维护 / 重开

- 每轮 design 结论之后回看：`design.md` 有没有被动摇？
- 若实践推翻某条：开新 issue → conclude / apply → 改 `design.md`；旧结论留在 issue 文档里作证据。

### 5. 验收

- `docs/design.md` 存在，含「两个原子 / 涌现 / 七条裁定 / 判据 / 不在本文件 / 如何修改」六节。
- README §设计与 mvp-plan §1 都有指针，且不重复内容。
- 无代码改动；`check` 不变（63 ok / 0 warn）。
