# issue: commit-cache — 把一次扫描的结果落成缓存文件（设计定稿）

- **domain**：design
- **关联**：relates-to `perf-audit`（它把索引/缓存列为明确不做，但留了"再单独立项"的口子，并给了触发条件——本 issue 就是那个立项）；relates-to `action-log-relations`（总流是"顺手落盘"的那个进程）；relates-to `action-log`（现成的流式原语）；relates-to `issue-list-scaling`（规模论证的前置）

## 背景

`perf-audit` 的结论是"无索引"：每条读命令都从提交历史现算模型，换来"零状态、永远和 git 一致"。它同时留了一句："如果将来长历史上确实疼，再单独立项"，并给了触发条件（真实仓 1k+ issue，或单次 `path --all` > 10 MB）。

本 issue 就是那个"单独立项"。触发还没有到——本仓现在 69 issue / 367 提交——所以**当时不建**，先把设计记下来，免得真要建时重新推一遍。（2026-10-29 test 后改判：按两条读路径重算，`Log` 路径 10k 提交起就回本，值得做。见 test 与修订后的 hypothesize。）

新增的论点是这一条：**缓存不必是"额外一遍"**。`action-log-relations` 里的总流本来就要遍历每条提交、用 `trailer.Parse` 解析全部字段；把解析结果顺手落盘，缓存就是总流的副产物。这把缓存从"多付一次全史扫描"变成"零边际成本产出"——原来挡着它的成本理由消失了，剩下的是正确性和写策略。

## 今天的账：缓存一定是净亏

本仓 366 提交，三次取最小：

| 命令 | 耗时 | 其中 |
| --- | --- | --- |
| `kiln --version` | 62 ms（`cmd /c` 包一层；`perf-audit` 记录纯启动 46 ms） | 进程启动地板 |
| `action log --jsonl` | 117 ms | 地板 + 一次 `git log` + 解析 |
| `graph --json` | 127 ms | 地板 + 同上 + 建模折叠（≈10 ms） |
| `path --all --json` | 169 ms | 地板 + 同上 + 渲染 170 KB |

`graph` 只比 `action log` 多 10 ms——**折叠和建模不是瓶颈，`git log` 的传输与解析才是**。而在 366 提交上，省掉 log 最多省 20 来毫秒，缓存要多付一次读盘 + 一整套失效/损坏/并发的正确性支出。不划算。

## 为什么相信它在规模上会赢

`perf-audit` 与 `timeline-stream` 已经测过 100k：

- 全史 `git log` **1.3–1.7 s**，`path --all` 峰值 **190 MB**，`show` 851 ms，`commit` 1.5 s；
- 首行 64 ms（有 commit-graph）/ 359 ms（无）。

瓶颈是 **body 的字节数与解析**（100k 条 × 约 450 B ≈ 45 MB），而缓存恰好能整段省掉它：只存解析后的记录（hash、日期、issue、action、title、domain、tags、relations），约 100–200 B/条 → 100k 时 10–20 MB，顺序读 + 零解析，量级上是几十毫秒对一秒。

换算下来，`graph` / `check` / `list` 在 100k 上大概能快 10–30×。**`path --all` 是个例外**：它 35 MB 的输出本身就是大头，缓存救不了它；`--stat` 的 diff 计算也是另一层（每提交确定，可缓存，但体积大一个量级）。

## 真要建时的清单（现在只记，不写代码）

1. **键 = commit hash，只增不改。** 同一个 hash 的消息、日期、父提交永不变化 → 没有失效逻辑，只有 GC。这是整个方案能成立的前提，也是它比"缓存派生模型"安全得多的原因。
2. **但解析依赖配置。** 关系别名 → 规范名由词表决定；缓存里应存**原文键值**、读时再解析，或以配置指纹做命名空间。否则改一次 `.kilnconfig.jsonc` 就会读到旧词表下的规范名。
3. **jj 不一样。** 重写会换 commit id、弃用提交留垃圾；colocated 仓里 git hash 与 jj change id 是两套身份。缓存必须按后端分键，jj 可能得二期。
4. **写策略才是真难点。** 读命令要不要写盘（只读仓、CI 并发、`--no-cache` / `KILN_NO_CACHE`）；放哪（`.git/kiln/cache/` 每克隆一份、worktree 天然共享、不进版本控制；还是 XDG 用户缓存，跨克隆但 key 要自己算）；原子写（temp + rename）；**半写损坏必须退化为全扫，绝不给错结果**。
5. **格式版本化**：magic + version 头，不匹配就当没有，别做迁移。
6. **GC**：按可达提交裁剪；手动 `kiln cache gc` 还是自动，取决于体积。
7. **验收硬条件**：命中与不命中的输出**逐字节一致**。这条比"快多少"重要——`perf-audit` 的三批优化全是这么验收的。
8. **与"只写 stdout"的契约冲突**：`machine-readable-output` 的约定是命令只产出文档；一个后台落盘行为要不要在 `-h` 与文档里显式声明？

## 先做便宜的那两步（都测过，零/低成本）

- **git 自己的 commit-graph**：100k 上首行 359 → 64 ms（`timeline-stream` 实测）。这是 git 的持久化缓存，维护成本为零。kiln 该不该在文档里建议、或在读路径上可选地 `git commit-graph write`？几行代码，先于自己造缓存。
- **`%(trailers)` 只读 trailer 块**：本仓 `%B` 156,223 B → `%(trailers)` 107,018 B（**−31%**），时间在噪声内。但**兼容性有洞**：本仓 352 条动作里 git 认不出 4 条——
  - `f8413d8`：整条消息只有 trailer，没有标题行；
  - `c12f6eb`、`8a0fe99`、`e0ff712`：标题与 trailer 之间没有空行（正是 `commit-format` 那条 issue 的历史产物）。

  所以它只能当"快路径 + 回退"，不能直接换掉 `%B`。反过来看，这个洞恰好支持本 issue 的立场：**解析语义应该留在 kiln 里**，缓存存的应该是 kiln 的解析结果，而不是把解析外包给 git 的 `%(trailers)`。

## collect（2026-10-29）：git 怎么区分"存储"与"计算"

> 依据：[git-commit-graph](https://git-scm.com/docs/git-commit-graph)、[commit-graph 格式](https://git-scm.com/docs/commit-graph-format)、[racy-git](https://git-scm.com/docs/racy-git)、[bitmap-format](https://git-scm.com/docs/bitmap-format)。本机 git 2.55.0。

### 1. 两个平面

| 平面 | git 里的东西 | 特点 |
| --- | --- | --- |
| 真相 | object db（commit = tree + parents + author/committer + message）、refs、index 里的 path→OID | 内容寻址、不可变；只被新建覆盖，不被"更新" |
| 加速 | commit-graph、reachability bitmap、multi-pack-index、`.rev`、index 的 stat 缓存、untracked cache、fsmonitor | 全可删可重建；删掉只变慢，不改变任何答案 |

index 是两栖的：`path→OID` 是真相（暂存区），`stat` 信息是加速。

### 2. commit-graph：把"提交自带的事实"和"算出来的事实"放进同一个文件

每条提交存：OID、父提交（positional 下标）、root tree OID、提交时间、generation number（拓扑层级），可选再加 corrected commit date（GDA2）、**changed-paths Bloom filter**（BIDX/BDAT）、以及分层用的 BASE。也就是说：

- **父提交 / 树 / 时间**是"提交里本来就有的"，复制过来只为加速遍历；
- **generation number / corrected commit date / Bloom filter** 是**算出来的**，git 照样缓存——这正是"计算的那部分也可以缓存"的先例。

关键在**键**：这些派生数据以 commit OID 为键，而 OID 不可变 → **永远不会过期**。bitmap 同理，以 tip 提交为键：给某个 tip 算的可达性集合对该 tip 恒真，tip 一变就不用它。

### 3. 失效机制（可以直接抄的五条）

1. **内容寻址**：键不可变 → 不需要失效逻辑，只需要 GC。
2. **缺失即正常**：commit-graph 不记录"覆盖到哪"，它就是"没有更新的提交"。实测：写完 graph 再提交，`git rev-list --count HEAD` 仍 4、`git log` 仍 4 行、`git commit-graph verify` 仍 exit 0——**陈旧只变慢，不变错**，缺的提交回落到对象库按需读。
3. **自校验文件名**：split 层的文件名 = 去掉尾部 trailer 的 SHA-1 = 它自己的 trailer。实测本仓三层全部成立（`8a169f2…` / `8cc7b5f…` / `eaf71be…`），所以内容被截断或篡改可以靠名字发现。
4. **结构版本靠换 id，不迁移**：GDA2 / GDO2 之所以带 "2"，是因为老版本写过错的 GDAT / GDOV；新 git 直接忽略旧 chunk 重写。对 kiln 的含义：格式一变就换 magic / version，旧文件当没有。
5. **元数据 + 可疑才验**（index / racy-git）：先比 stat（mode、mtime、ctime、uid、gid、ino、size），不一致才看内容；写入时若条目"racy"（mtime 不早于 index 自身）就把 size 截成 0，强制下次重验。经典的"便宜判断 + 贵兜底"。

还有一条**边界**：replace object / graft 一出现，git 直接关掉 commit-graph 的读写——语义被外部改写时缓存自动退场。kiln 的类比是**改关系词表**：槽位与强度变了，折叠就不再是同一个函数，所以缓存必须带词表指纹。

### 4. 分层的工程策略（本仓正在用）

`--split` 把 commit-graph 写成**不可变的一层层**：新提交进新的 tip 层，`commit-graph-chain` 列出层哈希；tip 超过前一层 2 倍（`--size-multiple=2` 默认）或超过 `--max-commits` 就合并；`--expire-time` 删旧层；`--split=no-merge` / `replace` 是极端档。本仓现在正好三层（7,164 / 27,392 / 14,104 字节）。

### 5. jj 是同一形态

jj 也把索引存成内容寻址的不可变片段：`.jj/repo/index/segments/<hash>`（本机 jj 0.45.1 实测），外加 `op_links/`。名字不同、语义相同：**追加不可变片段，由读取方归并**。jj 明说内部格式会变，所以只能学形态，不能读它的文件。

### 6. 对 kiln 的直接推论

1. **枚举与取属性分开**。枚举只要 OID 列表——`git rev-list HEAD` 只走拓扑、不解消息；属性靠 `OID → record` 查缓存，缺的才去读 body。实测本仓：`rev-list` 15,211 B / 66.2 ms，`--format=%H%x00%aI` 24,857 B，带 body 157,633 B（**10×**）。这样"新鲜度"问题自然消失：**枚举永远来自 rev-list，缓存只回答属性**，rebase / amend 留下的不可达记录根本不会被枚举到，最多占地方等 GC。
2. **缓存文件自校验**：文件名或头部存内容 hash，对不上就当没有（照抄 commit-graph 的 trailer 约定）。
3. **派生结果可以缓存，但键要装下全部输入**。某 issue 的折叠路径 = f(它的动作 OID 序列, 词表指纹)；键一变就是新条目，旧条目自然作废——不需要"失效逻辑"，只需要 GC。generation number / bitmap 就是这么活的。
4. **但默认先不缓存派生结果**。折叠只要 ~10 ms（本仓），而派生缓存会把"命中与否字节一致"从天然成立变成需要证明。等派生本身变贵（100k 上的 `check` 规则之类）再说。
5. **合并策略直接借 `size-multiple=2`**：记录层按"新增超过已有 2 倍就合并"来管，比"最多留 N 个文件"好推理。

### 7. 由此新增的问题

10. **枚举也交给 git 吗**：`rev-list` 在"有缓存"和"没缓存"两条路径上都要跑（它便宜但非零）。这会不会让"一个提取层两个数据源"变成三处？还是把它当成提取层的第一步，所有路径共用？
11. **派生缓存做不做**：做的话键 = (动作 OID 序列, 词表指纹)；不做的话，100k 上折叠的真实耗时得先量出来，别凭"本仓 10 ms"外推。
12. **层合并策略**：照抄 `size-multiple=2` + expire，还是简化成"最多 N 层、超过就全量重写"？
13. **还没量到的**：`git rev-list` 在 100k 的耗时（本仓 66 ms 里 ~60 ms 是进程启动，比例不可外推）；逐条 `git log -1 --format=%B <oid>` 补缺口 vs 一次 `git cat-file --batch`；jj 侧没有 `rev-list` 等价物（枚举要靠 `jj log --no-graph -r 'all()'`，而它本来就不增量）。

## hypothesize（2026-10-29）：缓存成什么形状，怎么保证"变快不变错"

> 本节是初版。第 2 条（枚举）、第 4 条（写入）、第 7 条（验收）已被下文「hypothesize（2026-10-29 修订）」替换；另外 `chain` 文件也已取消，改为“目录即索引”（见修订版 §8）。记录层字段、顺序契约、失效与 GC 这三块的结论仍然成立。

结论先行：

1. **缓存只存属性层**：`OID → 已解析的记录`（trailer 全字段 + author date）。不存派生态（T3）、不存 diff（T4/T5）、v1 也不存改动文件（T2）。
2. **枚举永远来自 git**：`git log --author-date-order --format=%H`。顺序、时效、完整性三件事因此都不归缓存管——缓存只回答"这个 OID 的属性是什么"。
3. **文件是不可变分层 + chain + 自校验名**，形态照抄 commit-graph；格式变了换 magic，旧文件当没有。
4. **写入是显式的**：`kiln cache sync` 写盘并 GC；所有读命令只读。`--no-cache` / `KILN_NO_CACHE=1` 关闭。读命令永远不写盘。
5. **默认关闭**。先实现、再在 100k 合成仓上量，默认值留给 conclude——今天（372 提交）它一定是净亏。
6. **v1 只支持 git**，jj 保持现状。

### 1. 记录层格式

位置：`$(git rev-parse --git-common-dir)/kiln/records/`（本仓就是 `.git`；worktree 天然共享一份）。

```text
.git/kiln/records/
  chain                    # 一行一个层哈希，新层在前
  layer-<sha1>.rec         # 不可变层；<sha1> = 去掉尾部 20 字节的 SHA-1 = 文件自己的 trailer
```

层头：magic `KILNREC1` + 格式版本 + **词表指纹**（关系名/槽位/强度 + 别名集合的哈希）+ 记录数 + 变长记录区 + 20 字节 trailer。词表指纹不匹配 → **整层忽略**（回落全扫）。理由是折叠语义依赖词表，而按 `design-philosophy` 词表几乎不变，指纹失配只意味着"重建一次"。

记录（每条提交一条，不只是动作）：

```text
OID(20) | authorDate(8, unix 秒) | tzOffset(2, 分钟) | flags(1) | 字段块(TLV)
```

`flags` 里记 `isAction`：不记就会被非动作提交反复读 body——本仓 372 提交里 352 条是动作，20 条非动作，不记的话每次都要多读 20 条 body，规模上不划算。

字段块存**已解析**的 `issue / action / title / domain / scope / target / refs / tags / relations / unrelate`（关系存规范名与靶）。不存 trailer 原文：读时再解析要 100k × ~1–3 µs，几十到几百毫秒，等于把省下的时间还回去一半。

### 2. 读路径

```text
枚举：git log --author-date-order --format=%H      （本仓 15,252 B；不含任何 body）
   ↓ OID 列表（顺序即输出顺序）
查表：OID → record       命中 → 直接用
      ↓ 缺失的 OID 收集起来
补缺：一次 git cat-file --batch（stdin 喂 OID）
      ↓ 返回 `<oid> commit <size>\n<payload>`，按字节数读，天然分帧
解析：只对这几个缺口跑 trailer.Parse
```

没有缓存时，走的就是今天这条路（`LogEach` 流式扫全史）。两条路共用同一个记录结构与同一份渲染代码，所以"命中与否字节一致"不是靠测试保证，而是**结构上不存在第二条输出路径**。

> 更正 collect 里的措辞：那里写的是"枚举走 `git rev-list`"，这里改成 `git log --author-date-order --format=%H`。原因是 `rev-list` 的默认顺序不是 author-date-order，而**顺序是输出契约的一部分**（见 §3 的同秒提交）；`git log --format=%H` 与 `rev-list` 一样只吐 OID、不带 body（本仓 15,252 B / ~65 ms），成本相同而语义正确。

### 3. 顺序：不给缓存排序权

本仓现有 3 对**同一秒**的提交，而且三对都是**直接父子**（`子^ == 父`）：

| 时间（+08:00） | 子（现输出在前） | 父（在后） | 备注 |
| --- | --- | --- | --- |
| 2026-10-14 12:53:33 | `8a0fe99` apply | `e0ff712` ask | author 与 commit date 都相同 |
| 2026-10-17 20:25:39 | `3f15978` apply | `832be77` ask | author 同秒，**commit date 差 74 秒** |
| 2026-10-23 17:21:23 | `ec5a656` hypothesize | `3dc7ae4` collect | author 与 commit date 都相同 |

第二行说明问题不在"时间"：commit date 差 74 秒，输出仍是子在前——因为 `--author-date-order` 的定义是**两条规则**：

1. **父提交不能出现在它的子提交之前**（拓扑约束）；
2. 其余情形按 **author date** 倒序。

规则 1 管得到的地方（父子），日期并列不影响结果；规则 2 只在规则 1 管不到的地方起作用（不同分支之间）。

风险的真实形状分三层，越往下越致命：

1. **同秒本身只是预警**：对相等的 key 做**稳定排序**会保留输入顺序，而输入顺序正是 git 的枚举顺序 → 恰好复现。所以"日期相等"不能单独当判据。
2. **不稳定排序会坏**：Go 的 `sort.Slice` 不保证稳定（`sort.SliceStable` 才保证），一旦用了前者，这 6 条的先后由实现决定。
3. **倒挂才是根本问题**：`--author-date-order` 的输出**并不是按日期单调的**——规则 1 优先。rebase / amend / cherry-pick 很容易造出"父提交的 author date 比子提交更新"。实测本仓 374 提交、375 条父子边，倒挂 **0 处**，所以今天看不出来；但任何按日期排序的实现，遇到倒挂的仓库就会把父排到子前面，直接违反规则 1。再加一层：如果缓存哪天自己枚举（不问 git），顺序连来源都没有了。

避免办法，按代价排：

1. **不让缓存决定顺序**（选定）：枚举用 `git log --author-date-order --format=%H`，返回的序列**原样使用**，Go 侧一律不排序。已实测：`--format=%H` 与今天 `-z %H%x00%aI%x00%B` 的 OID 序列逐条相同（374/374，首个不一致位置 −1），所以快路径与慢路径的顺序**按构造一致**，不是靠"稳定排序运气好"。
2. **让缓存存父提交并复刻规则 1**（可行但白干）：等于把 git 的 revision walker 重写一遍；而且规则 1 管不到的并列（不同分支、同一秒）git 也没有公开契约，复刻不出来。
3. **缓存里存"扫描序号"**（否决）：序号只在写入时的仓库状态下成立；新提交要插到最前、rebase 后整体失真，而为了知道"哪些 OID 还算数"仍然要枚举一次——成本更高、正确性更弱。

推论：`--limit` 的语义原样保留——"枚举序列里的前 N 条动作"，不是"日期最新的 N 条"。

### 4. 写路径与并发

- `kiln cache sync`：跑一次全史扫描（就是今天的 `LogEach`），把枚举到但缓存里没有的 OID 写成**一个新层**，然后原子更新 `chain`（新层在最前）。
- 层名是内容哈希 → 同样的输入重复写是幂等的，不会产生两份。
- 并发：`chain` 用 `O_EXCL` 锁；拿不到锁就不写、exit 0、stderr 一行说明（worktree + 多 agent 是真实场景，宁可退化也不阻塞）。
- 只读仓（CI 挂载、`GIT_DIR` 只读）：`sync` 报错 exit 1；读命令完全不受影响（查不到就走今天的全扫）。
- 半写/断电：层文件写到临时名再 rename；`chain` 里引用的层随时可能被删，读侧**索引失败就当作不存在**。

### 5. GC 与层合并

不可达记录（rebase/amend 之后的旧提交）散在各层里，没法部分删。策略：

- 层数 > 16，或"枚举结果之外"的 OID 占比 > 30% 时，`sync` 顺带全量重写（等价于 commit-graph 的 `--split=replace`）；
- 否则新层里只放增量，等价于 `--split=no-merge` + 手工合并阈值；
- 不设 `--expire-time` 这类按时间的策略——kiln 的规模远没到需要它。

### 6. 明确不做

- 不缓存折叠/序号/标题/诊断（T3–T5）；
- 不缓存 diff 正文；
- v1 不缓存每提交的改动文件（T2）——它的代价是给每条提交算 tree diff，和"读 trailer"不是一个量级；
- 不做 daemon、不做跨机器共享、不做后台自动写。

### 7. 验收（写进 test 的清单）

1. **字节一致**：本仓 + 100k 合成仓，每个读命令在 `--no-cache` / 缓存命中 / 缓存缺层 三种状态下 stdout 字节与退出码完全相同。
2. **损坏退化**：截断一层、翻转一个字节、篡改文件名 → 该层被忽略，输出不变，不报错。
3. **版本不符**：改 magic 或词表指纹 → 整层忽略，回落到全扫。
4. **只读仓**：缓存目录不可写时，读命令照常；`sync` exit 1 且信息明确。
5. **并发**：两个 `sync` 同时跑，`chain` 不损坏，至少一个成功。
6. **性能**：100k 合成仓上 `graph` / `list` / `check` 的冷（无缓存）、热（命中）、`--no-cache` 三组时间与内存峰值，全部记录。
7. **jj**：行为与今天完全一致（不支持缓存）。

| 替代 | 否掉的理由 |
| --- | --- |
| 缓存放 XDG 用户目录 | 跨克隆共享要自己算 key，仓库移动/改名就要处理失效；`.git` 下天然一仓一份 |

## 落地顺序（2026-10-29）：先总流，后缓存

依赖是单向的：**缓存存的就是总流吐出来的那条记录**（`OID → 属性`），所以记录的形状必须先由流定下来。反过来先做缓存，等于在还没有消费者的时候就冻结一个磁盘格式；等流一加字段，格式和版本号都要返工一遍。

| 维度 | 总流（`action-log-relations`） | 缓存（本 issue） |
| --- | --- | --- |
| 收益 | 立刻有人用：下游插件一次拿全动作信息 | 现在零收益（372 提交、~60 ms 进程地板） |
| 风险 | 给 `--jsonl` 加字段，向后兼容 | 写盘、并发、损坏、GC、只读仓 |
| 验证 | 与 `graph` / `path` 对账 | 必须 100k 合成仓 + 字节一致证明 |
| 前置 | 无 | 记录形状（来自总流）+ `perf-audit` 的触发条件 |

结论：**总流先落地**，建议拆两个 apply（先 T1 字段，再 T2 文件/行数）；缓存继续等触发条件。等它落地那天，"缓存是总流的副产物"才真的成立——同一份记录，一边渲染成 NDJSON，一边落盘。

关系上记一条 `blocked-by action-log-relations`：不是"流不做，缓存就写不了"，而是**记录格式只能由流先定**；哪天改主意（比如缓存只认 T1、不等 T2），撤掉这条边就行。

> 2026-10-29 test 修正（第二次测量）：门槛取决于读路径。`Log()`（默认序）从 ~3k 提交起缓存就回本（1.5–3.5 次读，100k 省 73%）；`action log`（author-date）要 100k 全量 dump 且只值 36%。"关 commit-graph"不是通用优化，只对 `action log` 全量扫描有意义。详见 test 节。

## test（2026-10-29）：什么规模才划算

> **同日更正（第二次测量）**：第一版把 `action log` 的遍历方式当成了所有读命令的方式。实际是两条路径——`Log()`（默认序）供 `graph` / `list` / `check` / `path` / `status` / `show`，`LogEach()`（author-date）只供 `action log`。下面按路径分开；上一版"缓存只省 1/3"的结论只对 `action log` 成立。

**结论先行**：

1. **两条路径的成本结构完全不同。** `Log` 路径今天 100k 972 ms，其中"读正文"占 744 ms，枚举只要 229 ms——缓存把它压到 262 ms（**−73%**）。`LogEach` 路径今天 1,300 ms，光枚举（author-date）就 800 ms——缓存只能压到 834 ms（**−36%**）。
2. **缓存对 `Log` 路径从 ~3k–10k 提交起就划算**：回本只要 1.5–3.5 次读。对 `action log`，要么 100k 级全量 dump，要么不做——它的首屏靠 `--limit` 早停（46 ms），缓存帮不上。
3. **commit-graph 只对"枚举"有用**：`Log` 路径枚举 229（有图）/ 763（无图），body walk 两者几乎一样（973 / 951）。对 `LogEach` 的 author-date body walk，图反而是 −35% 的拖累（1,300 / 858）。所以不要全局关图；它只在"`action log` 全量扫描"这一种情况下值得关。

### 方法与口径

- **合成仓**：逐字节复用本仓 382 条真实提交消息（355 B/条），按序循环；空树；时间每条 +60 s；`git fast-import` 建仓后 `git commit-graph write --reachable`（"有图"状态）。规模 1k / 3k / 10k / 30k / 100k；另造 100k 合并仓（每 6 条一次 merge）做拓扑对照。
- **两条路径**：
  - `Log` = `git log --format=%H%x1f%aI%x1f%B%x1e`（今天 `git.go:33` 的命令），默认序，一次读进内存；
  - `LogEach` = `git log -z --author-date-order --format=%H%x00%aI%x00%B`（今天 `git.go:56` 的命令），流式。
  - 缓存 = 对应的枚举命令（`--format=%H` 不带/带 `--author-date-order`）+ 读层 + 解码。
- **记录层**是原型格式：20 B OID + 标志 + 日期 + 长度前缀字符串，**77 B/提交**；解码用 map 按 OID 查表。
- **计时**：每项 5 次取 min；机器 Windows / NTFS / Git 2.55 / Go 1.27，进程地板 ~42 ms。探针是 `.cacheprobe/` 里的一次性 Go 程序（不入库），复用 `internal/trailer.Parse` 与 `model.DefaultRelationSet`。
- **为什么 `Log` 路径可以用默认序**：`engine.Build` 拿到动作后按 `Date`（author date）对每条 issue 稳定重排再折叠（[engine.go:77](../internal/engine/engine.go#L77)），所以遍历顺序只影响**同一秒并列**的 tie-break 与 `Issue.Domain`；缓存枚举用同一条 `git log` 序，这些也原样不变。

### 6. 对设计的修正

- **枚举要分两条**：`Log` 路径用 `git log --format=%H`（默认序），`LogEach` 路径用 `git log --author-date-order --format=%H`。缓存只回答"这个 OID 的记录是什么"，用哪条序由命令决定——这仍是"顺序只认 git"。
- **`sync` 必须批量或增量**：sync 仍是一次全扫。`Log` 路径 100k 一次 1,043 ms，回本 1.5 次读——批量下很容易，逐提交 sync 仍然不可行。增量可以用 `git rev-list <new> ^<last-synced>` 只枚举新增段（需要"上次同步点"的引用语义）。
- **验收目标可以写实**（100k 合成仓）：`graph --json` ≤ 0.6 s、`list` ≤ 0.5 s、`action log --jsonl`（全量）≤ 0.9 s；本仓（382 提交）三者都应在 0.11 s 以内，即缓存对小仓不可见也不拖慢。
- 记录层体积与解码都不是瓶颈：77 B/提交、0.34 µs/条。

### 7. 一份层，两条序（"写一次、读多次"仍然成立）

缓存层存的是 **`OID → 记录`**，不是"第 N 条是谁"。记录里只有属性、没有顺序，所以：

- **一份层，两条路径共用**：`Log` 路径和 `LogEach` 路径查的是同一张表；不会存两份，层体积仍是每提交一条。
- **`sync` 用哪条序写都一样**：记录与序无关。用便宜的默认序写（100k 973 ms）比按 author-date 扫（1,300 ms）省 1/3；记录里带 author date，所以 `action log` 读到一份"按默认序写"的层，`date` 字段也完整。
- **读的时候各付各的枚举费**：`Log` 路径 229 + 34 ms，`LogEach` 路径 800 + 34 ms。差的 570 ms 是 author-date 的固有成本，不是分路径或缓存带来的——要免掉它只能缓存"顺序"，而那条路已被否（新提交要插到最前）。

一句话：**写一次（默认序）→ N 个命令各取所需**。分路径只改变每个读者自己的枚举价，不改变"一次写"。

### 8. 没测 / 限制

- **没能克隆真实大仓**（本机访问 GitHub 失败：schannel `SEC_E_NO_CREDENTIALS`），全部是合成仓。正文与 trailer 组合是真实的，但**树是空的**；缓存不碰 T2（改动文件/行数），所以空树只影响"真实仓的 I/O 局部性"。
- 只测了两种拓扑：线性、每 6 条一次 merge；无 octopus、无很长的并行分支。
- "有图反而更慢"是 **Windows + Git 2.55 + NTFS** 的实测，Linux/CI 与其它 git 版本必须复核。
- 探针把 42 MB 输出读进内存；`Log()` 本来就是全量读，所以 `Log` 路径的数字更贴近；`LogEach` 路径 kiln 是流式的，实测比探针快约 5%。
- 解码原型未优化（100k 33.6 ms）：排序数组 + 二分、或一次读进大缓冲还能再降。
- 首字节延迟差异很大（有图 42 ms、无图 530 ms），说明 git 两条路径的缓冲策略不同；本表只比总时长。
- 探针踩过的坑（对实现有参考价值）：`bufio.Reader.Read` 会短读，按 `Read` 的返回值推进会让层解码错位——必须 `io.ReadFull`；这条同样适用于"验收第 2 条 损坏退化"。
- **建层只测了两种形态**：全量 `git log` 一次（100k 973 ms）与增量 1 条（rev-list 52 ms + cat-file ~50 ms）；增量 10/100/1000 条没有逐点测，按每对象 ~9 µs 外推。全量若改用 `rev-list + cat-file` 实测 1,227 ms，比 log 慢（见修订后 hypothesize §3）。

## hypothesize（2026-10-29 修订）：两条读路径，一份记录层

> 上一版假设"所有读命令都走 author-date 枚举"，于是把收益估成 1/3、门槛推到 100k。test 更正后按两条路径重推：下面替换的是枚举（第 2 条）、写入（第 4 条）与验收（第 7 条），记录层与"顺序只认 git"这两条不变。

结论先行：

1. **记录层不变、与序无关**：`OID → T1 记录`（trailer 全字段 + author date + `isAction` + `subject` + `unknownKeys`）。一份层，两条路径共用。
2. **枚举两条，都由 git 给**：`Log` 路径 `git log --format=%H`（默认序），`LogEach` 路径 `git log --author-date-order --format=%H`。缓存不存顺序、不排序。
3. **写只有一条，而且是增量的**：`kiln cache sync` 用 `git rev-list HEAD ^<已覆盖 tip>` 找新增提交，一次 `git cat-file --batch` 取消息，解析后写一个新层；层头记下本层覆盖的 tip。首次（或版本/词表不符）才全量。
4. **读默认用缓存（有就用），并且顺手把补缺写回去**：枚举完整才声明 `covered=HEAD`；写失败静默；`--no-cache` / `KILN_NO_CACHE=1` 同时关读和写。
5. **`action log --limit` 不走缓存**：有图时枚举只要 46 ms，"枚举 800 + 解码 34"反而更慢。
6. **成本（实测）**：首次建层 100k 973 ms（一次 `git log` 走完）；增量 1 条提交 ≈ 100 ms；命中读 `Log` 路径 262 ms、`LogEach` 路径 834 ms。

### 1. 记录（比原型多两个字段）

```text
OID(20) | authorDate(8) | tzOffset(2) | flags(1) | 字段块(TLV)
flags: bit0 = isAction
TLV:   issue action title subject domain scope target refs tags
       relations(name,target) unrelate unknownKeys
```

`subject` 与 `unknownKeys` 是下游还要用、但只能从消息里算出来的两个值：

- `action log` 的 `title` 兜底用 `subject`（`engine.Subject`，首行非空）；
- `check` 报 `unknown-trailer` 用 `unknownKeys`（`trailer.UnknownKeys`）。

不存它们就得存原文（355 B/条）——那是缓存想省掉的东西。两项都依赖词表，所以层头的**词表指纹**仍然覆盖得住。

（test 里的 77 B/提交是**下界**：那个原型只写了 `refs / target / scope / relations / unrelate`，漏了 `issue / action / title / domain / tags / subject / unknownKeys`。正式格式见下。）

### 1.1 文件与磁盘布局

```text
.git/kiln/records/              # $(git rev-parse --path-format=absolute --git-common-dir)/kiln/records
  layer-<40 hex>.rec            # 不可变；名字 = 内容（除末尾 20 B）的 SHA-1
  layer-<40 hex>.rec.tmp-<pid>  # 写临时名，完成后 rename；读侧只认 .rec
```

**一个层一个文件**；没有 chain、没有索引文件、没有锁文件（§8）。常态 ≤64 层。

**为什么分层**：一次写入只追加新记录，不改已有文件。

| 维度 | 单文件（每次重写） | 分层（本方案） |
| --- | --- | --- |
| 每次提交的写量 | 整份（100k ≈ 13 MB） | 一个 1 条记录的小层（≈ 350 B） |
| 并发写 | 要么加锁，要么读改写（会丢掉别人刚写的记录） | 只新增文件 + 内容寻址，天然幂等 |
| 读到的状态 | 重写窗口内靠 rename 兜底 | 任意时刻都是若干完整层的并集 |
| 崩溃 / 断电 | 旧版已被替换，只能整份重来 | 旧层不动，最坏多一个坏文件（哈希不符被忽略） |
| 删除 / GC | 重写整份 | 先写新层再删旧层，中间状态仍然合法 |

**怎么分**：

1. 一次写入（读顺手写或 `sync`）产生 ≥1 条"现有层里没有的 OID" → 写一个新层，只装这批记录 + 当时的 covered tips。
2. 层内记录按 OID 升序、字符串表按字典序 → 序列化确定，同输入同名。
3. 层数达到 **64** 时合并成一层：读所有层 → 按 OID 去重 → 重建字符串表 → 写新层 → 尽力删旧层。合并是纯本地操作（不读 git），100k ≈ 80 ms；摊到 64 次写 ≈ 1.3 ms/次。
4. **上限只决定两件事**：合并多久来一次、一次读要开几个文件。64 层时读多 64 次 open（~1–2 ms）；哈希量与层数无关，因为总字节不变。
5. 典型形态：一个大层（全量或上次合并）+ 若干 1 条的小层；`gc` 之后回到一个。

**为什么不无限分层**：读要 open 每个层，层数会随提交数线性长；而且 GC 最终要重写，合并就是这个重写的自然形态。

**层数对读的影响（实测）**：同样 13 MB 总量，读 + SHA-1 校验 5 次取 min：

| 层数 | 1 | 16 | 64 | 256 | 1024 |
| --- | --- | --- | --- | --- | --- |
| 读 + 校验 | 8.6 ms | 11.2 | 10.8 | 17.4 | 52.1 |

64 层比单文件多约 **2 ms**（每多一个文件只多一次 open/close，Windows 上约 30–60 µs）。真正的拐点在几百层：256 层 +8.8 ms、1024 层 +43.5 ms。所以 64 这个上限是"读侧几乎无感、写侧合并够稀疏"的交点；解码量跟记录数走、不跟层数走，每层多一张几百个串的小表可以忽略。

层布局（小端）：

```text
偏移  长度      字段
0     8        magic "KILNREC1"
8     2        layout = 1
10    20       词表指纹（关系名 / 槽位 / 强度 / 别名）
30    2        tipCount
32    20×N     覆盖的 HEAD（去重、升序）
..    4        strCount
..    ...      字符串表：strCount × (u16 长度 + UTF-8)，字典序
..    4        recCount
..    ...      记录区：recCount 条，按 OID 升序
末尾  20       SHA-1（前面所有字节）——文件名就是它的 hex
```

单条记录：

```text
OID[20] | date i64 | tz i16 | flags u8 | 7 × u32 字符串表索引
flags: bit0 isAction; bit1 "subject == title"（相等就不再存 subject）
索引：issue action title subject domain scope target
数组：refs / tags / unrelate / unknownKeys  （u16 个数 + u32 索引）
      relations                            （u16 个数 + (u32 name, u32 target)）
```

**为什么带字符串表**：100k 提交里 issue 名只有几百个、action 只有 6 个、target/refs 都是 issue 名、标题重复率也高。内联字符串每条约 240 B（原文 355 B 的七折），建表后约 **130 B/条 → 100k ≈ 13 MB**。表按字典序、记录按 OID 排序，序列化因此是确定的：同样输入产生同样字节、同一个文件名——这是并发幂等（§8）和内容寻址的前提。

其它约定：

- 权限 0644 / 目录 0755；**不 fsync**——断电最多留一个哈希不符的层，读侧忽略、下次重写。
- 布局或字段一变就换 magic（`KILNREC2`），旧层当没有，不做迁移（§collect 第 4 条）。
- 合并 = 读所有层 → 按 OID 去重 → 重新建表 → 写一个新层 → 尽力删旧层；因为序列化确定，两个进程同时合并会得到同一个文件名。
- 100k 的估计值（13 MB / ~130 B 一条）要在 apply 里实测，误差主要来自标题长度。

### 2. 读路径（两条）

```text
Log 路径（graph/list/check/path/status/show）
  枚举   git log --format=%H                     100k 229 ms
  查表   OID → record（命中直接构建 model.Action）
  补缺   git cat-file --batch，只取缺的（通常 0 条）
  构建   engine.Build（与全扫路径同一份代码）

LogEach 路径（action log，无 --limit）
  枚举   git log --author-date-order --format=%H 100k 800 ms
  其余同上

action log --limit N：不查缓存，直接流式（有图 46 ms）
```

**冷缓存不绕路**：目录里一个合法层都没有时，直接用今天的全扫（`Log` 或 `LogEach`），**不要**先用 `rev-list` 枚举再 `cat-file` 补——实测全量 `cat-file` 1,227 ms 比 `log` 973 ms 慢，冷启动会白亏 25%。有层之后才走"枚举 + 补缺"。

**全史重写之后**（rebase / amend 全部提交）：缓存里全是旧 OID，第一次读会 100% 走 `cat-file` 补缺，比直接全扫慢约 25%；这一次会把新记录写进去并声明新的 `covered`，第二次起恢复命中。

**读顺手写**（这是本版与初版最大的不同）：读路径把它**本来就要算**的那批记录（补缺出来的，通常 0 条或几条）写成一个新层——数据已经在手里，只多一次编码 + 落盘。实测 100k 冷读 **+238 ms**（解析只做一次；其中编码约 100 ms、写 3 ms），之后命中为 0。两层规则：

- **枚举完整**（`Log` 路径、无 `--limit` 的 `LogEach`）→ 新层声明 `covered = {HEAD}`；
- **部分枚举**（`action log --limit N`）→ 层照写，但**不声明覆盖**，只贡献记录。

写失败（只读仓、磁盘满、沙箱）**静默跳过**：不改 stdout、不改退出码。

**层数上限**：读路径发现层数 ≥ 64 时，先做一次纯本地合并（读所有层 → 按 OID 合并 → 重建字符串表 → 写新层 → 尽力删旧层，100k ≈ 80 ms），避免"每提交一层"无限增长；合并同样无锁、幂等（见 §8）。

两条路径与全扫共用 `engine.Build` 与渲染，所以"命中与否字节一致"仍是结构保证，不是测试保证。

### 3. 写路径（增量优先）

```text
已覆盖 = HEAD ∈ ∪covered           只读 ≤64 个层头（并校验哈希），无 git 进程；命中即 exit 0
covered = 各层头里记录的 tip 集合（只信校验通过的层）
新增    = git rev-list HEAD ^<covered...>          100k 加 1 条 ≈ 52 ms
消息    = git cat-file --batch（一次进程）          100k 加 1 条 ≈ 50 ms
记录    = trailer.Parse + engine.Subject + trailer.UnknownKeys
新层    = layer-<sha1>.rec（不可变、自校验名），层头记 covered' = {HEAD}
目录    = 写完 rename 到位；不需要 chain，也不需要锁（见 §8）
```

`sync` 的语义是**幂等补缺**，不是"每次重建"：HEAD 已经被某个（校验通过的）层覆盖，就直接 `已是最新`，一个 git 进程都不开。这一步顺带把并发问题降级了（见 §8）。

**全量只在首次/版本不符/词表不符时做**，用 `git log --format=%H%x1f%aI%x1f%B%x1e`（100k 973 ms）。不用 `rev-list + cat-file` 做全量：实测 1,227 ms（cat-file 每对象约 9 µs，pretty 打印是流式批量），反而慢。

不 `fsync`：断电最多留下一个哈希不符的层，读侧忽略、下次 `sync` 重写；缓存不值得为持久性付这个代价。

### 4. 增量 sync 的边界

- `rev-list` 报未知版本（covered tip 被 GC / 仓库被换）→ 回落全量。
- HEAD 回退或切分支：只算"从 HEAD 可达但未被覆盖"的部分；覆盖不到的旧记录留在层里等 GC。
- 覆盖语义按 **tip 的可达集**：层头存写入时的 HEAD，`rev-list HEAD ^t` 恰好给出之后的增量；多层各存各的 tip，取并集。

### 5. 收益与门槛（重算）

| 命令 | 100k 无缓存 | 100k 命中 | 省 |
| --- | --- | --- | --- |
| `graph --json` | 1,228 | 518 | 58% |
| `list` | 1,114 | 404 | 64% |
| `action log --jsonl`（全量） | 1,335 | 869 | 35% |
| `action log --limit 5` | 46 | 46（不走缓存） | — |

| 提交数 | `Log` 路径每次读省 | 增量 sync | 回本读 |
| --- | --- | --- | --- |
| 3,000 | 21 ms | ~100 ms | 5 |
| 10,000 | 72 ms | ~100 ms | 2 |
| 30,000 | 216 ms | ~100 ms | 1 |
| 100,000 | 710 ms | ~100 ms | 1 |

结论：**≥10k 提交时，每次提交后 sync 一次也能回本**；3k–10k 建议批量 sync。表里的命中读按原型 7.7 MB 层测（解码 33.6 ms）；正式格式约 13 MB，解码预计 +15–25 ms，不改变结论。

### 6. 开关：一律开启，`--no-cache` 是唯一例外

缓存是**后台行为**，不是用户要记得打开的开关：没有配置项，读命令自动写、自动合并、自动清理。

- **关闭**：`--no-cache` / `KILN_NO_CACHE=1`，只影响本次进程；输出逐字节不变——它存在的意义是排查问题和做 A/B 验收。
- **`kiln cache gc`**：唯一保留的命令，按 `rev-list --all` 强制清理（旧记录、坏层、旧指纹层、临时文件）。日常不需要，读路径自己维护。
- **位置**：`$(git rev-parse --path-format=absolute --git-common-dir)/kiln/records/`；老 git（<2.31）回落相对路径拼接。
- **兼容性**：配置里现在没有 `cache` 键；写过 `"cache": {…}` 的文件会被严格解析判为 unknown field（0.x 不承诺配置兼容）。播种的默认配置只留一句注释说明它默认开启、`--no-cache` 可绕过。

### 7. 与"总流"的关系

"扫一次、多次取"现在不需要额外的命令：**第一次读就是那次扫描**，它顺手把结果落盘，后面的读直接命中。`sync` 只是把"第一次读"提前做掉（预热），或者在批量导入后一次性补齐。

### 8. 多 worktree、并发、损坏

**worktree**：缓存放 `--git-common-dir` 下，所有 worktree 共享一份。键是 OID（对象级），与"哪个 worktree 写的"无关；实测 linked worktree 上 `git rev-parse --git-common-dir` 返回主 `.git`，kiln 在 worktree 里读到的历史与主仓一致。各 worktree 的 HEAD 各自做增量，层头记各自的 covered tip，取并集。**GC 的可达性按 `git rev-list --all` 算**，不能只按当前 HEAD：否则一个 worktree 的 GC 会删掉另一个还在用的记录——正确性不受影响（缺了走补缺或全扫），只是白丢效率。

**并发：不要锁，去掉 `chain`，目录即索引。**

- 层名是内容哈希：两个 `sync` 写出同样内容 → 同一个文件名，**幂等**；写临时名再 `rename` 到位，读者只认 `layer-*.rec`，看不到半成品。
- 读者把目录列出来，逐个打开、校验、合并；读到一半有新层出现或被删都无害——记录按 OID 合并，同 OID 的记录内容必然相同。
- 删除（合并、GC）永远是"先把新层放好，再尽力删旧层"；删不掉（Windows 上还有读者打开）就下次再删，留着只是重复记录。
- 于是没有锁、没有 stale lock、没有"chain 写坏"这种状态；唯一的互斥点是重命名同名文件，失败即视为"别人已经写好了同样的内容"。
- 代价：每次读多一次 readdir + 最多 64 次 open（~1–2 ms），可忽略。

**并发 sync 为什么是"空转"而不是"冲突"**：记录的键是不可变 OID，`sync` 的语义是"补齐缺的记录"，不是"重建"。于是：

- **缓存不失效时 `sync` 什么都不做**：HEAD 已被某个校验通过的层覆盖 → 直接 exit 0，连 `rev-list` 都不跑。多个 agent 反复 `sync` 同一状态，成本是几十微秒级的层头读。
- **两个 `sync` 同时看到"有新提交"**：各自做一遍增量（~100 ms），写出**同一个内容哈希**的层 → 第二个 `rename` 覆盖的是逐字节相同的文件，等于空写；不会出现第二份层，也不会互相覆盖坏。
- **两个 `sync` 的 HEAD 不同**（两个 worktree、或一个先一个后）：增量集合不同，各写一层，并集正好覆盖两者；没有"谁赢"的问题。
- **两个 `sync` 的词表不同**（一个进程刚改过配置）：指纹进层头 → 层名不同 → 两份并存；每个读者只认自己指纹的层，另一份等 `gc` 清掉。**这是并发里唯一会"两种真相并存"的情形，而指纹把它关掉了。**
- 真有重复劳动，上界也就是一次增量（~100 ms），且只在"两个进程同时落在同一个 race 窗口"时发生；精确去重（第二次读 covered 再判断）不值得为它引入锁。

**读者也写**：并发分析不变——读路径写的也是内容寻址的层。两个读者补同一批记录 → 同一个层名；一个读者合并、另一个同时追加 → 合并层只收它读到的旧层，追加层名字不同、并存，重复记录在按 OID 合并时自然消掉。新增的只有一种失败：读成功、写失败（只读仓、磁盘满、沙箱）——静默跳过，输出与退出码不变。

**损坏 / 丢失**：

| 情形 | 读路径 | 写入 / 维护 |
| --- | --- | --- |
| 目录不存在、被删 | 全扫（今天的行为），不报错 | 下次 `sync` 重建 |
| 层被截断、位翻转、改名 | 整层忽略（层名 = 内容 SHA-1，校验不过就当不存在） | `sync` 重新写；`gc` 清掉坏文件 |
| 头部 magic / 版本 / 词表不符 | 整层忽略 | 新版本层照常写；旧版本留给 `gc` |
| 半写 / 断电 | 看不到（临时名 + rename） | 重跑 `sync` |
| 磁盘满 / 只读仓 | 不受影响 | `sync` exit 1 + 明确信息 |
| 内容错但哈希通过 | 只可能来自代码 bug，靠"字节一致"验收兜底 | — |

**必须每次都校验整层哈希**：7.7 MB 层实测 SHA-1 **4.6 ms**（1.7 GB/s），100k 的 11 MB 层约 6 ms——相对 262 ms 的命中读可忽略。不校验的话，一个翻转的字节会被解成一条"看起来正常"的错记录；校验不过就整层丢，不做部分恢复（无法定位坏在哪条）。

### 8.1 用 Go 的并发做到"不阻塞"

诚实的前提：kiln 是 CLI，**进程退出后没有"后台"**。所以"不阻塞"只能是**不阻塞输出**——缓存工作与渲染/打印重叠，退出前 join 收拢。让进程提前返回、把写盘留给"之后"是不可能的：goroutine 会跟着进程一起死，只留下被忽略的临时文件。

值得开 goroutine 的地方（都只影响中间步骤，不影响输出字节）：

1. **编码 + 落盘**，与渲染重叠：100k 全冷读的编码约 50 ms，而渲染/打印是 10–300 ms（`path --all` 是 35 MB，几百毫秒）；重叠后这 50 ms 基本白拿。主 goroutine 只负责写 stdout。
2. **多层解码与校验并行**：≤64 个层、总共 13 MB；每层一个 goroutine，用 `GOMAXPROCS` 限流（`errgroup` + `context`）；合并进 map 时要么单线程、要么按 OID 前缀分片，最终编码前统一按 OID 排序。预计省 20–30 ms。
3. **补缺时的消息解析并行**：`cat-file --batch` 是流式的，读到一条就丢给 worker pool 解析；100k 是 70 ms 的单线程成本，8 核大约 15 ms。
4. 可选：**`mmap` 层文件**，省掉一次 13 MB 拷贝（Windows 走 `CreateFileMapping`），约 5–10 ms。

不能做 / 要小心的：

- **不能在退出时不管 goroutine**：会白干（临时文件被忽略，安全但没写进去）。
- **不要起子进程做"后台写"**：那等于把 daemon 换个名字，还要处理孤儿进程。
- **只有主 goroutine 写 stdout**；缓存的任何错误都不改退出码、不往 stdout 写。
- **取消**：`action log` 提前停止（`--limit`、破管道）时用 `context` 取消扫描，并且**不要**写一个声明 `covered = HEAD` 的层（枚举不完整）；已经算出的记录可以写，`covered` 留空。
- **确定性**：并行只用于顺序无关的中间步骤；编码前统一排序，所以并发不改变层名。
- **测试**：`go test -race`；同一状态跑两次比对层名。

**净收益的实话**：这些加起来在 100k 上是几十毫秒（相对 1.3 s 的扫描约 3–5%）；真正的收益来自缓存本身（973 → 262 ms）。并发值得做，但别指望它改变量级。

### 9. GC：全部自动，`gc` 只是逃生口

GC 只有两种活：**删掉永远不会再被用的层**（坏层、旧 magic、被杀留下的临时文件）和**丢掉不可达记录**（rebase / amend 之后的旧 OID）。前者不需要可达性，后者要 `rev-list --all`。把它们挂到读路径已有的三个时机上，就不需要额外命令：

1. **扫描时（免费）**：每个层打开即校验哈希与 magic；不符 → 立即 `unlink`（它永远不会被用上，留着只占地方）。`.tmp-*` 超过 1 小时 → `unlink`（写到一半被杀的残留；1 小时是躲开活着的写者）。
2. **合并时（已有动作）**：层数 ≥64，或完整枚举里 OID 全部未命中且已有层（历史被重写）。合并在去重的同时做一次**垃圾判定阶梯**：
   - 记录数 == 本次枚举到的 OID 数 → 没有候选垃圾，什么都不用算（单分支、无重写的常态）；
   - 否则跑 `git rev-list --count --all`（100k ≈ 73 ms）：与记录数相等 → 全是别处的可达提交，仍然不用清；
   - 再否则跑 `git rev-list --all` 取集合（100k ≈ 200 ms），丢掉不可达记录，并把 tips 收敛到"仍在 `--all` 里"的那些。
3. **重写信号（免费判定）**：完整枚举 100% 未命中且已有层 → 立即执行第 2 步，不等 64 层。

**成本**：100k 上空闲合并 ≈ 80 ms（每 64 次写一次 → 1.3 ms/写）；单分支有候选但无垃圾 +73 ms；真有垃圾 +200 ms。这三种都只发生在合并那一次读上，摊到写上是 1.3–4.4 ms。

**旧指纹层不自动删**：不同分支可以带不同的 `.kilnconfig.jsonc`，切分支时指纹会变；自动删会在来回切时反复重建 13 MB。它们只被显式的 `kiln cache gc` 清——这也是 `gc` 唯一的独占职责。

**`kiln cache gc`**：强制做一遍上面第 2 步（不看候选，直接跑 `--all`），外加删旧指纹 / 旧 magic / 坏层 / 临时文件。它是逃生口（换过词表、想立刻回收磁盘、怀疑缓存脏了），**不是日常路径**——正常情况垃圾在合并时已经清掉。

**不做**：定时器、后台线程、daemon（非目标）；也不在每次读上算可达性——可达性只在"合并且存在候选"时才付费。

**安全**：任何删除都只是让下一次读变慢；读者在任意中间状态（层被删、被合并、被替换）看到的都是合法并集。

### 10. 验收（替换上一版第 7 条）

1. **字节一致**：本仓 + 100k；`graph` / `list` / `check` / `path` / `status` / `show` 与 `action log`（含 `--limit`）在 `--no-cache` / 命中 / 缺层 三态下 stdout 与退出码一致。
2. **损坏退化**：截断、翻转一个字节、改名 → 该层被忽略，输出不变，不报错。
3. **版本/词表不符** → 整层忽略，回落全扫。
4. **只读仓**：读命令照常；`sync` exit 1 且信息明确。
5. **并发**：两个 `sync` 同时跑（两个 worktree）→ 层不损坏、没有半成品被读到、至少一个成功；`sync` 与读并发时读到的输出与串行一致。
6. **worktree**：两个 worktree 各 sync 一次后共用同一份层；删掉其中一个 worktree 不影响另一个；GC 用 `rev-list --all` 时另一 worktree 的命中率不下降。
7. **性能**（100k，有 commit-graph）：`graph --json` ≤ 0.6 s、`list` ≤ 0.5 s、`action log --jsonl` 全量 ≤ 0.9 s、`action log --limit 5` ≤ 60 ms（无图时它与今天一样是 ~544 ms，缓存不掺和）。
8. **增量**：100k 仓加 1 个提交后 `sync` ≤ 200 ms，新层只含 1 条记录，之后读命中率 100%。
9. **自愈**：删掉一个层、翻转一个字节后，输出不变；再 `sync` 一次后命中率恢复 100%。
10. **空转**：HEAD 已被覆盖时 `sync` 不产生新层、不 spawn git 进程；两个进程对同一 HEAD 各 `sync` 一次后，目录里仍然只有一层（内容寻址 + 校验通过后幂等）。
11. **读顺手写**：空目录下第一次 `graph` 建层；第二次 `graph` 命中且不产生新层；`action log --limit 5` 产生的层不声明覆盖（`covered` 为空），但它的记录能被后续读命中。
12. **写失败静默**：缓存目录只读 / `GIT_DIR` 只读时，读命令的 stdout、stderr、退出码与 `--no-cache` 完全一致。
13. **层数上限**：连续 100 次"提交 → 读"后，层数 ≤ 64（读路径的本地合并生效），且总记录数不变。
14. **默认关**：配置里没有 `cache` 项时，任何读命令都不创建 `.git/kiln/records/`、不写盘；`kiln cache sync` exit 1 并提示去配置里打开。
15. **配置开关**：`cache.enabled=true` 后行为与验收 1–13 一致；`--no-cache` / `KILN_NO_CACHE=1` 在开启后仍能完全关掉（输出字节不变）。
16. **GC 自动**：全史 rebase 后第一次读触发合并 + 可达性过滤，层数回到 1、记录数回到可达数；正常单分支读**不调用** `rev-list --all`（`GIT_TRACE2` 断言）；坏层在扫描时被删；`.tmp-*` 超过 1 小时被删；`rev-list --all` 失败时跳过 GC 且不报错。
17. **`gc` 逃生口**：显式 `gc` 能清掉旧指纹层与旧 magic 层；`gc` 前后输出字节一致。
18. **并发确定性**：`go test -race` 通过；同一仓库状态下连跑两次产生同名层；`--limit`/破管道取消时不留下声明 `covered` 的层。
19. **jj**：行为与今天完全一致（不支持缓存）。

## 结论（2026-10-29）

**落地了什么**（git 后端，`cache.enabled` 显式开启）：

- `internal/cache`：层格式（`KILNREC1`、词表指纹、字典序字符串表、按 OID 排序、SHA-1 trailer、文件名即内容哈希）、扫描/校验/原子写/按 OID 合并/Sweep；确定性编码 → 同输入同名 → 并发幂等。
- 读路径：`Log` 路径（`graph` / `list` / `check` / `path` / `status` / `show`）枚举 + 查层 + `cat-file --batch` 补缺 + 顺手写；`action log` 全量走**流式枚举**（`EachOIDAuthorDate`）边枚举边查表边输出，`--limit` 保持直读。
- 写路径：`kiln cache sync` 增量预热（HEAD 已覆盖即空转、不开 git）；`kiln cache gc` 按 `rev-list --all` 清理；两者与读路径共用同一个写层函数。
- 自动 GC：扫描时删坏层；合并（层数 ≥64）时按"记录数 vs 枚举数"判定，有候选才跑可达性剪枝；**重写信号**（完整枚举全未命中且已有层）立刻合并 + 剪枝。
- 开关：**默认开启**（后台行为）；`--no-cache` / `KILN_NO_CACHE` 是唯一例外；`kiln cache gc` 是唯一保留的命令。

**实测**（100k 合成仓，Windows，min of 5）：

| 命令 | 全扫 | 命中缓存 |
| --- | --- | --- |
| `graph --json` | 1,266 ms | 631 ms（−50%） |
| `action log --jsonl` | 1,413 ms | 1,001 ms（−29%） |
| `action log --limit 5` | 103 ms | 103 ms（不走缓存） |

冷读 +238 ms（一次性）；层 7.3 MB（合成仓标题大量重复，真实仓更大）；`cache gc` 437 ms。

**验收覆盖**：字节一致（冷 / 命中 / `--no-cache` 三态，六个读命令 + `action log` 两种模式 + worktree）、损坏层回落、自愈、空转、层数上限合并、合并剪枝、重写信号、`sync` 幂等、`gc` 丢弃不可达、默认关、配置开关、写失败静默，共 15 条测试钉住。

**没钉住的**：

- 真实只读文件系统（用"把 `.git/kiln` 做成文件让写必败"模拟）；
- 并发 `-race`（本机 CGO 关闭，跑不了；确定性由排序编码保证）；
- 两个进程同时对同一 HEAD `sync` 的压测（靠内容寻址 + 原子 rename 幂等，逻辑成立但没压）；
- git < 2.31 的 `--path-format` 回落、Linux/macOS 的表现。

**与设计的偏差**（都是实测后的收敛）：

- GC 的第二档 `rev-list --count --all` 没实现：直接从"记录数 > 枚举数"跳到 `rev-list --all`，只在有候选时才付费。
- `action log` 的缓存路径必须**流式枚举**才有收益：先枚举再渲染会让 100k jsonl 从 1,413 ms 变成 1,452 ms（比全扫还慢 4%），因为流式读取本来就把遍历和渲染重叠了。

## 非目标

- 不做 daemon / 常驻进程 / 跨进程内存共享；
- 不做跨机器共享缓存；
- 不缓存 diff 正文（T4 永远按需）；
- 不改任何命令的输出字节（命中与否必须字节一致）；
- 不在本 issue 里动 `path --all` 的 35 MB 输出（那是 `path-batch` / `issue-list-scaling` 的地盘）。
