# issue: action-granularity — 动作要不要分阶段提交

- **domain**：design
- **关联**：relates-to `status-by-domain`

## 背景

实现 `status-by-domain` 时，整个过程只留下了两个 kiln 动作：

```
status-by-domain   ask → apply
```

读代码、定方案、改代码、跑测试、在真实仓库里验证——这些环节**都没有**各自落成 `hypothesize` / `test` / `collect`，而是被压进了一个 `apply`。回看仓库，其余 issue 也清一色是 `ask → apply` 两段式。

也就是说：kiln 提供了表达"研究过程"的词汇，但实际用起来只用了两个端点。

## 要回答的问题

一个 issue 的动作应该多细？

**粗粒度（现状）**：`ask`（提出问题，通常连同设计一起）→ `apply`（实现一次性落地）。

- 好处：提交少、历史干净、不打断心流、不落半成品。
- 代价：研究路径被压扁成两点；`kiln path` 看不出"当时怎么想的"，也看不出哪一步验证过。

**细粒度**：把过程中的关键节点各自提交——`hypothesize`（先落方案）→ `test`（跑测试并记录结果）→ `conclude`（得出结论）→ `apply`（落地）。

- 好处：路径完整，可回溯"方案什么时候定的""哪次验证通过"。
- 代价：提交变多、有噪声，且"哪些节点值得单独提交"没有客观标准，容易滑向形式主义。

## 待定

1. 是否要一个**中间粒度**：只在两个节点额外提交——`hypothesize`（方案定稿）与 `test`（验证通过），其余过程仍并进 `apply`？
2. 与 `check` 的关系：当前规则只要求"含起点动作、以终点动作收尾"，多几个中间动作不影响判定，因此加细粒度**不增加**校验负担。
3. 要不要写进 Agent 的使用约定（例如 Skill 里规定：先 `hypothesize` 落方案，再 `apply` 落实现）？还是保持"随场景自由"？

## 非目标

- 不引入任何**强制**：`check` 不会因为缺中间动作而报错。
- 不改动作词表本身（`ask` / `hypothesize` / `collect` / `test` / `conclude` / `apply` 不变）。

## collect（2026-10-28）：63 个 issue 的实测——两段式已经不存在了

### 0. 先把前提更正

ask 写于 2026-10-14，依据是 `status-by-domain` 只有 `ask → apply`，并推断"其余 issue 也清一色两段式"。这个前提**今天不成立**：

- 63 个 issue / 297 个动作；**中位 4、均值 4.71、p90 10**；
- 41/63 个 issue 有 ≥3 个动作；恰好 2 个的 18 个，≤2 的 22 个（含 4 个只有 `ask` 的 open issue）。

所以问题已经从「只用了两端」变成「粒度分布是否健康、要不要强制/约定」。

### 1. 动作使用

| 动作 | 次数 | 覆盖 issue 数 |
| --- | --- | --- |
| `ask` | 63 | 63 |
| `hypothesize` | **73** | 30 |
| `test` | 49 | 20 |
| `apply` | 46 | 35 |
| `conclude` | 36 | 35 |
| `collect` | 30 | 25 |

中间动作里 `hypothesize` 最多（73 次），`test` 与 `collect` 次之；三者覆盖的 issue 数分别是 30 / 20 / 25。

### 2. 每个 issue 的动作数

| --- | --- |
| 1 | 4（open，只有 ask） |
| 2 | 18 |
| 3 | 9 |
| 4 | 6 |
| 5 | 9 |
| 6 | 4 |
| 7–9 | 5 |

双峰：**快改型 2 个动作，研究型 5–10 个，长尾到 18**。

### 3. 序列与「连发 hypothesize」

- `ask → apply` ×15；`ask → apply → conclude` ×5；`ask` ×4；`ask → conclude` ×3；其余 36 个 issue 的序列各不相同。
- 常见研究序列：`ask → collect → hypothesize → … → terminal`。
- **15 个 issue 出现 ≥2 个连续 `hypothesize`**，最长 5（`help-relation-flags`、`relation-revision`；`agent-ux-review`、`cli-necessity`、`relation-vocabulary` 各 4）。

解读：连续 `hypothesize` 是**方案修订**的自然形态（"假设（续）……"），不是重复提交；它们带来的是读侧长度——真正的噪声风险在**标题不可区分**，不在数量。

### 4. 与 `check` 的关系（代码事实）

- `engine.Check` 只要求「含起点动作、以终点动作收尾」；中间动作的数量不影响判定。
- 当前 `check`：58 ok / 5 warn / 0 error，5 条 warn 全是「缺少终点动作」。
- 因此加细粒度**不增加**校验负担；反过来，`check` 也不会因为缺中间动作报错（与「非目标」一致）。

没有单调变细或变粗：**粒度跟 issue 类型走，不跟时间走**。

### 6. 观察（留给 hypothesize）

1. 「中间粒度 = 只加 hypothesize + test」的提法已被实践打破：`collect` 也在用（25 个 issue）。
2. 快改 issue 保持 2 个动作是合理的，不该强制加中间节点。
3. 连发 `hypothesize` 是修订，不是噪声；但「续」很多时，`path` 的可读性依赖标题是否能区分。
4. 判据候选（不是规则）：**某一步的结论会被后面引用**（方案定稿 / 验证通过 / 外部证据落地）才值得单独提交；否则并进下一个动作。

### 7. 边界

- 只做本仓实测；外部对照（atomic commits / PR stacks / worklog 粒度）未做，留给 hypothesize 或 test。
- 不改词表、不改 `check`、不给任何强制。

## conclude（2026-10-28）：粒度是作者的选择，工具不教也不评

### 0. 裁决

- **不引入中间粒度规则、不写判据、不写 Agent 约定**。一个 issue 切几个动作，完全由作者按任务自定。
- kiln 只在「能被解析」的层面约束：**起点动作存在、以终点动作收尾、`--title` 必填**。这些是结构，不是方法论。
- 用户愿意切细也可以：本仓已有 18 个动作的 issue、5 连 `hypothesize`；工具不评价、不提示、不惩罚。

### 1. 为什么不做「判据」

- 判据听起来中立，落地只有两条路：进 `check`（强制）或进 Skill / 文档（教用户）。前者违背本 issue 的非目标，后者是「工具教用户怎么用」——kiln 是二进制工具，不承担这个职责。
- 判据无法客观化：collect 实测里快改 2 个、研究型 5–10、长尾 18，同一个仓库里都成立；任何阈值都会误伤。
- 表达能力已经由词表给出（`ask` / `hypothesize` / `collect` / `test` / `conclude` / `apply`）；选哪几个、切多细，是使用者的判断。

### 2. 本仓数据只作观察，不作规范

- 中位 4、p90 10、41/63 个 issue 有 ≥3 个动作；`hypothesize` 73、`test` 49、`collect` 30；15 个 issue 有连发 `hypothesize`。
- 这些只说明「词表被用起来了」，不说明「应该这样用」。
- ask 原来的担心（只用了两端）已被实践自然消解：不需要工具介入。

### 3. 与既有裁决的一致性

- `design-philosophy`（Zettelkasten）：原子性是方向，不是规则；工具只给两端约束。
- `check` 的规则只到「起点 + 终点」，不检查中间动作。
- `flag-value-leading-dashes`：写侧只拒绝「不可解析 / 会静默错」的输入（`--title` 必填），不评价工作方式。
- 文档仍可教**语法**（怎么调用、有哪些动作），但不教**工作方式**（切多细）。

### 4. 明确不做

- 不写 Skill / Agent 粒度约定；不加 `check` 规则、不加提示、不加 lint。
- 不改词表，不改任何命令行为。

### 5. 验收

- 本结论与 collect 数据留档；无代码改动。
- `check` 现状不变（58 ok / 5 warn，warn 均为缺终点）。
- 若将来出现「跨团队协作需要统一粒度」的真实场景，再另开 issue 讨论——当前没有。

> 一句话：粒度是作者的选择；kiln 只保证提交能被解析（起点、终点、标题），不评价你切几刀。
