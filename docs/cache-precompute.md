# issue: cache-precompute — 预计算缓存：还该预计算什么、能省多少、值不值

- **domain**：design
- **关联**：relates-to `commit-cache`（记录层缓存本身）；relates-to `cache-perf`（warm 读的钱花在哪）；relates-to `commit-prepend`（HEAD 前移后的首读，D1 是这条最可能的落地形态）

## 背景

kiln 的读路径已经预计算了两层**原始材料**：枚举快照是 `git log --format=%H` 的答案（按 HEAD 存），记录层是每条提交 trailer 解析后的字段。两层合起来让热读**不启动 git**。

没有预计算的是再往上一层：折叠出来的 `model.Repo`，以及各命令的视图（计数、过滤、关系边、排版）。这些今天每次读都重做一遍。这条 issue 要问的是：**要不要把它们也存盘？**

先决问题是"哪些命令真的需要算"——不为不需要算的命令存答案。

## 要回答的问题

1. **预计算到哪一层**：记录（已有）／折叠模型 `model.Repo`／视图（`status` 的行、`list` 的过滤结果、`graph` 的边与布局）。三层的失效面与复用范围差很多。
2. **能省多少**：收益只出现在**同一 HEAD 的重复读**上；提交后的第一次读仍要全算，一分不省。需要一份按层拆开的成本表，而不是端到端一个数。
3. **值不值**：失效键是 `HEAD × 版本指纹 × 视图种类`，每次提交全部失效；还要多一份存储、多一套"失效即重算"的正确性兜底。与进程地板（20–27 ms）比，省下的时间够不够被感知？
4. **形态**：存序列化的模型，还是存每个视图的字节？前者服务所有视图但体积大、解码要重新物化；后者省得最多但要×视图数，且只服务那一个命令。

## 判据

- **先定集合**：只对"要算的命令"设计；查表、写入、轻计算不进入讨论。
- **分开看三种读**：冷读（无缓存）、提交后首读（快照失效）、warm 读（同 HEAD 重复读）。预计算只可能改善其中一种。
- **不能有第二个真源**：任何预计算层失效时必须整体重算；与现路径输出逐字节一致，还必须是"删掉它也一样对"。
- **收益要超过噪声**：warm 已在地板附近的仓库，不算收益。

## collect（2026-10-30）：18 个入口里 7 个要算，6 个共用一次折叠

### 1. 命令面盘点

help 表 17 行加上 `help` 自身，共 18 个命令入口：

| 类别 | 命令 | 是否算 |
| --- | --- | --- |
| 读历史（重计算） | `path` `show` `status` `check` `list` `graph` `action log` | **7 个** |
| 问外部状态（轻计算，不折叠） | `worktree list`（每区 gone/dirty/unmerged）、`cache gc`（可达集） | 2 个 |
| 查表 / 静态 | `version` `help` `action list` `config path` | 4 个 |
| 纯删除 | `cache clear` | 1 个 |
| 写入（结果是动作本身） | `do` `commit` `worktree new` `worktree remove` | 4 个 |

7 个里前 6 个（`path` `show` `status` `check` `list` `graph`）的"算"是**同一个算**：把提交流折叠成 `model.Repo`，之后每个视图只是廉价投影。

| 命令 | 交付的结果 | 折叠之后还算什么 |
| --- | --- | --- |
| `status` | 全库概览 | 计数 + 按 domain 分组 + 排序 |
| `list` | 过滤后的问题 | status/tag/domain/action/search 过滤 + 日期排序 |
| `check` | 语义诊断 | 逐规则遍历全部 issue/action/关系 |
| `graph` | 关系图 | 按（无序对, slot）折叠边 + ascii/mermaid 布局；`--issue/--depth` 再 BFS |
| `path` | 一个问题的时间线 | 按 issue 排动作 + 关系折叠；`--stat` 再逐动作要 diffstat |
| `show` | 一个动作的完整变更 | 按序号/动作名定位（含歧义提示）+ 一次 `git show` |

`action log` 是刻意的例外：不折叠，按作者日期流式扫全部提交，`--limit` 提前停；它有独立的部分枚举路径。写入路径里唯一会读库的是 `do`/`commit` 的**起点动作**（`refuseDuplicateStart` 查重名），它走缓存里的一次折叠。

### 2. 折叠发生在哪

```text
internal/cli/load.go:155   loadRepo → loadCached（Scan 层 + 枚举快照）→ Builder → model.Repo
internal/engine            Summarize / GroupByDomain（status）、Filter（list）
                           FoldEdges / Graph / Mermaid（graph）、PathLines（path）、Check（check）
internal/cli/show.go       折叠后还要一次 git（ShowStat/Show）
```

所以今天缓存的边界正好停在"原始材料"：**枚举与记录存了，折叠与视图没存**。

### 3. 缓存现状：已经是预计算，但只到原始材料层

| 层 | 存的是什么 | 单位成本 | 100k 体积 | 失效键 |
| --- | --- | --- | --- | --- |
| 枚举快照 | `git log` 的提交列表 | ~20 B/提交 | ~2 MB | HEAD |
| 记录层 | 每条提交解析后的 trailer 字段 | ~130 B/提交（真实仓口径） | ~13 MB | HEAD / 合并时按可达集过滤 |
| 折叠模型（假设） | `model.Repo` 序列化 | **未测** | **未测** | HEAD + 版本 |
| 视图（假设） | 每个命令的输出字节 | 未测 | 未测 × 视图数 | HEAD + 版本 + 视图 |

冷读（无缓存）100k 约 **1,095 ms**；热读 0 个 git 进程。缓存命中与否不影响输出，这是现状的硬约束。

### 4. 成本分布（实测）

100k warm 端到端 **185 ms**（`cache-perf` 实测；README 另一次口径为 146 ms，两次绝对值差约 20%，比例仍可参考）：

| 组成 | ms | 说明 |
| --- | --- | --- |
| 进程地板 | ~20 | 启动 + 退出 |
| 进程内 | 89 | 见下 |
| 全新进程的堆增长 | ~76 | 由分配总量决定，`GOGC` 无差别 |

89 ms 的拆解：`cache.Scan` 26 ／ 枚举快照 1 ／ `gaps` 6 ／ **取记录 + 建模 55**。也就是说，就算把模型存盘，**今天可省的上界是那 55 ms**（还要付读回/物化一份模型的成本），`Scan` 与地板的钱照付。

真仓（455 提交）：warm `list` 25 ms，已在地板量级——视图计算在噪声内。

### 5. 三种读，预计算只可能改善一种

| 场景 | 455 提交 | 100k | 预计算能否改善 |
| --- | --- | --- | --- |
| 冷读（clear 后第一读） | ~0.1 s | ~1.1 s | 不能，本来就在建 |
| 提交后首读（快照失效） | 130 ms | ~440 ms | 不能，必须重走一遍才知道顺序 |
| warm（同 HEAD 重复读） | 25 ms | 146–185 ms | **只能改善这一种** |

kiln 自己的常态是"提交完立刻读一次"（agent 循环 / 校验脚本），也就是**首读**是主场景；同 HEAD 的重复读目前没有证据表明是高频路径。

### 6. 与 `commit-prepend` 的关系

这条最可能的真实形态不是"存视图"，而是**增量折叠**：HEAD 前进时把新动作并进已有模型，而不是重算整张图。那正是 `commit-prepend` 里 deferred 的 D1（读时按父链扩展），触发条件是 ≥30k 提交或 ≥10k 非线性历史。本 issue 不重复论证，只记下：**预计算视图省的是重复读，增量折叠省的是首读——后者才对得上当前工作流**。

## hypothesize（2026-10-30）：一条线性主干 + 两个二次项

### 结论先行

1. **主干是线性的，而且只占总时间的一半上下**：折叠（`loadCached`）≈ **1.0–1.4 ms / 1k 提交**，100k 提交时 104 ms；六个走折叠的命令在 100k 的 warm 读里，折叠占 **41–68%**（`list` 62%、`path <one>` 68%、`graph` 47%）。
2. **两个二次项都在视图层，不在折叠层**：
   - `path --all`／批量 `path` 的 `incidentEdges` 对每个 issue 扫全部边 ⇒ **O(I×E)**：100k 稀疏关系 4.8 s，3 关系/动作 16.6 s；同规模无关系时只有 212 ms。
   - `graph` 系列的 `FoldEdges` 在遇到 `unrelate` 时对每个 unrelate 扫整个状态表 ⇒ **O(U×E)**：100k、3 关系/动作 + unrelate 时 **61.7 s**，同样的边数去掉 unrelate 只有 387 ms（**160×**）。
3. 其余命令（`list` `status` `check` `path <one>` `show` `action log`）随提交数线性；`action log` 是编码受限（80k 行 ≈ 204 ms），不是折叠受限。
4. **"计算量更大"的排序会随关系密度翻转**：稀疏仓 `graph` 只比 `list` 多 30%；一旦关系密集，`graph` 从 221 ms 涨到 61.7 s，成为最贵的命令。`path --all` 则从一开始就是第二贵的，且随规模按平方走。
5. **对预计算缓存的含义**：把折叠结果存盘最多省那 104 ms，对 `path --all` 只占 2%、对 dense 的 `graph` 只占 0.2%。缓存改变常数，不改变形状；这两个二次项靠缓存无解，只能靠索引。

### 测量条件

- 合成仓：`git fast-import`，每 5 个提交 4 个动作，每 5 个动作 1 个 issue；关系密度分三档——无关系（E=0）、每动作 1 条 `caused-by`（E≈0.8×动作数）、每动作 3 条 + 每 4 个动作一条 `unrelate`。
- Windows 本机，warm 读（先跑一次填缓存），端到端为 3–5 次中位数；进程地板 27 ms（`kiln help`）。
- 进程内相位用临时探针（`go test`，直接调 `loadCached`、`engine.Summarize/Filter/Check/FoldEdges/Graph`、`incidentEdges`）测得，不在产品代码里。

### 1. 符号与每条命令的形状

C=提交数，A≈0.8C=动作数，I≈0.16C=issue 数，D=关系声明数，E=折叠后的边数，U=unrelate 条数。

| 命令 | 形状（warm） | 100k 实测 | 主导项 |
| --- | --- | --- | --- |
| `list` / `status` / `check` | O(C) 折叠 + O(I log I) | 168 / 170 / 179 ms | 折叠（58–62%） |
| `path <one>` | O(C) + O(I) | 153 ms | 折叠（68%） |
| `show` | O(C) + 一次 git | 218 ms | 折叠（48%）+ git（23%） |
| `graph` | O(C) + O(A log A + E) + 渲染 | 221 ms（稀疏）／61.7 s（dense+unrelate） | 关系密集时 FoldEdges（99.8%） |
| `graph --json` / `--mermaid` | 同上 + JSON/文本量 | 251 ms／220 ms | 同上 |
| `action log --jsonl` | O(C) 流式，不折叠 | 231 ms | 行编码（88%） |
| `path --all --json` | O(C) + **O(I×E)** + 输出 | 4.8 s（E≈80k）／16.6 s（E≈240k） | `incidentEdges`（93%） |

### 2. 主干：折叠线性增长，冷读才是大头

| 阶段 | 10k | 100k | 说明 |
| --- | --- | --- | --- |
| `git log`（冷读） | 129 ms | 730 ms | 每 10× 提交 ×5.7；消息越大越慢 |
| 解析 + 折叠（冷读） | 15 ms | 139 ms | 线性 |
| **`loadCached`（warm）** | **8.7–16 ms** | **104–133 ms** | 线性；关系密集时记录更大，+28% |

100k 的 warm 折叠 ≈ 104 ms（稀疏）≈ 0.001 ms/提交。真仓（455 提交）折叠 ≈ 2 ms，已经在地板里。

### 3. 100k 的耗时占比（稀疏关系，E≈80k）

| 命令 | 总 | 地板 | 折叠 | 自身计算 | 渲染/输出 |
| --- | --- | --- | --- | --- | --- |
| `list` | 168 | 27（16%） | **104（62%）** | 1.5 | 35 |
| `status` | 170 | 27 | **104（61%）** | 4.5 | 34 |
| `check` | 179 | 27 | **104（58%）** | 11 | 37 |
| `path <one>` | 153 | 27 | **104（68%）** | 2 | 20 |
| `graph` | 221 | 27 | **104（47%）** | 27（FoldEdges） | 63 |
| `graph --json` | 251 | 27 | **104（41%）** | 27 | 93 |
| `show` | 218 | 27 | **104（48%）** | 50（git show） | 37 |
| `action log --jsonl` | 231 | 27 | —（不折叠） | 204（80k 行编码） | — |
| `path --all --json` | 4824 | 27 | 104（2%） | **4495（93%）** | 198 |

两条读数：**折叠是"每条命令都要付的固定税"**，在 100k 前它是主要成本；**一旦进入 `path --all` 或关系密集的 `graph`，税的占比被压到 2% 以下，二次项接管**。

### 4. 二次项 A：`path --all` 的 incidentEdges

`pathBatch` 先折一次边，然后对每个 issue 调 `incidentEdges`，而它遍历整张边表。实测（100k，I=16000）：

| E | `path --all --json` 端到端 | 其中 incidentEdges |
| --- | --- | --- |
| 0 | 212 ms | 0 |
| ≈80k（1 关系/动作） | 4 824 ms | 4 495 ms |
| ≈240k（3 关系/动作） | 16 577 ms | 14 720 ms |

E 从 80k 到 240k（3×），incident 从 4.5 s 到 14.7 s（3.3×）⇒ 对 E 线性；I 再乘上去就是 I×E，约 **3.5 ns 一次（issue, edge）比较**。10k→100k 的形状：57.6 ms → 4 495 ms（78×，规模 10×）。

若把边按 issue 建一次索引（O(E)，240k 条约 10 ms），这项从"每个 issue 扫全表"变成"只扫自己的度"。

### 5. 二次项 B：`FoldEdges` 的 unrelate

`FoldEdges` 对每条 `unrelate` 执行 `for k := range state`，把匹配的 pair 删掉。于是 U 条 unrelate 各自扫一遍当前状态表：

| 仓（10k，3 关系/动作） | 边数 | FoldEdges | `graph` 端到端 |
| --- | --- | --- | --- |
| 无 unrelate | 23 628 | **5.25 ms** | 58.9 ms |
| 每 4 个动作 1 条 unrelate | 23 214 | **195 ms** | 264 ms |

100k 时同样的对照放大成：无 unrelate `graph` **387 ms**，有 unrelate **61 698 ms**（`graph --json` 51 271 ms）——**160×**，且 FoldEdges 占 99.8%。unrelate 数量与状态表都随 C 增长，合起来是 Θ(C²)。

这个形状在本仓几乎不会出现（449 个动作里只有 1 条 `unrelate`、84 条关系），所以今天 `graph` 31 ms；但它是一条真实的悬崖。

### 6. 外推到 1M

线性项 ×10、二次项 ×100：

| 命令 | 100k 实测 | 1M 外推 |
| --- | --- | --- |
| `list` / `status` / `check` | 168 / 170 / 179 ms | ≈ 1.4 / 1.5 / 1.6 s |
| `path <one>` / `show` | 153 / 218 ms | ≈ 1.4 / 1.9 s |
| `action log --jsonl` | 231 ms | ≈ 2 s |
| `graph`（稀疏，E≈0.8×动作数） | 221 ms | ≈ 2 s |
| `path --all`（E≈0） | 212 ms | ≈ 2 s |
| `path --all`（E≈80k） | 4.8 s | ≈ 8 min |
| `path --all`（E≈240k） | 16.6 s | ≈ 28 min |
| `graph`（带 unrelate） | 61.7 s | ≈ 1.7 h |

冷读的 `git log` 也会按 ×10 走（730 ms → ≈ 7 s），但它每次 HEAD 移动只付一次，量级已经被 warm 读的二次项盖过。

### 7. 对"预计算缓存"的读数

- 存折叠模型：100k 最多省 104 ms（`list` 的 62%），但对 `path --all` 是 2%、对 dense 的 `graph` 是 0.2%；1M 时折叠 ≈ 1 s，而那两个二次项已是分钟到小时级。**缓存可以把线性主干抹掉，抹不掉形状。**
- 存视图：`path --all` 的输出是 80k 动作 + 240k 边，落盘与读回都不比现算便宜；`graph` 的 61.7 s 是算出来的，存下来只对"同一个 HEAD 再读一次"有效，而这份输出每个 HEAD 只读一次。
- 真正值得"预计算"的是**每条 issue 的邻接边索引**——但它 O(E) 一次构建只要 ~10 ms（240k 边），每次读重建即可，不需要落盘，也不需要失效逻辑。

所以本 issue 的倾向（留给 test 验证）：**不做模型/视图缓存；两个二次项若真被大仓触发，先改视图算法**。

### 8. 可证伪的预测（test 用）

| # | 预测 | 判据 |
| --- | --- | --- |
| P1 | `incidentEdges` 改成按 issue 建索引后，100k 稀疏 `path --all` 从 4.8 s 降到 ≤ 300 ms | 端到端 |
| P2 | `FoldEdges` 把 unrelate 改成按 pair 直接删后，100k dense `graph` 从 61.7 s 降到 ≤ 700 ms（对齐无 unrelate 的 387 ms 量级） | 端到端 |
| P3 | 折叠保持线性：1M 合成仓 warm 折叠 1.0–1.5 s，`list` ≤ 2 s | 实测斜率 |
| P4 | 真仓（449 提交、84 关系、1 unrelate）三个命令都在 50 ms 内 | 实测（现为 31–37 ms） |
| P5 | 存折叠模型对 `path --all` 的改善 < 3%（因为折叠只占 2%） | 对比 |

## 非目标

- 不做视图级（`status`/`list` 输出字节）缓存，除非出现同 HEAD 重复读的证据；
- 不改记录层/枚举快照格式；
- 不引入第二个真源：任何预计算层必须可删、失效即重算；
- 不把 `action log` 的流式路径改成折叠（它的大小无关内存是设计目标）。
