# issue: cache-precompute — 预计算缓存：还该预计算什么、能省多少、值不值

- **domain**：design
- **关联**：relates-to `commit-cache`（记录层缓存本身）；relates-to `cache-perf`（warm 读的钱花在哪）；relates-to `commit-prepend`（HEAD 前移后的首读，D1 是这条最可能的落地形态）

## 背景

kiln 的读路径已经预计算了两层**原始材料**：枚举快照是 `git log --format=%H` 的答案（按 HEAD 存），记录层是每条提交 trailer 解析后的字段。两层合起来让热读**不启动 git**。

没有预计算的是再往上一层：折叠出来的 `model.Repo`，以及各命令的视图（计数、过滤、关系边、排版）。这些今天每次读都重做一遍。这条 issue 要问的是：**要不要把它们也存盘？**

先决问题是"哪些命令真的需要算"——不为不需要算的命令存答案。

## 要回答的问题

1. **预计算到哪一层**：记录（已有）／折叠模型 `model.Repo`／视图（`status` 的行、`list` 的过滤结果、`graph` 的边与布局）。三层的失效面与复用范围差很多。
2. **能省多少**：收益只出现在**同一 HEAD 的重复读**上；提交后的第一次读仍要全算，一分不省。需要一份按层拆开的成本表，而不是端到端一个数。
3. **值不值**：失效键是 `HEAD × 版本指纹 × 视图种类`，每次提交全部失效；还要多一份存储、多一套"失效即重算"的正确性兜底。与进程地板（20–27 ms）比，省下的时间够不够被感知？
4. **形态**：存序列化的模型，还是存每个视图的字节？前者服务所有视图但体积大、解码要重新物化；后者省得最多但要×视图数，且只服务那一个命令。

## 判据

- **先定集合**：只对"要算的命令"设计；查表、写入、轻计算不进入讨论。
- **分开看三种读**：冷读（无缓存）、提交后首读（快照失效）、warm 读（同 HEAD 重复读）。预计算只可能改善其中一种。
- **不能有第二个真源**：任何预计算层失效时必须整体重算；与现路径输出逐字节一致，还必须是"删掉它也一样对"。
- **收益要超过噪声**：warm 已在地板附近的仓库，不算收益。

## 非目标

- 不做视图级（`status`/`list` 输出字节）缓存，除非出现同 HEAD 重复读的证据；
- 不改记录层/枚举快照格式；
- 不引入第二个真源：任何预计算层必须可删、失效即重算；
- 不把 `action log` 的流式路径改成折叠（它的大小无关内存是设计目标）。
