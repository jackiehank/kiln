# issue: common-origin — 两个 issue「同源」时该怎么表达

- **状态**：ask（进行中）
- **domain**：design
- **关联**：derived-from `relation-vocabulary`

## 背景

`relation-vocabulary` 第四轮测试里，4/4 个 agent 在同一道题上翻车：

> #8：两个 issue 由**同一次线上故障**的记录引出，但两条各自独立、无先后

它们的答案都是 `derived-from`（正解 `relates-to`）。表面原因是我题面里写了"引出"，但**背后是个真实缺口**：

**当两个 issue 有共同来源、而那个来源不是一个 issue 时，没有任何键能表达"同源"。** agent 只好硬编一条兄弟之间的 `derived-from`——语义上是错的（它俩之间并没有引发关系），但它表达了 agent "想说的那件事"。

## 要回答的问题

1. **这算不算一个关系？** 两个 issue 共用同一个非 issue 来源（一次故障、一篇论文、一场会议、一份需求文档），它们之间用 `relates-to` 就够，还是值得一个**独立的关系类型**？
2. **如果值得，方向是什么？** "同源"是**对称**的（两个都源自同一处），更像 `relates-to` 那样的**无向**关系，而非有向对。
3. **来源本身要不要能被寻址？** 现有键只能指向另一条 issue。若要表达"源自一次故障"，来源需要有个标识（如 `source: incident-2026-10-14`）——那就不是"issue 之间的关系"，而是"issue 与非 issue 来源的关系"，属于另一类建模。
4. **还是一律用 `relates-to` 兜底**，只在文档里写明"共同来源之间用 `relates-to`"？——最小方案，但它把信息抹平了：读的人分不出这俩是"同源"还是"碰巧相关"。

## 候选

| 方案 | 形态 | 代价 |
| --- | --- | --- |
| **A** 不加，`relates-to` 兜底 | 现有 5 键不动 | 信息被抹平 |
| **B** 新增无向键 `same-origin` / `co-derived` | 对称、一个名字 | 词表 +1；与 `relates-to` 的边界要靠释义说清 |
| **C** 引入"外部来源"引用（如 `source: <非 issue 标识>`） | 能表达"源自故障/论文" | 打破"键只指向 issue"的现有约定，改动最大 |

## 非目标

- 不改现有 5 个键；只讨论是否**新增**。
- 不改代码。

## 备注

这条缺口是 `relation-vocabulary` 第四轮测试**顺带发现**的——正好说明"拿 agent 当代理用户"能挖出设计者自己没想到的问题。
