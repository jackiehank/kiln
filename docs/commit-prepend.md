# 提交时增量前插（B）：何时需要、能省多少、值不值得

## 背景

perf-profile 的结论把「B（提交时增量前插）」列为 deferred：HEAD 每移动一次，
下一次读就要整条重走一次 `git log` 出顺序（每序一次；线性历史两序共享快照后是一次）。
kiln 自己的工作流恰好是 commit 完立刻 check / show / list——每一次提交后都付这笔走链。

B 的形态：`kiln commit` 产生新提交 N（父 = 旧 HEAD H），若缓存里已有 H 的枚举快照，
就把 N 前插到快照头部、写出以 N 为键的新快照；没有 H 的快照就退回整条走链。

## 问题

1. **何时需要**：走链在什么仓库规模、什么工作流下才成为可感知成本？
   参照：进程地板 27 ms、一次 git 子进程约 50 ms——省下来的走链要和这两者比，而不是和零比。
2. **能省多少**：每次 HEAD 移动省掉一次整链走链（每序），换一次前插（写快照 + 层）。
   真仓（450）/ 1k / 10k / 100k 上各是多少绝对量与相对量？前插自身的成本
   （快照写入、层数增长、60 层 merge 频率）又占多少？
3. **值不值得**：实现、维护、正确性成本 vs 收益。要给出明确的做 / 不做建议与触发条件，
   以及如果做，是「commit 时写」还是「读时按父链扩展」。

## 判据

- 用实测回答「何时」「省多少」；不靠估算。
- 「值不值得」必须有立场：做 / 不做 / 有条件做，写清条件和放弃的理由。
- 先验证前提：新提交（单父、父 = 旧 HEAD）在两种顺序里都必然排在首位——若不成立，B 直接出局。

## collect（2026-10-30）：能拿掉的只有 walk

### 前提成立：单父新提交在两种顺序里都排第一

证明：读到的 tip 从 H 前进到 N，N 只有一个父 H。`reachable(N) = {N} ∪ reachable(H)`，
其余提交全是 H 的祖先；任何「子先于父」的顺序都必须把 N 排在 H 之前，也就排在所有提交之前。
git 的默认序和 `--author-date-order` 都是这种遍历（父提交在子提交被弹出后才入队），所以 N 必为第一。

实测（小仓：merge 历史，新提交的作者/提交者日期设成 2019，老于全部旧提交）：默认序与
作者日序的第一条都是 N；在它上面再叠一个更老的 N2，N2 仍是第一。**日期不必校验**，
前插就是按 oid 前插；要校验的只有「父 == 快照的 HEAD」。

### 测量方法

- `nulrun` 启动器（子进程输出到 NUL，打印墙钟毫秒）；每个仓库先清空 `.git/kiln`，之后每轮
  `git commit --allow-empty` 移动一次 HEAD；表中为首读/中位数，±10–25% 噪声。
- 「提交后首读」= 快照失效后的第一次读；「warm」= 紧接着的第二次读。
- 「前插后」= 用探针测试手工构造「父快照 + 新 tip 前插」的文件（不改产品代码），再测第一次读；
  此时新提交的记录还没进层，所以仍要付一次 cat-file。

### 结果

提交后首读（默认序）：

| 仓库 | 提交数 | 提交后 list | warm list | 差值 = walk + cat-file + 写回 |
| --- | --- | --- | --- | --- |
| 真仓 | 455 | 130 | 25 | 105 |
| 1k | 1009 | 131 | 25 | 106 |
| 10k | 10004 | 157 | 35 | 122 |
| 10k + merge | 10005 | 159 | 35 | 124 |
| 100k | 100016 | 437 | 149 | 288 |
| 100k + merge | 100029 | 441 | 146 | 295 |

前插后的首读（同一次提交、此前没有任何读）：

| 仓库 | list 首读 | 省 | action log 首读 | 省 |
| --- | --- | --- | --- | --- |
| 真仓 | 76 | 54 | 未测 | |
| 1k | 76 | 55 | 未测 | |
| 10k | 94 | 63 | 未测 | |
| 10k + merge | 85 | 74 | 未测 | |
| 100k | 203 | 234 | 836 → 220 | 616 |
| 100k + merge | 210 | 231 | 783 → 217 | 566 |

- 前插后首读 ≈ warm + 一次 cat-file + 写回：`76 = 25 + 48 + 3`、`203 = 149 + 48 + 3`。
  **cat-file 是读新提交的记录，任何读都要付；前插拿不掉它。**
- 100k 的「log 首读」今天要 836 ms：walk（裸 `git log --author-date-order` 481）+
  kiln 流式解析与建 oid 列表的差（约 140）+ cat-file 48 + warm 165。
- 前插后的快照与整链重走**逐字节一致**（探针在六个仓库、两种顺序上比对了 cached / uncached 输出）。

### 前插自身的成本

- 快照 2 MB @100k：写 3.1 ms、读 1.6 ms（Go 探针，本机缓存目录）；455 提交时 <1 ms。
  前插动作本身可以忽略；真正的成本在实现与维护。

### 事实与推论

- walk 的规模曲线很平：默认序 51 / 54 / 57 / 170（455 / 1k / 10k / 100k），
  作者日序 60 / 53 / 90（10k 非线性）/ 481（100k）。20k 提交以内基本是 git 启动的
  ~50 ms 地板，10k 只比 1k 多 3 ms；100k 才开始线性涨。
- 真仓 455 提交 / 16 天 ≈ 28 提交/天；按此线性外推，10k ≈ 1 年、100k ≈ 10 年（外推，不当承诺）。
- 提交后首读能省 54–234 ms（默认序）；100k 的「作者日序先读」能省 566–616 ms。
  省不掉的 76–220 ms 是 warm + 一次 cat-file。
- 单次提交循环：真仓 commit 289 + check 130 = 419 → 365（−13%）；
  100k 275 + 430 = 705 → 478（−32%）；100k 上「提交后先读 action log」1058 → 492（−54%）。
