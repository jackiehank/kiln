# 提交时增量前插（B）：何时需要、能省多少、值不值得

## 背景

perf-profile 的结论把「B（提交时增量前插）」列为 deferred：HEAD 每移动一次，
下一次读就要整条重走一次 `git log` 出顺序（每序一次；线性历史两序共享快照后是一次）。
kiln 自己的工作流恰好是 commit 完立刻 check / show / list——每一次提交后都付这笔走链。

B 的形态：`kiln commit` 产生新提交 N（父 = 旧 HEAD H），若缓存里已有 H 的枚举快照，
就把 N 前插到快照头部、写出以 N 为键的新快照；没有 H 的快照就退回整条走链。

## 问题

1. **何时需要**：走链在什么仓库规模、什么工作流下才成为可感知成本？
   参照：进程地板 27 ms、一次 git 子进程约 50 ms——省下来的走链要和这两者比，而不是和零比。
2. **能省多少**：每次 HEAD 移动省掉一次整链走链（每序），换一次前插（写快照 + 层）。
   真仓（450）/ 1k / 10k / 100k 上各是多少绝对量与相对量？前插自身的成本
   （快照写入、层数增长、60 层 merge 频率）又占多少？
3. **值不值得**：实现、维护、正确性成本 vs 收益。要给出明确的做 / 不做建议与触发条件，
   以及如果做，是「commit 时写」还是「读时按父链扩展」。

## 判据

- 用实测回答「何时」「省多少」；不靠估算。
- 「值不值得」必须有立场：做 / 不做 / 有条件做，写清条件和放弃的理由。
- 先验证前提：新提交（单父、父 = 旧 HEAD）在两种顺序里都必然排在首位——若不成立，B 直接出局。
