# 提交时增量前插（B）：何时需要、能省多少、值不值得

## 背景

perf-profile 的结论把「B（提交时增量前插）」列为 deferred：HEAD 每移动一次，
下一次读就要整条重走一次 `git log` 出顺序（每序一次；线性历史两序共享快照后是一次）。
kiln 自己的工作流恰好是 commit 完立刻 check / show / list——每一次提交后都付这笔走链。

B 的形态：`kiln commit` 产生新提交 N（父 = 旧 HEAD H），若缓存里已有 H 的枚举快照，
就把 N 前插到快照头部、写出以 N 为键的新快照；没有 H 的快照就退回整条走链。

## 问题

1. **何时需要**：走链在什么仓库规模、什么工作流下才成为可感知成本？
   参照：进程地板 27 ms、一次 git 子进程约 50 ms——省下来的走链要和这两者比，而不是和零比。
2. **能省多少**：每次 HEAD 移动省掉一次整链走链（每序），换一次前插（写快照 + 层）。
   真仓（450）/ 1k / 10k / 100k 上各是多少绝对量与相对量？前插自身的成本
   （快照写入、层数增长、60 层 merge 频率）又占多少？
3. **值不值得**：实现、维护、正确性成本 vs 收益。要给出明确的做 / 不做建议与触发条件，
   以及如果做，是「commit 时写」还是「读时按父链扩展」。

## 判据

- 用实测回答「何时」「省多少」；不靠估算。
- 「值不值得」必须有立场：做 / 不做 / 有条件做，写清条件和放弃的理由。
- 先验证前提：新提交（单父、父 = 旧 HEAD）在两种顺序里都必然排在首位——若不成立，B 直接出局。

## collect（2026-10-30）：能拿掉的只有 walk

### 前提成立：单父新提交在两种顺序里都排第一

证明：读到的 tip 从 H 前进到 N，N 只有一个父 H。`reachable(N) = {N} ∪ reachable(H)`，
其余提交全是 H 的祖先；任何「子先于父」的顺序都必须把 N 排在 H 之前，也就排在所有提交之前。
git 的默认序和 `--author-date-order` 都是这种遍历（父提交在子提交被弹出后才入队），所以 N 必为第一。

实测（小仓：merge 历史，新提交的作者/提交者日期设成 2019，老于全部旧提交）：默认序与
作者日序的第一条都是 N；在它上面再叠一个更老的 N2，N2 仍是第一。**日期不必校验**，
前插就是按 oid 前插；要校验的只有「父 == 快照的 HEAD」。

### 测量方法

- `nulrun` 启动器（子进程输出到 NUL，打印墙钟毫秒）；每个仓库先清空 `.git/kiln`，之后每轮
  `git commit --allow-empty` 移动一次 HEAD；表中为首读/中位数，±10–25% 噪声。
- 「提交后首读」= 快照失效后的第一次读；「warm」= 紧接着的第二次读。
- 「前插后」= 用探针测试手工构造「父快照 + 新 tip 前插」的文件（不改产品代码），再测第一次读；
  此时新提交的记录还没进层，所以仍要付一次 cat-file。

### 结果

提交后首读（默认序）：

| 仓库 | 提交数 | 提交后 list | warm list | 差值 = walk + cat-file + 写回 |
| --- | --- | --- | --- | --- |
| 真仓 | 455 | 130 | 25 | 105 |
| 1k | 1009 | 131 | 25 | 106 |
| 10k | 10004 | 157 | 35 | 122 |
| 10k + merge | 10005 | 159 | 35 | 124 |
| 100k | 100016 | 437 | 149 | 288 |
| 100k + merge | 100029 | 441 | 146 | 295 |

前插后的首读（同一次提交、此前没有任何读）：

| 仓库 | list 首读 | 省 | action log 首读 | 省 |
| --- | --- | --- | --- | --- |
| 真仓 | 76 | 54 | 未测 | |
| 1k | 76 | 55 | 未测 | |
| 10k | 94 | 63 | 未测 | |
| 10k + merge | 85 | 74 | 未测 | |
| 100k | 203 | 234 | 836 → 220 | 616 |
| 100k + merge | 210 | 231 | 783 → 217 | 566 |

- 前插后首读 ≈ warm + 一次 cat-file + 写回：`76 = 25 + 48 + 3`、`203 = 149 + 48 + 3`。
  **cat-file 是读新提交的记录，任何读都要付；前插拿不掉它。**
- 100k 的「log 首读」今天要 836 ms：walk（裸 `git log --author-date-order` 481）+
  kiln 流式解析与建 oid 列表的差（约 140）+ cat-file 48 + warm 165。
- 前插后的快照与整链重走**逐字节一致**（探针在六个仓库、两种顺序上比对了 cached / uncached 输出）。

### 前插自身的成本

- 快照 2 MB @100k：写 3.1 ms、读 1.6 ms（Go 探针，本机缓存目录）；455 提交时 <1 ms。
  前插动作本身可以忽略；真正的成本在实现与维护。

### 事实与推论

- walk 的规模曲线很平：默认序 51 / 54 / 57 / 170（455 / 1k / 10k / 100k），
  作者日序 60 / 53 / 90（10k 非线性）/ 481（100k）。20k 提交以内基本是 git 启动的
  ~50 ms 地板，10k 只比 1k 多 3 ms；100k 才开始线性涨。
- 真仓 455 提交 / 16 天 ≈ 28 提交/天；按此线性外推，10k ≈ 1 年、100k ≈ 10 年（外推，不当承诺）。
- 提交后首读能省 54–234 ms（默认序）；100k 的「作者日序先读」能省 566–616 ms。
  省不掉的 76–220 ms 是 warm + 一次 cat-file。
- 单次提交循环：真仓 commit 289 + check 130 = 419 → 365（−13%）；
  100k 275 + 430 = 705 → 478（−32%）；100k 上「提交后先读 action log」1058 → 492（−54%）。

## hypothesize（2026-10-30）：三种形态，读时按父链扩展最优

### 形态与成本落点

| 形态 | 谁付前插 | 覆盖 | 无读的连续提交 | 读时还要 cat-file | 实现量 |
| --- | --- | --- | --- | --- | --- |
| D1 读时按父链扩展 | 读 | kiln 提交 + 任意单父 git 提交 | 不付 | 是（本来就要付） | ~120 行 |
| D2 commit 写 hint + 读时扩展 | commit 写 ~40 B | 仅 kiln 提交 | ≈0 | 是 | ~90 行 |
| D3 commit 时整份前插 | commit 读父快照 + 写回（100k 约 5 ms） | 仅 kiln 提交 | 每次付 5 ms（1000 次 = 5 s） | 是 | ~70 行 |

排序是 D1 > D2 > D3，理由：

- 唯一能拿掉的是 walk；cat-file 三种形态都要付。想连它一起省，只能在 commit 时把新提交的
  记录也写了——但那只是把 48 ms 从读搬到 commit：提交后必读时打平，连续提交不读时净亏。
- D3 把枚举写回从读搬到 commit：有读时打平（读少 3 ms、commit 多 5 ms），无读时净亏；
  而且它只认 kiln 自己的提交，`git commit` / rebase / pull 后的新 HEAD 一样退回走链。
- D2 的 hint 只回答「父是谁」；D1 读记录时 cat-file 的输出里本来就有 `parent` 行，
  解析它不花进程。D2 没有额外收益，只多一个文件和一条写路径。

### D1 的实现骨架

- `vcs.RawCommit` 加 `Parents / ParentsKnown`，git 的 cat-file 解析顺带填（零进程）。
- 枚举 miss 时先 `Commits([HEAD])`——这次调用读本来就要付；单父且父快照存在，就把
  HEAD 前插到父快照（同 kind）并写回；任一条件不满足就退回 walk。
- **关键**：这次取到的记录要喂给随后 `loadCached` / `actionLogCached` 的 fetch，否则同一条
  记录取两次（+48 ms），小仓净亏。枚举因此要能带一个 seed 回来。
- 边界：父快照已被 prune（窗口 4 份）或多提交连发只覆盖最后一跳 → 退回 walk；
  inv（replace refs / shallow / grafts）变了 → key 不匹配 → 退回。
- 两个调用点：`loadCached`（默认序）和 `actionLogCached`（作者日序）；`--limit` 不写快照，不接。
- 测试：前插后的输出与 uncached 逐字节一致（collect 的探针做法可复用）；覆盖 merge 仓、
  更老的作者日期、共享 kind、父快照缺失、两次提交无读。

实现量约 120 行 + 3–4 个测试；新增一条不变式：**单父且父快照在 ⇒ 前插等于重走**。

### 何时需要

| 规模 | 提交后首读（默认序）省 | 提交循环 | 作者日序首读省（非线性） |
| --- | --- | --- | --- |
| 455 | 54 | 419 → 365（−13%） | 未测（walk 仅 ~60，与默认序同量级） |
| 1k | 55 | −13% | 未测 |
| 10k | 63 | 431 → 369（−14%） | ~50（10k+merge 142 → ~90） |
| 100k | 231–234 | 705 → 478（−32%） | 566–616 |

- 无感区：<10k 提交，省 ≤63 ms、占循环 ≤14%，比一次 `git commit`（~150–200 ms）还小；
  当前真仓 455 提交就在这一区。
- 可感知区：≥30k 提交（默认序省 ~100 ms 起），或 ≥10k 且非线性（作者日序首读省 ~90–100 ms）。
- 明显收益区：100k 级，省 230–620 ms/次。
- 频率（真仓实测 28 提交/天，且提交后必读）：455 提交时每天省 1.5 s；100k 每天省 6.6 s
  （默认序）到 17 s（作者日序）。

### 判断

- 当前收益 ≈ 0（无感），实现与维护成本是真的：120 行 + 测试 + 一条新不变式；顺序错了会
  静默改变输出（回退方向是安全的，但覆盖不到"不报错但顺序不对"）。
- 因此立场是「不做，留触发条件」：仓库到 ≥30k 提交（或 ≥10k 非线性）且提交后必读时再做，
  且做 D1，不做 D3；D2 没有单独存在的理由。
- 如果只想要便宜的一半：把「读记录」的 cat-file 输出里的 parent 解析出来（`RawCommit` 加两个
  字段）本身无成本，也是 D1 的前置；但只有接上枚举扩展才产生收益，单独做没有意义。

## conclude（2026-10-30）：现在不值得做

- **能省多少**：只省 walk。提交后首读从 130 → 76（455 提交）、157 → 94（10k）、441 → 210
  （100k）；100k 的「作者日序先读」从 783–836 → 217–220。省不掉的 76–220 ms 是 warm 读数
  + 一次 cat-file（读新提交的记录），三种形态都拿不掉。
- **何时需要**：walk 在 20k 提交以内基本是 git 启动的 ~50 ms 地板；默认序的收益在 30k 提交
  才到 ~100 ms，100k 才到 230 ms。当前真仓 455 提交 / 16 天（~28 提交/天），提交后首读省
  54 ms，占 commit→check 循环 13%——低于一次 git commit 的噪声，人和 agent 都感知不到；
  按此速度 10k 约一年、100k 约十年。
- **值不值得**：现在不做。收益在无感区，而成本是 ~120 行实现、3–4 个测试和一条新的缓存
  不变式（「单父且父快照在 ⇒ 前插等于重走」）；这条不变式一旦错，输出会静默变序——虽然
  回退方向安全，但测试成本不低。等触发条件出现再做，是更划算的顺序。
- **若做，做哪个**：D1（读时按父链扩展）——成本落在读上、覆盖 kiln 与 `git commit`、
  失败零成本；D3（提交时整份前插）不做：它把同样的写回搬到 commit，对「连续提交不读」是
  净损失，且不覆盖 git 提交；D2（commit 写 hint）没有额外收益，只多一个文件。
- **触发条件**：仓库 ≥30k 提交（默认序省 ≥100 ms）或 ≥10k 且非线性（作者日序首读省
  ≥90 ms），并且提交后必读（agent 循环 / 校验脚本）；或者出现「大仓 + 每天上千次
  提交后立刻校验」的场景。到那时按 D1 落地，并复用 collect 的探针做逐字节回归。

以上与 perf-profile 的 deferred 一致：B 仍是 deferred，只是现在把触发条件与形态定清楚了。
