# issue: relation-rendering — `graph` / `status` 不渲染 `blocks` / `supersedes`，与 `path` 不一致

- **domain**：cli
- **关联**：relates-to `cli-necessity`

## 背景

同一个 `blocks:` 关系，**三个视图看到的程度不一样**：

- `kiln path <issue>`：**显示**——关系摘要里含 derived-from / spawns / relates-to / **blocks** / supersedes（`relationSummary`）。
- `kiln graph`：**不显示**——`relationLines` 只画 spawns / relates-to / derived-from（[engine.go](file:///c:/Users/jacki/kiln/internal/engine/engine.go#L277-L289)）。
- `kiln status`：**不显示**——status 只管 domain 分组与嵌套，不呈现依赖边。

于是：给 `evidence-fluidity` 声明 `blocks: cli-necessity` 后，`path` 能看到这条阻塞（`关系: blocks cli-necessity`），但 `graph` / `status` 里**看不到**——同一个事实，换个视图就消失了。

## 要回答的问题

1. **每个视图该渲染哪些关系？** 定一张"**视图 × 关系**"矩阵：`path`（过程视图）显示哪些、`graph`（关系视图）显示哪些、`status`（目录视图）显示哪些。现状**没有定义**，各视图各写各的。
2. **`graph` 该补 `blocks` / `supersedes` 吗？** 二者都是有向关系，画成箭头最自然；`part-of` 未来落地后同理。
3. **方向怎么画？** `blocks` 是"阻塞者 → 被阻塞者"；`graph` 现有条目是"我 spawns / related / derived-from 谁"的正向写法。反向边（"谁 `blocks` 我"）要不要一并生成？
4. **`status` 要不要显示关系？** 还是坚持"status 只管 domain 目录"、把关系留给 `graph`？（现状偏后者。）
5. **`check` 要不要顺带校验 `blocks` 一致性**（阻塞者未完成、被阻塞者却已推进 → 告警）？——mvp-plan §10 已有"`blocks` 状态一致性"条目，与本 issue 相邻但**不同**（那是校验，这是渲染）。

## 候选

| 方案 | 形态 | 代价 |
| --- | --- | --- |
| **A** 只补 `graph` | 给 `relationLines` 加 `blocks` / `supersedes` | 最小；`status` 仍不显示关系 |
| **B** 统一渲染 | 先定"视图 × 关系"矩阵，各视图按矩阵补齐 | 要先做设计决定；改动面较大 |
| **C** 全塞进 `graph` | 所有关系都在 `graph` 出现 | `graph` 会变臃肿；方向 / 反向边要处理 |

## 非目标

- 不改关系**词表**（那是 `relation-vocabulary`）。
- 不改 `path` 的关系摘要（它已显示）。

## 备注

由 `cli-necessity` 会话中发现：为 `evidence-fluidity` 声明 `blocks: cli-necessity` 后，`path` 能看到、`graph` / `status` 看不到。用户要求先**记录**、之后再解决。

## hypothesize：视角化渲染——X 为主语，动词按 X 的角色选正名 / 反名

> 用户推演（2026-10-18）：`relation-vocabulary` 刚定下「声明方是主语」；于是有向关系同样有主动/被动两面（`blocks` / `blocked-by`）。**渲染时，看与 X 有关的 issue，应该都能读成「X blocks Y」「X blocked-by Z」——主语始终是 X。**

### 0. 把「主语」拆成两个视角

| 视角 | 谁是主语 | 用在哪 |
| --- | --- | --- |
| **写侧** | 声明方（写这条 trailer 的 issue） | 决定**写哪个名**（按声明方在语义里扮的角色） |
| **读侧** | 被看的 issue X | 决定**渲染哪个名**（按 X 在语义里扮的角色） |

不变式统一为一句：**当前视角的 issue 就是主语**。「声明方是主语」只是写侧的特例。

### 1. 渲染规则（形式化）

每条边存成 `(声明方 D, 目标 T, 名字 n)`，`n` 是「D 相对 T 的角色」。名字两两成对（`blocks` ↔ `blocked-by`），`inverse(n)` 由配置机械给出。从视角 `X ∈ {D, T}` 渲染：

- `X == D` → `X <n> T`
- `X == T` → `X <inverse(n)> D`
- 对称关系（`relates-to`）→ 两侧同名，无正反

### 2. 例子：`blocks` / `blocked-by`

> 存：新建的 A 声明 `blocked-by: B`（A 是等待方）。
> - 看 A 的关系 → `A blocked-by B`
> - 看 B 的关系 → `B blocks A`

同一条边，两页两句，**主语都是当前页的 issue**——与 Jira / GitHub 的关系区的读法一致。两侧名都不需额外存储，一侧声明、另一侧渲染反名即可。

### 3. 由此确认：9 个名不是可选的，它们是**渲染词对**

| 语义 | 正名（声明方=等待/子/被引发/新） | 反名（声明方=阻塞/母/来源/旧） |
| --- | --- | --- |
| 引发 | `derived-from` | `spawns` |
| 分解 | `part-of` | `has-part` |
| 依赖 | `blocks` / `blocked-by` | （另一侧） |
| 取代 | `supersedes` | `superseded-by` |
| 关联 | `relates-to`（对称） | — |

配置里每个关系声明一个 `inverse`（或配对 id），引擎就能在**任意视角**渲染出「X 为主语」的句子。这也直接回答了本 issue 的问题 **3（反向边要不要生成）**：**要**，但不是存第二条边，而是渲染时换名。

### 4. 两种渲染形态，别混

| 形态 | 用在哪 | 方向 / 主语 |
| --- | --- | --- |
| **箭头** | `graph` / 全局图 | **规范化 = 声明源为箭尾**：`声明方 ──<声明的名>──▶ 目标`；单一侧声明 ⇒ 唯一形态 |
| **句子** | `path X` / X 的关系区 | **视角化**：主语 = X，动词按 X 的角色选正/反名 |

两者同源（同一个 `(对, 槽, 名字)`），只是投影不同；箭头管「图长什么样」，句子管「从 X 看，它跟谁什么关系」。→ 上一轮在 `relation-vocabulary` 写的「写 9 / 渲 1」应修正为「**写 9 / 句渲 2（正反） / 图渲 1（箭头）**」。

### 5. 回答本 issue 的「视图 × 关系」矩阵

| 视图 | 渲染形态 | 应包含的关系 | 备注 |
| --- | --- | --- | --- |
| `path X` | 句子（主语=X） | 全部 5 族，**含反向边**（X 为目标那些） | 现状缺反向边 |
| `graph` | 箭头（规范化） | 全部有向关系（含现在缺的 `blocks` / `supersedes`） | 问题 2 的答案 |
| `status` | 不渲染关系 | — | 维持现状（问题 4） |

### 6. 实现强制项（与 `relation-revision` 的接口）

- **反向推导从「可选优化」升为硬依赖**：X 视角里「X 是目标」的那些边，必须把**别人的声明反着读**。现状 `relationLines`（`engine.go:302`）只画本 issue 自己存的三族，连名都没反。
- 需要 per-issue 的**入边索引**（或全量扫）才能把入边翻出来；否则只能看到出边。
- **箭头 vs 句子对反名的需求不同**：箭头用「声明源为箭尾」，**不需要反名**（箭上的名就是声明时写的）；句子用「视角为主语」，需要 `inverse(name)`。两者都要**入边索引**——否则 X 为目标那些边根本看不到。
- 反名与配对（`inverse`）要么硬编码、要么进 `relations` 配置——与上一轮「名字可自定义」的设计对齐。

### 7. 待验证

1. **视角化会不会让人迷惑**：同一对在 A 页是 `blocked-by`、在 B 页是 `blocks`——需 subagent 代理实验验证可读性。
2. **箭头规范形式用哪一侧做正名方向**：如 `blocks` 的箭头是「阻塞者→被阻塞者」还是反过来；需与 `relation-vocabulary` 的箭头规格对齐。

### 结论（推演，未定论）

1. **合理且必要**：有向关系的正反名不是冗余，而是**视角渲染的词对**。
2. **命名不变式升级**：写侧主语=声明方，读侧主语=被看方；统一为「**当前视角的 issue 即主语**」。
3. **两形态**：全局图=规范化箭头（1 态）；关系列表=视角化句子（按主语选正/反名）。
4. **反向边要生成**，但只在**渲染时**换名——不存第二条边。
5. 由此，反向推导/入边索引从「可选」变成**硬依赖**。

### 5. 指标

1. **分臂、分题型正确率**（方向 / 跨页 / 词对 / 写侧）。
2. **系统性错误计数**：特别统计「把入边渲染当成独立关系」与「方向搞反」两类。
3. **自报困惑点**（自由文本）：让 agent 看完后写“哪一行最让你不确定”。

### 6. 预先定好的判据（避免事后挑数）

- **不迷惑**：A 臂方向题 ≥ 3/4，且 ≥ B 臂 − 1；A 臂跨页题全对。
- **迷惑**：A 臂出现 ≥ 2 题方向搞反，或跨页题把同一条边数成 2 条。→ 启用下面 mitigation。

### 7. 预登记的缓解措施（若判定迷惑）

1. 关系区句子后附规范化箭头：`P1 spawns P2（P2 ──derived-from──▶ P1）`。
2. 反名加 gloss：`spawns ＝ 我引发的（derived-from 的反面）`。
3. 分组头写明方向：`阻塞（我阻塞谁）` / `阻塞（谁阻塞我）`。
4. 写侧只在 Skill 里保留**主名 5 个**，反名仅出在**读侧渲染**（不要求 agent 写反名）。

### 8. 局限

- subagent 与本体同源，**不等于**多样本用户；只能作方向性参考。
- 图小（10 节点）、题少（方向题 4 道），统计力弱；结论应在后续真实使用中复核。
- 只测“读懂”，未测“长上下文下持续保持方向不混”。

### 9. 与既有实验的关系

`relation-vocabulary` 的实验二已证明：**箭头渲染只有一种形态，反向名在“读”上是冗余的**。本实验问的是**另一半**：把反名抛给**读侧句子**后，agent 还读得对吗——两个实验合起来才能定“写 9 / 句渲 2 / 图渲 1”。

### 4. 三个真发现

1. **视角化没害处**：入边被翻成 X 为主语后，方向题全对——“同一对在 A 页是 `blocked-by`、在 B 页是 `blocks` 会让人搞混”的担心，**在本实验未出现**。
2. **纯箭头 + 只给主名，反而制造了写侧方向错误**：B1 在两道写侧题上都把 `blocked-by` 写成了 `blocks`（`blocks: R` 意味着 Q 阻塞 R，**主语 / 名字错配**，语义正好反了）。原因是 B 臂页面上 **从未出现 `blocked-by`**，agent 手里只有 `blocks` 一个依赖名，于是拿它当“等待解析”用。相反 A 臂页面出现过 `blocked-by`，两个 agent 都写对。→ **读侧暴露反名，对写侧有正向价值**。这与 `relation-vocabulary` “写 5 / 渲 1”的直觉相反：渲 1（只箭主名）会把写侧带偏。
3. **箭头形态自己就是困惑源**：B1 的自报困惑点正是 `P10 ──supersedes──▶ P1` 的**箭头方向**；B2 困惑于 `relates-to` 对称时箭头是否有意义。→ 箭头适合全局图，不适合当单 issue 页面。

### 5. 自报困惑点

| 臂 | agent | 困惑行 |
| --- | --- | --- |
| A | A1 | `P1 spawns P2` |
| A | A2 | `P1 spawns P2`（“不在可写键列表里，不确定是 `derived-from` 的逆名还是一条独立关系”） |
| B | B1 | `P10 ──supersedes──▶ P1` 箭头方向 |
| B | B2 | `P1 ──relates-to──▶ P2`（对称关系的箭头方向） |

→ A 臂的困惑**全部集中在同一个点**：反名 `spawns` 出现了，但“可写键说明”里没有它。**这是可修的一个点，不是视角化的通病**。

### 6. 对设计的处置

1. **采纳 A 臂形态作单 issue 页面渲染**（视角化句子）——预登记判据均过。
2. **入边必须渲染**（反向推导 / 入边索引）——本实验里 A 臂的正向价值就来自入边（`blocked-by`）可见。
3. **反名给一句轻量标注**：`P1 spawns P2（= P2 由 P1 引发）`，消除 A 臂唯一稳定出现的困惑点；即预登记的 mitigation #2。
4. **全局图仍用声明源箭头**（B 臂形态），但不拿它当单 issue 页面。
5. 与 `relation-vocabulary` 的“写 5 / 渲 1”对齐：本实验建议**把“渲 1”限定为全局图**；单 issue 页面是“句渲 2”（正反两名都会出现）。

### 7. 局限

- **样本极小**：2/臂、同源模型；B 的 11/13 只由 1 个 agent 拉下，不足以定论。
- **变量混淆**：A/B 同时差了“句子 vs 箭头”和“反名是否出现”两件事；写侧差异（H4）**不能纯归因于视角化**，更可能是“反名可见性”。
- 题少（方向题 5 道）、图小（6 条边）；未测长上下文、跨多级引用、以及 agent 长时间工作下方向是否会逐渐漂。

### 8. 结论（`test`，方向性证据）

- **视角化渲染在本实验中不迷惑**（H1–H3 均过）。
- **但真正意外的是写侧**：不让 agent 在页面上看到反名，会诱发“把 `blocked-by` 写成 `blocks`”这种主语/名字错配——这为“读侧展示反名（句渲 2）”提供了直接理由。
- **建议进入 `conclude`**：定下单 issue 页面 = 视角化句子 + 反名带标注；全局图 = 声明源箭头；视角化的成立前提是**入边渲染先落地**。

## test：实验隔离与效度——怎么防 subagent 看到实验设计（2026-10-18）

> 用户追问：怎么避免 subagent 看到我们的实验设计？下面是实测过的隔离协议。

### 1. 泄漏面（先列全，再逐个堵）

| 通道 | 内容 | 堵法 |
| --- | --- | --- |
| **工具**（决定性） | 设计 + 预期答案就存在 `docs/relation-rendering.md`，`read`/`grep`/`bash` 一读就全裸 | **`--no-tools`** |
| **cwd 注入** | `<cwd>` 路径会进 system prompt；`kiln-exp` 这种目录名会泄露项目 | 用**中性**临时目录名 |
| **上下文文件** | `<agent-dir>/AGENTS.md`（全局，总是加载）+ 从 cwd 逐级向上找 `AGENTS.md`/`CLAUDE.md`（不要求 trust） | `-nc` / `--no-context-files` |
| **skills** | skill 的 name/description 会进 system prompt（完整指令按需加载） | `-ns` / `--no-skills` |
| **prompt templates** | `-np` / `--no-prompt-templates` |
| **项目 `.pi/`**（settings/extensions/SYSTEM.md） | `-na` / `--no-approve` 忽略 trust-gated 项目资源 |
| **session 复用** | `-c`/`-r`/`-f` 会带历史 | `--no-session` |
| **prompt 自身** | 只能靠不写：不提假设名、不提预期答案、不提“这是实验” | 人工审查 |

### 2. 四个探针（实测）

| 探针 | 条件 | 结果 |
| --- | --- | --- |
| **A** | `/tmp/kiln-exp` + `--no-tools`（本次实验的实际条件） | 上下文只剩 pi 默认 system prompt 块（`<tools>(none)</tools>`、`<rules>`、`<docs>`）+ 全局 `AGENTS.md` + cwd；**无任何实验内容**。唯一瑕疵：`<cwd>` 里出现 `kiln-exp` |
| **B** | 仓库目录 + `--no-tools` | 仅命中 `kiln`（来自 cwd 路径）；`relation-rendering` / `视角化` / `blocked-by` / `实验` 全无。→ **即使跑在仓库里，`--no-tools` 也足够** |
| **C** | 仓库目录 + 只开 `read` 工具 | **读出 `docs/relation-rendering.md` 的 D1–D5 预期答案、得分表、实验图** → 确认主泄漏通道 |
| **D** | `mktemp -d` 中性目录 + `-nc -ns -np -na --no-tools` | 全无；`<project_context>` 直接为空 |

### 3. 对本次实验的效度结论

- 本次 A 臂/B 臂跑在 `/tmp/kiln-exp` + `--no-tools` + `--no-session`，**未泄漏实验内容**（探针 A）；结论有效。
- 唯一瑕疵：目录名 `kiln-exp` 使 cwd 里出现项目名（不足以影响 13 道题）。
- 探针 C 警告：**如果以后需要给 subagent 开工具，必须在文件系统层隔离**——把题库/设计放它读不到的地方（单独目录、只挂题库）。

### 4. 加固配方（推荐以后照用）

```sh
d=$(mktemp -d)          # 中性目录名，且在仓库之外
cd "$d"
pi -p --no-session --no-tools \
   -nc -ns -np -na \
   "$(cat prompt.txt)"   # prompt 里不写假设名/预期答案
```

- `--no-tools` 是**决定性**那一项；其余四项是 belt-and-suspenders。
- 两臂的 prompt 文件分开放、且不在 subagent 的 cwd 下（防止未来开工具时读到对方臂）。
- 若要更彻底，用 `--system-prompt` 直接换掉默认提示（探针 A 显示的 `<docs>`/`<rules>` 无害，但可一并去掉）。

### 结论（隔离协议，已实测）

**设计在文件里，工具是唯一主通道；`--no-tools` 就已挡住。** cwd 名、AGENTS.md、skills 是次要通道，分别用中性目录名与 `-nc -ns -np -na` 堵。本次实验已安全，下一个实验按 §4 配方跑。

## conclude：结论（2026-10-18）

### 0. 选了哪个候选

**候选 B（统一渲染）**：先定「视图 × 关系」矩阵，各视图按矩阵补齐——而不是只给 `graph` 打补丁（A）、也不是把所有关系塞进 `graph`（C）。

### 1. 视图 × 关系矩阵（本 issue 的核心交付）

| 视图 | 渲染形态 | 渲染哪些关系 | 主语 / 方向 |
| --- | --- | --- | --- |
| `path X` | **视角化句子** | X 的**全部出边 + 入边**，5 族（`part-of` 落地后同理） | 主语 = X；X 是声明方用声明的名，X 是目标用 `inverse(name)` |
| `graph` | **声明源箭头** | 全部有向关系（**补上现在缺的 `blocks` / `supersedes`**） | 箭尾 = 声明方；标签 = 声明时写的名 |
| `status` | **不渲染关系** | — | 维持现状（关系归 `graph`） |

### 2. 两个渲染形态（定稿）

- **箭头（全局图）**：`声明方 ──<声明的名>──▶ 目标`。箭尾 = **声明源**（不是语义源）；同一 `(对, 槽)` 只有一个值（槽机制），所以一条边只有一种形态。**不需要反名**。
- **句子（`path X`）**：主语 = X。X 为声明方 → 用声明的名；X 为目标 → 用 `inverse(name)`。**反名首次出现时带一句轻量标注**（如 `P1 spawns P2（= P2 由 P1 引发）`）——实验里 A 臂唯一的困惑点就在这里。

### 3. 反向边：要生成，但只在渲染时

- **不存第二条边**。X 为目标那些边，靠**入边索引 / 反向推导**翻出来并在渲染时换名。
- 这是本 issue 的**硬前提**（现状 `relationLines`（`engine.go:302`）只画本 issue 自己存的三族、且无反名）。机制/键/槽部分归 `relation-revision`。

### 4. 逐个回答 issue 开头的问题

| # | 问题 | 结论 |
| --- | --- | --- |
| 1 | 每个视图渲染哪些关系？ | 见 §1 矩阵 |
| 2 | `graph` 该补 `blocks` / `supersedes` 吗？ | **是**（`part-of` 落地后同理） |
| 3 | 方向怎么画？反向边要不要生成？ | 箭头 = 声明源；反向边**渲时生成**（换名，不存） |
| 4 | `status` 要不要显示关系？ | **不显示**（维持“status 只管 domain 目录”） |
| 5 | `check` 要不要校验 `blocks` 一致性？ | **不在本 issue**——属 `mvp-plan` §10（校验），与渲染分开 |

### 5. 实验依据

- **4 agent 实验**（2 臂×2）：视角化**不迷惑**（H1–H3 全过，方向题 A 10/10 = B 10/10）。
- **意外在写侧**：纯箭头 + 只给主名，诱发 `blocked-by` → `blocks` 的**主语/名字错配**（语义反了）；读侧出现反名的 A 臂则全对。→ **读侧必须暴露反名**，这是“句渲 2”的直接理由。
- **隔离协议**已实测定稿（`--no-tools` 决定性；中性目录名 + `-nc -ns -np -na`）。

### 6. 与相邻 issue 的边界

- **词表** → `relation-vocabulary`。本结论要求它把「**渲 1**」限定为**全局图**，单 issue 页面是「**句渲 2**」（正反两名都会出现）。
