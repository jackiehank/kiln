# issue: readme-collaboration — README 讲清人机协作里的位置，以及它和看板类工具的差别

- **domain**：design
- **关联**：relates-to `readme`（这份使用手册的「与 agent 协作」一节就是本条的改动对象）；relates-to `agent-ux-review`（一手 agent 使用记录，是"agent 到底怎么用 kiln"的证据来源）

## 背景

README 已经把**机制**讲得比较齐：定位（过滤器不是注册器）、安装、五分钟上手、命令一览、trailer 规范、配置、worktree 模式、后端差异、`check`、机器可读输出、已知边界。

但有两件事它**没讲**，而这两件事恰好是第一次听说的团队最先问的：

1. **人和 agent 各干什么，双方共同依赖的到底是什么。** 现在的「与 agent 协作」只有 5 条要点，讲的都是**怎么用**（一条约定、先开单再落代码、`--json`、`check`、worktree 隔离），没有说清**分工模型**：谁提问、谁裁定、谁把过程记下来、凭什么双方看到的是同一份事实。
2. **它和看板类工具（Jira / Trello / GitHub Projects / Linear）是什么关系**——替代、补充，还是根本不在一个层面。README 里**一句都没有**。

误读的代价很具体。"git trailer 驱动的问题追踪"这个说法，第一反应通常是"**没有界面的 Jira**"或"**又一个 todo 列表**"。带着看板的心智模型来用，会期待状态列、指派人、拖拽、通知、跨团队可见性——这些 kiln 全都没有；而 kiln 真正擅长的"研究路径可重建、动作序列可审计、`git clone` 即全量"，看板也不做——但 README 从没把这层差别摆出来。于是读者要么高估它（当成看板替代品），要么低估它（当成提交信息规范的小玩具）。

## 要回答的问题

1. **读者是谁**：写给"人 + agent 一起干活"的工程团队，还是写给单个用 agent 的开发者？两者的"协作"含义不同（前者要跨人可见，后者只要自己回看）。
2. **分工模型怎么表述**：人负责什么（提问、裁定、review：读 `path` / `graph` / `show`），agent 负责什么（把每次探究动作提交成带 trailer 的 commit），双方共享什么（同一个仓库、同一份 git 历史，没有第二份真相）。要不要给一张"一次典型协作"的时序？
3. **差异维度收哪些**（初稿如下，待裁剪）：

   | 维度 | 看板类工具 | kiln |
   | --- | --- | --- |
   | 状态载体 | 中央服务里的卡片字段（列 / 指派人 / 标签）；服务不在就没有状态 | 提交信息里的 trailer；`git clone` 到哪，状态跟到哪 |
   | 记录单位 | 卡片 = **协调状态**（谁在做、排到哪、卡在哪个列） | 动作 = **研究过程**（问题怎么被想清楚、证据在哪、结论怎么落地），每条动作天然带 diff |
   | "现在到哪了" | 看列 | 看动作序列（`kiln path`）：不是"做完没"，而是"试过什么、结论从哪来" |
   | 关系 | 父子 / 依赖 / 关联，通常是外键，由服务端渲染 | 9 种类型化关系写在提交里，`graph` 从历史重建，后写者胜、全图只出一形 |
   | 谁来写 | 人点界面；agent 走 API（凭证、服务在跑、字段语义、并发写） | 人或 agent 都只发一条 `kiln commit`；agent 用的就是它本来就要做的那次提交 |
   | 审计 | 附加的变更日志 | 提交历史本身就是日志；`git log` / `blame` 直接可用 |
   | 离线 / 多副本 | 需要连服务 | 无服务、无隐式状态 |

4. **放在哪、写多长**：改造现有「与 agent 协作」一节（改名「人机协作」？），还是新增独立一节「和看板有什么不同」？倾向：**分工模型并进「与 agent 协作」**（它本来就是这节的缺失前半段），**与看板的差别单独一小节**（读者会带着具体工具名来搜）。两处合计**不超过一屏半**，理由留给 `docs/design.md`。
5. **英文版**：`README.en.md` 与 `README.md` 目前双语同构（顶部互链，i18n 时立的规矩）。改动必须**同一提交同步两版**，还是允许中文先行？倾向同步——否则英文读者恰好缺的正是"为什么不是看板"这层。
6. **语气**：只陈述"各自适合什么"，**不评判看板工具好坏**。看板在跨团队可见性、排期与里程碑、权限与通知、非工程干系人参与、WIP 限制上更强，这些要**如实写进边界**——kiln 不替代看板，它替代的是"工程团队为了 agent 再维护一份状态"的那部分。

## 非目标

- **不改代码、不改命令面**——纯文档。
- **不写成竞品评测 / 营销对比页**：不逐条打分，不列功能矩阵的长表；只讲两类工具**各自回答什么问题**。
- **不承诺看板集成**（同步 / 导入 / 导出）——那是另一个 issue；本条的"不同"是解释，不是路线图。
- **不把 `docs/design.md` 的理由搬进 README**：README 留结论与一句话理由，论证仍在 `design.md` / `docs/`。

## hypothesize：收窄为「单人 + agent」，场景前置（用户裁定）

> 用户裁定（2026-11-01）：① 读者是**单人用 agent**，多人协作暂不在范围内——多人会缺一个 `author` 字段；② **使用场景放文档开头**，读者看一眼就要判断这个工具对他有没有用。

### 1. 读者收窄 → 协作模型只写两方

「与 agent 协作」不写"团队"，只写**一个人 + 一个（或几个）agent**：人提问 / 裁定 / review，agent 采集 / 提交，双方共享一个仓库、一份 git 历史。跨人可见性、排期、权限、通知这些**团队功能**不进主张，改放"边界"里——今天做不到的，不写成卖点。

### 2. 多人的缺口 = `author`，而且早就论证过

缺的不是数据，是**呈现**：每个动作都是一条提交，`git` 本来就有 `%an/%ae`；但本仓所有提交**共用同一个身份**（人 / agent 全糊在一起），且 `path` / `show` / `list` 都不渲染作者。[author-attribution](author-attribution.md) 的结论是"不做"，重启条件恰好是「出现第二个行动者在同一仓库提交」——**多人协作就是那个触发条件**。

→ 本 issue 的处理：README 把它写成**明示的边界**（"今天面向单人 + agent；多人协作前要先解决动作归属"），并把这条作为 `author-attribution` 重启的正式证据（relates-to）。**不在 README 里承诺一个不存在的字段。**

### 3. 结构变化：场景前置，机制后移

判据是"**看一眼就知道有没有用**"，所以顺序要变——现在的 README 先讲定位与"两个原子"，读者的第一个问题是"这和我有什么关系"，却要在第 200 行才看到 agent 协作：

| 现在 | 改后 |
| --- | --- |
| 定位（过滤器 vs 注册器）→ 设计（两个原子）→ 安装 → … | **什么时候该用它**（三条场景，每条一句）→ 一句话定位 → 和看板有什么不同 → 设计（两个原子）→ 安装 → … |

- **场景三条**（初稿）：① agent 干完活，过程只剩聊天记录；② 要复盘"这个结论是怎么来的"；③ 并行 agent 互相污染。每条落到一个命令，不落到形容词。
- **「两个原子 + 涌现」下沉**：它是理由，不是入口；放在场景与看板之后。
- **看板一节 ≤ 12 行**：一张维度表 + 一段"看板更强的地方"。只解释两类工具**回答不同问题**，不打分。

## apply：落地

- **README 顶部重排成三节**：「什么时候该用它」→「它是什么」→「和看板有什么不同」；「设计：两个原子 + 涌现」下沉到第四节。第一屏回答"是不是我的问题"，理由排在后面。
- **场景三条都落到命令**：`kiln path` / `show` / `graph` 对应"复盘结论怎么来的"，`worktree new` 对应"并行 agent 互相污染"；收尾一句"三条都不占？那 kiln 大概帮不上你——它不排期、不管人、也不生成待办列表"。
- **新增「和看板有什么不同」**：六维对照（状态住在哪 / 记录单位 / 到哪了 / 关系 / 谁来写 / 审计）+ 一段"看板更强的地方"（跨团队可见性、排期与里程碑、权限与通知、非工程干系人、WIP 限制），明写**不替代看板**。
- **「与 agent 协作」补分工**：人提问 / 拍结论 / review，agent 采集 / 提交；并说清"人拍的板落在 `conclude` / `apply`，agent 跑的腿落在 `collect` / `test`"。
- **多人边界如实落地**：新增一条"多人协作暂时不在范围内"——git 有 `%an/%ae`，但本仓共用同一身份、`path` / `show` / `list` 不渲染作者；指向 [author-attribution](author-attribution.md)。「它不做什么」同时加一条「不管人：没有指派人 / 通知 / 权限模型，也没有排期」。
- **中英同步**：`README.en.md` 同结构落地（When to use it / What it is / How it differs from a kanban board；Working with agents 补分工段与边界注），两版标题序列一一对应。

### 非目标（本轮）

- 未引入 `author` trailer——按 [author-attribution](author-attribution.md) 的结论走 git 身份路线，多人需求未到，只在 README 里写清边界。
