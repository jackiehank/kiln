# issue: refactor — 全面重构与性能优化

- **domain**：design
- **关联**：relates-to `perf-audit`（性能边界与三次低风险优化）；relates-to `commit-cache`（缓存落地后，"git 还是不是大头"这个问题换了答案）

## 背景

用户提出：kiln 需要一次全面的重构，同时把性能再推一档；性能侧先回答一个具体问题——**现在主要的耗时是不是在调用 git 上**。

`perf-audit` 的结论是"无索引 + 压掉进程"：真仓读命令 0.10–0.17 s，`--stat` 从 14.5 s 降到 0.31 s。`commit-cache` 之后，热读路径变成"一次 `git log --format=%H` + 一次本地层解码"，于是原来那句"一次 `git log` 是地板"不再自动成立：剩下的一次 git 进程仍按进程计价，而 kiln 自己开始解码 7 MB 级的层、建 100k 条记录。**谁是大头，取决于规模，得测。**

代码侧的现状（本仓 `c325656`）：

| 维度 | 数字 |
| --- | --- |
| 非测试代码 | 18 个文件 / 8,638 行 |
| 测试代码 | 11 个文件 / 7,311 行 |
| 最大单文件 | `internal/cli/cli.go` 3,471 行 / 117 个顶层函数 / 52 个 `(*env)` 方法 |
| 后端 | `vcs/git` 852 行 / 38 个函数；`vcs/jj` 496 行 / 24 个函数 |
| 覆盖率 | cli 86.3%、cache 82.7%、engine 80.9%、config 91.7%、trailer 94.9%、git 45.0%、jj 28.2%、model 33.3% |

`cli.go` 同时承担参数解析、命令编排、渲染（文本 / JSON / ascii / mermaid）与缓存协调；两个后端在 `Log` / `Show` / `Action` / `Changes` 等处各写一遍语义。

## 要回答的问题

1. **耗时归属**：热读 / 冷读的墙上时间里，进程创建、kiln 自身 CPU、一次 `git` 进程各占多少？随提交数怎么变？"git 是不是大头"在哪个规模上反转？
2. **自身 CPU 的热点**：解码层、建 map、建模型、折边、排序、渲染各多少？有没有同一个文件扫两遍这类重复劳动？
3. **不变成本**：一次进程创建（空 Go 程序）在本机多少毫秒？kiln 的二进制（5.5 MB）比它多付多少？二进制大小与初始化能不能压？
4. **结构性代价**：`cli.go` 3,471 行是不是真障碍——改一个命令要碰几处？渲染与编排能不能分开？两个后端重复的语义值不值得抽公共层？覆盖率最低的 `model` / `jj` 是"没测"还是"难测"？
5. **重构边界**：哪些是移动代码、契约为零风险的安全区；哪些必须和性能一起改；哪些（索引 / daemon / 并发 / 新依赖）明确不做？

## 非目标

- 不改 CLI 契约：命令、flag、文本 / JSON 输出逐字节不变；
- 不为性能引入常驻进程、索引或第三方依赖；
- 不重写已被验证的解析器与缓存格式（`trailer` / `cache` 的编码）；
- 不在测量前排并发，不为"整齐"做无收益的搬迁；
- 不把"重构"当目的——每条改动要说清它买到了什么。

## 验收（collect 完成时）

- 热读 × 真仓 + 合成规模的耗时分解表（进程创建 / `git` 子进程 / 自身 CPU）；
- 自身 CPU 的分阶段明细，含 100k 上的行级证据（谁在扫两遍、谁在排序）；
- 结构性盘点：文件与函数规模、后端重复面、覆盖率缺口；
- 明确回答"git 是不是主要耗时"，并给出反转点；
- 候选方向清单（必做 / 可选 / 不做），留给 hypothesize 定性。

## 采集（2026-10-29）：耗时到底在哪

### 口径：三层分开量

绝对耗时一直在被"测量工具本身"污染，所以这次分三层，各量各的：

1. **进程内**：临时探针（独立 module，`replace` 指回本仓）直接调 `cli.Run(argv, io.Discard, os.Stderr)`，只计 `Run` 内部的墙钟；输出丢给 `io.Discard`，不掺终端 / 磁盘。这是"kiln 自己花了多少"的**唯一可信口径**。
2. **git 子进程**：PATH 前置一个 `git.exe` 垫片，转发给真 git 并记录每次调用的存活时间与参数。它回答"调了几次 git、每次多久"，也证明"调 git"是不是瓶颈。
3. **端到端**：.NET `ProcessStartInfo` 起进程、读管道、`WaitForExit`；同一个 harness 里跑一个空 Go 程序做地板。它回答"用户等多久"，其中差额就是"Run 之外的成本"（进程创建、二进制加载）。

另有一个**阶段探针**：用真实包（`cache.Scan`、`engine.ActionsFromRecords`、`engine.Build`、`engine.FoldEdges`）逐段复刻热读路径，并与进程内总时长对账（账对得上，见 §3）。

- **机器**：Windows，Go 1.27.0，git 2.55.0.windows.3；kiln 由 `c325656` 的源码构建。绝对数字只属于这台机器（进程贵是 Windows + 本机 Defender 的特征），结构性结论不依赖它。
- **合成仓**：`git fast-import`，消息语料逐字取自本仓（关系、标题、body 的真实分布），N = 3k / 10k / 100k 提交。**注意：语料是循环的，100k 提交只有 72 个 issue**——所以折边和渲染被低估；读取与解码不被低估。
- **取数**：每个数字 3–7 次取 min；"端到端"表 7 次。

### 0. 一句话答案

- **本仓规模（406 提交 / 72 issue / 层 94 KB）：是。** `status` 端到端 96.3 ms，其中一次 git 进程 52.5 ms、进程地板 39.3 ms、kiln 自己的逻辑 **1–3 ms**。
- **10k 提交：还是 git，但只剩 69%。** `graph --json` 进程内 92.4 ms，git 63.8 ms、自身 28.6 ms。
- **100k 提交：反转。** `graph` 的 git 占 42%、`list` 52%、`path` 35%，**kiln 自身 CPU 成了大头**（195–392 ms），其中约 138 ms 是测量证明的浪费（见 §3）。
- **例外是 `action log`**：任何规模上 git 都占 84–96%，因为作者日期枚举拿不到缓存（author date 不在 commit-graph 里，git 必须逐个解析提交对象）。

### 1. 地板：一次调用里，进程占多大

用 `-overlay` 把 `cmd/kiln/main.go` 换成一个"判断环境变量就打印 `hi` 并返回"的版本，得到**同尺寸、同链接、什么都不做**的二进制——这样二进制大小与运行时的成本就和命令逻辑分开了。

| 项 | 端到端 min (ms) | 说明 |
| --- | --- | --- |
| 空 Go 程序 `hello.exe`（2.5 MB） | 32.3 | 进程创建 + 测量侧管道 + Go 运行时 |
| 同二进制改走"空分支"（5.5 MB） | 39.3 | 多 7 ms = 二进制 2.5 → 5.5 MB |
| `kiln --version` | 59.0 | 39.3 + **19.7**（见下一行） |
| `--version` 内部那 19.7 ms | — | Go 的 `time.Local` 惰性初始化：`time.Now()` 首次调用本机实测 20.5 ms |
| 一次 `git --version`（PATH 上的 `cmd\git.exe`） | 43.7 | Git for Windows 的 launcher |
| 直呼真身 `mingw64\bin\git.exe --version` | 30.8 | **launcher 链本身 ≈13 ms/次** |

两件事值得记住：

- **`--version` 的 20 ms 花在打印本地时间上**，不在命令逻辑里；`cli.Run` 内部实测把 `--version` 的第二、三次调用压到 0 µs，说明是一次性初始化。读命令不付这笔钱（提交日期带显式时区偏移，不碰 `time.Local`）。
- **kiln 的每次 git 调用是 2 个进程**：`exec.Command("git")` → PATH 上的 `cmd\git.exe` → 再 exec `mingw64\bin\git.exe`。`git.go` 里 `WaitDelay` 的注释已经记了这件事（杀 launcher 不等于杀真身），但没人量过它 ≈13 ms。

### 2. 热读分解：git 子进程 vs kiln 自身

进程内口径；"git 子进程"取自阶段探针的 `LogOIDs` 实际耗时，"自身"= 进程内总时长 − git。

| 仓 / 规模 | 命令 | `cli.Run` 内 (ms) | git 子进程 (ms) | kiln 自身 (ms) | git 占比 |
| --- | --- | --- | --- | --- | --- |
| 本仓 406 提交 / 层 94 KB | `status` | 53.6 | 52.5 | **1.1** | 98% |
| 同上 | `graph --json` | 55.1 | 52.5 | 2.6 | 95% |
| 同上 | `action log --jsonl` | 68.9 | 66 † | 2.9 | 96% |
| 3k 提交 | `graph --json` | 62.0 | 52.2 | 9.8 | 84% |
| 10k 提交 | `graph --json` | 92.4 | 63.8 | 28.6 | 69% |
| 100k 提交 | `graph --json` | 507.0 | 212.5 | **294.5** | 42% |
| 100k 提交 | `list --json` | 406.7 | 212.5 | 194.2 | 52% |
| 100k 提交 | `path --all --json` | 604.6 | 212.5 | 392.1 | 35% |
| 100k 提交 | `action log --jsonl` | 844.7 | 707 † | 137.7 | 84% |

† `action log` 走 `--author-date-order`，阶段探针没有对应实现，用垫片量（含垫片自身 ≈5 ms）。

**真仓的账能对上**：端到端 96.3 ≈ 39.3（地板）+ 52.5（git）+ 4.5（自身 + 输出）。

### 3. 自身 CPU 的分段（100k，`graph --json`）

阶段探针 4 次取 min，并用进程内 507.0 ms 对账：

| 阶段 | ms | 占比 | 备注 |
| --- | --- | --- | --- |
| `git log --format=%H` | 212.5 | 44.6% | 4.1 MB OID + 一次进程 |
| `cache.Scan` | 31.4 | 6.6% | 读 7.0 MB + SHA-1 + 解码 100k 条 |
| 建 index：`make(map, 0)` | 51.8 | 10.9% | 没有容量提示，反复扩容 |
| —— 同一件事、预分配 `len(oids)` | **9.2** | 1.9% | **差 42.6 ms** |
| `engine.Build` | 47.6 | 10.0% | |
| 折边 + 排序 | 97.7 | 20.5% | `sort.SliceStable` 占其中 ~65%（pprof） |
| 再扫一遍层（`maybeMerge`） | 35.4 | 7.4% | 同一次读里第二次 `cache.Scan` |
| 渲染（只有 72 个 issue） | ≈0 | | 语料低估了这项 |
| 合计 | 476.4 | | 进程内 507.0；差 ≈30 = 记录装配 + i18n |

三笔**测量证明**的浪费（合计 ≈138 ms，占 100k 热读的 27%）：

1. **每次热读把层读两遍。** pprof 的 `cache.Scan` 调用方：54% 来自 `maybeMerge`、46% 来自 `loadCached`。`loadCached` 已经解出了 `layers`，但它把 `records` 交给下游后，`maybeMerge` 又 `cache.Scan(dir)` 一遍来数层数——7 MB 读两遍、SHA-1 两遍、解码两遍（31.4 + 35.4 ms）。
2. **index map 没有容量提示。** `make(map[[20]byte]cache.Record, 0)` 插入 10 万条：[20]byte 键 + `Record` 值（含 4 个 slice 头）体量大，扩容与搬迁把 9.2 ms 的活干成 51.8 ms。
3. **折边把所有动作全量排序。** `FoldEdges` 为了"按时间顺序折叠声明"，把 100k 个 `model.Action` 装进 `[]item` 再用 `sort.SliceStable` 按 `time.Time` 比较——100k 条、每比较一次 `Equal`+`Before`；pprof 行级显示排序 400/620 ms（5 次运行），即 ≈65%。

### 4. 冷读：建层要付多少

| 仓 | 冷 (ms) | 热 (ms) | 多付 (ms) | 层大小 |
| --- | --- | --- | --- | --- |
| 本仓（`status`） | 95.3 | 56.6 | +38.7 | 94 KB |
| 10k（`graph --json`） | 201.3 | 89.5 | +111.8 | 766 KB |
| 100k（`graph --json`） | 1358.2 | 525.9 | +832.3 | 7.0 MB |

100k 上多付的 832 ms 里，约 700 ms 是"带 body 的全史 `git log`"（912 − 212），其余是解析 100k 条消息 + 编码 + 写 7 MB。

### 5. 命令形态：git 调了几次

垫片实测（真仓）：

| 命令 | git 调用 |
| --- | --- |
| `status` / `list` / `check` / `graph` / `path` | 1 × `log --format=%H` |
| `action log` | 1 × `log --author-date-order --format=%H`（流式，可提前停） |
| `show` | 2 ×（`log --format=%H` + `show <hash>`） |
| `worktree list` | 1 × `worktree list --porcelain`（不读历史） |
| `--no-cache` 变体 | 同样 1 次，但换成带 body 的 `log --format=%H%x1f%aI%x1f%B%x1e` |

体量：100k 上 `path --all --json` 输出 31.5 MB、`action log --jsonl` 31.8 MB——渲染与写盘本身也是一笔账（`path --all --json` 写文件 903 ms vs 写 `Discard` 604 ms）。

### 6. 结论

1. **"git 是不是主要耗时"取决于规模，且在 10k–100k 之间反转。** 真仓 98% 是那一次 git 进程；10k 时降到 69%；100k 时 `graph` / `list` / `path` 都跌破 52%，kiln 自身成为大头。
2. **小规模上最大的单项不是代码，是进程。** 每次调用 ≈39 ms 地板（含 7 ms 二进制尺寸），一次 git ≈50 ms（其中 ≈13 ms 是 launcher 链），kiln 自己的逻辑 1–3 ms。**在真仓规模上继续"优化代码"没有意义**——除非动进程形态（不现实）或干脆不调 git。
3. **大规模上最大的单项在 kiln 自己这边**，而且不是算法复杂度问题，是三处"顺手写"的浪费：扫两遍层、map 不预分配、全量稳定排序。
4. **`action log` 是唯一没被缓存救到的命令**（作者日期不在 commit-graph 里），它的 84–96% 永远是 git；要动它只能动枚举方式，不是动 kiln 的 CPU。
5. **冷读的代价与层大小成正比**，100k 一次性 +832 ms；只要层还在读路径上，这就是"第一次用"的地板。

### 7. 结构性盘点（重构侧）

| 项 | 现状 | 观察 |
| --- | --- | --- |
| `internal/cli/cli.go` | 3,471 行 / 117 函数 / 52 个 `(*env)` 方法 | 占非测试代码 40%；解析、编排、渲染、缓存协调全在一处 |
| `loadCached` | 1 个函数里做完：扫层、算缺失、补拉、判重写、判合并、建模 | 70 行、6 个职责；"扫两遍层"就长在这里 |
| 两个后端 | `git` 38 函数 / `jj` 24 函数，**17 个同名方法**（`Log`/`LogEach`/`Action`/`ActionChecked`/`action`/`Changes`/`Unchanged`/`Show`/`ShowStat`/`IsDedicated`/`NewWorkspace`/`ListWorkspaces`/`Dirty`/`AreaState`/`dirty`/`RemoveWorkspace`/`run`） | 语义各写一遍；jj 不实现 `CacheBackend`，分叉是设计使然，但重复的模板可以抽 |
| 渲染 | 文本在 `cli`、ascii/mermaid 在 `engine`、JSON 在 `cli` | 同一条数据三种出口，没有共同的渲染接口，测试只能走 `cli.Run` |
| 覆盖率 | `model` 33.3%、`jj` 28.2%、`git` 45.0% | 重构最想动的地方恰好是测得最薄的地方 |
| 测试规模 | 11 文件 / 7,311 行，`internal/cli` 单包 13.1 s | 反馈不慢，但端到端测试占主导 |

### 8. 候选方向（留给 hypothesize 定性，本 collect 不决定）

**有测量证据、可预期收益**：

1. 热读**只扫一遍层**：`loadCached` 把已解出的 `layers` 传给 `maybeMerge`，别让它再 `Scan`。（100k：−35 ms）
2. **预分配** index map 与 `missing`：`make(map[[20]byte]cache.Record, len(oids))`。（100k：−43 ms）
3. **折边去掉全量稳定排序**：先按 `(Date, issue)` 生成 `int64` 键 + `sort.Slice`；或者干脆不排——每个 issue 的 actions 本身已是时间序，按 issue 归并即可。（100k：−60 ms 量级）
4. （可选）**缓存命中时省掉一次哈希往返**：层内记录本来就按 OID 有序，把 `oids` 排序后与记录做归并，也许比建 map 更快——未测，需 hypothesize 里定性。

**结构性（重构）候选**：

5. 把 `cli.go` 按"解析 / 编排 / 渲染"拆包，先拆渲染（可脱离 `cli.Run` 测试）；
6. 给两个后端抽一层公共语义（模板方法或 helper），不动 `vcs.Repo` 契约；
7. 补 `model` / `jj` 的测试到与 `cli` 同档（50%–80%），再谈搬迁；
8. `--version` 的 20 ms：改印 UTC，或把 `构建时间` 挪出 `time.Local`——只影响诊断命令。

**明确不做**：

- daemon / 常驻进程 / 索引 / 并发读——与"无状态、永远和 git 一致"的设计冲突，且本 collect 没测出它们能赢过"一次 git 进程 + 本地层"；
- 二进制瘦身（`-s -w` 实测只省 ≈2 ms，不值）；
- `show` / `--stat` 路径的进一步批量——`perf-audit` 已经做过，且不在这个问题的热点里。

### 9. 没测到的 / 口径警告

- **只有 Windows**：Linux/macOS 上进程创建便宜一个量级，"地板"结构不变但占比会小很多；本 collect 的结论里"进程是大头"只对这台机器成立。
- **合成语料只有 72 个 issue**：折边与渲染被低估；真实"多 issue"仓的 `graph` / `path` 会更贵，`FoldEdges` 那笔可能更显著。
- `show` / `--stat` / `commit` 只量了调用数，没做分解。
- 并发读（两个进程同时写层）没测；`go test -race` 在本机不可用（CGO 关闭）。
- 5.5 MB 二进制的 +7 ms 无法进一步拆分（链接布局 vs Defender 扫描）。

## 采集（续，2026-10-29）：一次 git 调用里，"调用"占多少、"干活"占多少

问题来自上一个 collect 的边界：真仓 98% 的时间标在"git 子进程"上，但那一格里其实混着三样东西——**起进程**、**git 自己启动**、**git 读历史**。如果前两样是大头，那"自己实现 git 读取"就值得认真考虑；如果大头是第三样，就没什么可省的。所以先把这一格拆开。

### 1. 怎么把三样分开：分层减法

不用猜，用同一把尺子（同一个 .NET `ProcessStartInfo` harness、同目录、15 次取 min）量一串"启动得越来越多"的命令，相邻两项的差就是那一层：

| 命令 | min (ms) | 这一层买到的东西 | 增量 |
| --- | --- | --- | --- |
| `cmd.exe /c exit` | 25.9 | **OS 起一个原生进程并回收**（任何子进程都付） | — |
| `hello.exe`（Go，2.5 MB） | 31.2 | + Go 运行时 | +5.3 |
| `git --version`（PATH 上的 launcher） | 58.0 | + git 镜像加载与启动 | +26.8 |
| ↳ 直呼真身 `mingw64\bin\git.exe --version` | 44.1 | 少掉 launcher 那一跳 | **−13.9** |
| `git rev-parse --git-dir` | 59.3 | + 仓库发现（读 config / 解析 `.git`） | +1.3 |
| `git log -1 --format=%H` | 61.6 | + 读出一个提交 | +2.3 |
| `git log --format=%H`（本仓约 400 提交） | 65.9 | + 遍历 400 余提交、输出 4.1 KB | +4.3 |
| `git log --format=%H`（r100000） | 243.8 | + 遍历 100k 提交、输出 4.1 MB | +182 |

同一把尺子下的合成仓：`rev-parse --git-dir` 在每个规模都是 58 ms 左右，`log --format=%H` 是 3k 64.9 / 10k 78.1 / 100k 243.8。

**读数**：

- **"调用"+ "启动" ≈ 58 ms，与规模无关**；其中 26 ms 是 OS 的进程地板，其余 ≈32 ms 是 git 自己的加载与启动（含 launcher 那一跳 13.9 ms），仓库发现只有 1–2 ms。
- **"干活"随规模线性长**：本仓约 7 ms（12%），3k 约 7 ms，10k 约 20 ms，100k 约 186 ms（76%）。
- 本仓规模上，一次 git 调用 **~88% 是"起进程 + git 启动"，只有 ~12% 在真正读历史**；100k 上反过来。
- 顺带确认：**kiln 每次调用 git 是 2 个进程**，launcher 那一跳值 13.9 ms（≈24% 的固定成本）。

### 2. 那"自己实现"能省到哪一步

关键是：**别自己读 packfile，读 commit-graph 就够了**。kiln 热读只需要"OID 列表 + 顺序"，而 commit-graph 恰好存了 OID、提交时间、父提交索引，全是预先算好的。

写了两个一次性探针（`%TEMP%` 下，不入库）验证可行性：

- **解析**：100k 的 `commit-graph`（6.0 MB，含 OIDF/OIDL/CDAT/GDA2）读 + 解析 = **6.2–6.7 ms**；本仓是 4 层 chain（802 提交）0.5 ms。
- **顺序**：照 git 的走法实现（按提交时间从新到旧的优先队列，弹出后把父提交按顺序插回队列，同秒的先进先出）。结果与 `git log --format=%H` **逐字节一致**：
  - r100000（纯线性）100,000 行全同；
  - 本仓 408 行全同——注意它包含一个**同一秒的两条提交**（`a01c065` / `95c67e8`），单纯按时间排序在这里就错了（第一次尝试在 idx 163 分叉），加回队列语义才对齐。
- **成本**：解析 + 走图 = **11 ms @100k**（6.5 + 4.6）、**0.7 ms @本仓**；对照 git 进程内的 212.5 / 52.5 ms，是 **19× / 75×**。
- 端到端对照（都起一个进程、都把 4.1 MB 写出去）：Go 读图 83 ms vs `git log` 244 ms @100k；本仓 34 vs 60 ms。**只有当它在 kiln 进程内跑，收益才是全额**（不然一半被自己的进程地板吃掉）。

### 3. 还有一条更便宜的路：把"枚举结果"本身缓存起来

上面那个实验说明 git 的输出顺序是可以复现的，但也说明复现顺序要写一套走图逻辑。**换个角度：顺序不用复现，存下来就行。**

`git log` 对同一个 HEAD 的输出是确定的（提交不可变；开关固定）。所以可以缓存"HEAD → 有序 OID 列表"：

- 成本：读回 4.1 MB 文本并切成 `[]string` = **2.1 ms @100k**（存二进制 20 B/OID 还能砍半），本仓 ≈0。
- 失效：不用跑 git 去问 HEAD——**从文件系统读**（`.git/HEAD` → 符号引用 → `.git/refs/heads/…` 或 `packed-refs`；worktree 用各自 HEAD，对象仍在共同目录）。kiln 已经有 `commonDirFromFS` 这套走文件系统的先例。
- 风险：HEAD 之外还能改历史的东西——`refs/replace/*`、`info/grafts`、`shallow`、以及 `GIT_NO_REPLACE_OBJECTS` 之类的开关。失效键要把这些都算进去（或存成"这几个文件的内容哈希"），算不清就回退 git。
- 好处：**顺序逐字节等于 git**（存的就是 git 的输出），不需要复现走图；坏处：多一份"和 HEAD 绑定"的可变快照，和现有"无索引、可合并的内容寻址层"是两种东西。

### 4. 三条路放在一起（进程内成本，热读）

| 方案 | 100k | 本仓 | 顺序正确性 | 主要风险 |
| --- | --- | --- | --- | --- |
| 现状：一次 `git log --format=%H` | 212.5 ms | 52.5 ms | 同 git | — |
| A. 内建 commit-graph 读 + 复现走图 | 11 ms | 0.7 ms | 已实测逐字节一致（两个仓） | graph 缺失/过期要有回退；chain/16B vs 20+H/octopus/SHA-256/shallow/replace/grafts |
| B. 缓存枚举顺序（HEAD 快照） | 2.1 ms | ≈0 | 存的就是 git 输出 | 失效键（replace/grafts/shallow）；多一份可变状态 |
| C. 信任缓存、零 git（HEAD 命中即答） | 0 ms | 0 ms | 需要层自带 commit date + parents，否则顺序不保真 | 同上，且等于把 commit-graph 自己存一遍 |

- 若目标只是"真仓 96 ms → 50 ms 上下"，**B 最划算**：改动小、顺序天然一致、成本 2 ms。
- **A** 是"正经实现"，但要连带把"graph 不存在/过期"的两条回退路径做对，还要覆盖 git 的替换/嫁接/浅克隆语义；这些没人替我们测。graph 缺失时可以顺手写一份（`git commit-graph write --reachable`：本仓 200 ms、100k 609 ms），但那也只能挂在冷读/后台，不能挂在热读上。
- **C** 只有把层扩展成"能自己排序"才有意义，本质是把 commit-graph 抄进缓存，工作量最大、收益与 B 同量级，不推荐。
- 三条都仍然需要 git：**冷读 / 缺记录时补消息**、`show` / `--stat`、`commit`、`worktree`。所以这不是"把 git 换掉"，而是"把热读那一次 git 拿掉"。

### 5. 结论（续）

1. **"调用"确实很贵，而且在真仓规模上它就是全部**：一次 git 调用 ~58 ms 固定成本里，26 ms 是 OS 进程地板、27 ms 是 git 自己启动、13.9 ms 是 launcher 那一跳；真正读历史只有 7 ms。
2. **所以"自己实现读取"方向成立，但要收窄**：读 commit-graph（11 ms @100k）而不是读 packfile；甚至更省——缓存枚举顺序（2.1 ms），一行 git 都不用跑。
3. **顺序是这件事的真门槛，不是性能**：单按时间排序在本仓第 163 行就分叉（同一秒的两条提交），必须复现 git 的队列语义；而"存下 git 的输出"天然绕过它。这也是为什么 B 比 A 风险低。
4. **先做便宜的**：100k 那 138 ms 的浪费（层扫两遍、map 不预分配、全量稳定排序）与这件事正交，且成本低得多；"拿掉热读的那次 git"单独立项更合适——它要带一整套回退与黄金测试。

## 讨论（2026-10-29）：分层缓存要不要换成 SQLite

问题：现在是"内容寻址的分层文件"，要不要改成 SQLite？改了什么会变？

### 1. 分层缓存今天实际付出了什么（已测）

| 项 | 本仓 | 10k | 100k | 备注 |
| --- | --- | --- | --- | --- |
| 每读一次：扫全部层 | 1.5 ms | 3.6 ms | 31 ms（重复扫 +35 ms） | 读字节 + SHA-1 校验 + 全量解码 |
| 每读一次：建 index map | ≈0 | 3.6 → 0.5 ms | 52 → 9 ms | 无容量提示，可修 |
| 命中时写入 | 363 B，<1 ms | 同量级 | 同量级 | 只写"本次新见到的提交" |
| 每 64 层合并一次 | 可忽略 | — | encode+write 7 MB ≈ 130 ms | 摊到每次读 ≈2 ms |
| 冷读建层 | +39 ms | +112 ms | +832 ms | 一次性 |
| 代码量 | — | — | 1,308 行 / 49 个函数（`internal/cache` + `cli/cache.go`） | 含 merge / sweep / rewrite 信号 |

**关键观察**：除"冷读建层"外，分层缓存在热读上的固定成本只有**解码全量层**这一项（31 ms @100k、1.5 ms @本仓）。写入与合并已经被"只写增量 + 摊薄重写"压到噪声级。

### 2. SQLite 会改变什么

| 维度 | 现在 | 换成 SQLite | 影响 |
| --- | --- | --- | --- |
| 写入 | 增量层文件（363 B）+ 每 64 层重写 | 行级 upsert，永不重写 | 省掉 merge/rewrite/sweep 那套逻辑（≈150 行 + 测试），摊薄成本 ≈2 ms/读归零 |
| 全量读取 | 手写二进制解码 7 MB = 31 ms | 逐行走 `database/sql` 物化 100k 行 | **大概率更慢**（驱动/反射开销），这条是估计、未实测 |
| 局部读取 | 没有：所有命令都建全量模型 | 可按 `issue` 索引只查需要的行 | 上限收益：窄命令 100k 上可省 ~30 ms；但要先把 model 改成惰性加载，是一次真重构 |
| 并发写 | 内容寻址 + 原子 rename ⇒ 天然幂等，无需锁 | WAL + `busy_timeout` + `-wal`/`-shm` | 语义更通用，但引入锁竞争与超时策略 |
| 损坏 | 层名 ≠ 内容哈希 ⇒ 忽略并删除 | 整库损坏只能重建；有 `integrity_check` | 都是"删了重建"，但 SQLite 多一层 schema/迁移 |
| 只读 / 网盘 | 失败就静默跳过；读只需读权限 | RW 打开在只读挂载上会失败；NFS/SMB 上锁不可靠 | `.git/kiln` 常跟着仓库放在网盘/共享盘，这条是**减分** |
| 依赖 | `go.mod` 零依赖，单二进制 5.5 MB | 纯 Go 实现（modernc / ncruces）拉进数 MB 代码 | 本机实测二进制 2.5 → 5.5 MB 就多付 **≈8 ms 启动地板**；在"还没拿掉 git 调用"之前，这是净亏 |
| GC | 删层文件 | `DELETE` + `VACUUM`（= 重写整库） | 复杂度平移，不消失 |

注：本机无法 `go get`（代理不可达），所以 SQLite 侧的行物化/打开成本是**推断**，不是实测；这也提醒一件事——引入依赖会带来一条现在没有的供应链。

### 3. 值不值，取决于仓库规模

| 规模 | 现在热读的解码成本 | SQLite 能省下的 | 结论 |
| --- | --- | --- | --- |
| 1k | 1.5 ms | ≈0（打开一个库本身就要 1–3 ms） | 不值 |
| 10k | 3.6 ms | ≈0.5 ms | 不值 |
| 100k | 31 ms（+35 ms 重复扫） | ≈2 ms 摊薄；窄命令 ≤30 ms | 边界，且重复扫是我们自己的 bug，5 行就能修 |
| 1M | ≈310 ms | 部分读可省 200 ms 以上 | 开始值，但那时真正的瓶颈可能是别处 |

**而且它一点也帮不到当前最大的那块成本**：一次 git 进程 ≈52 ms（本仓）/212 ms（100k）。在"热读还起 git"的前提下换存储，真仓只会从 96 ms 变成 ~104 ms。

### 4. 什么时候该换（触发条件，留给后续）

1. 热读不再起 git（枚举快照或 commit-graph 读）之后，读路径的下一个瓶颈才是"解码全量层"；
2. 中位仓库到 100k 提交以上，或 1M 级要"只读一个 issue"成为常态（需要 model 惰性化）；
3. 需要检索类能力（`doc-search` 复活、标题/正文全文搜索）——SQLite FTS 是它真正的强项；
4. 多进程并发写同一份缓存真的出过故障（目前没有证据，现方案靠幂等绕开锁）。

反过来，如果确认大量仓库在网盘/只读环境使用，SQLite 是**负收益**。

### 5. 结论（讨论）

**现在不换。** 分层缓存已经把这层压到噪声级（热读 1.5–31 ms），而 SQLite 的三项收益里：增量更新只值 ~2 ms/读、局部读取要先重构 model、并发安全我们已用幂等绕开；代价是唯一的零依赖 + 一套新的迁移/锁/网盘失败模式，以及 +8 ms 量级的启动地板。真正的瓶颈是 git 进程，换存储对它零帮助。

若真要换，最小路径：保持"缓存可随时删"的契约（schema 版本不匹配就整库重建）、先只替换"读全部 + 写增量"两处、用现有逐字节一致测试当回归网、并先量出 driver 的行物化成本再决定。

## 假设（2026-10-29）：顺序是"先清浪费 → 再去掉那次 git → 冷读与渲染 → 结构重构"

### 1. 排序依据（三条，按重要性）

1. **按"用户感知的规模"排序，不按"能省多少毫秒"排。** 真仓热读 96 ms 里，git 52.5 ms、进程地板 39.3 ms、kiln 自己 4 ms——除了"热读不再起 git"，没有任何改动能把它压下一半；而 P0 那三处在真仓只值 1.5 ms（噪声内）。反过来，100k 上 git 只占 42%，自身 CPU 才是大头。
2. **但便宜的先做。** P0 三处合计约 40 行、契约零风险、且能把 100k 的"自身 CPU"清掉 138 ms。先做它，P1 的收益才可归因；否则 P1 的 −212 ms 会被自身 CPU 的噪声淹掉一半。
3. **结构重构最后做。** 拆 `cli.go`、抽后端公共层、model 惰性化，今天都没有可测收益；先做会把测量基线搅乱。而且 P1 落地后可能发现"惰性化"根本不需要——先测再动。

### 2. 四步方案

| 步 | 内容 | 真仓热读 | 100k `graph` | 100k `path --all` | 100k `action log` | 风险 | 规模 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 现在 | — | 96 ms | 507 ms | 605 ms | 845 ms | — | — |
| **P0** | 三处热修：① 热读只扫一遍层 ② index map 预分配 ③ FoldEdges 去掉全量稳定排序 | ~95 ms | ~370 ms | ~467 ms | ~810 ms | 极低 | ~40 行 |
| **P1** | 枚举快照：热读**不起 git**（内容寻址 `enum-*` 文件，键 = HEAD + 枚举种类 + 失效因子） | **~45 ms** | **~160 ms** | ~257 ms | **~145 ms** | 中 | ~250 行 + 测试 |
| **P2** | ① `commit` 时把新 HEAD 追加进快照（提交后第一次读也 0 次 git）② `path` 的 31.5 MB 渲染效率 | ~45 ms | ~160 ms | ~180 ms | ~145 ms | 低 | ~80 行 |
| **P3** | 结构重构：拆 `cli.go`（先拆渲染）、后端抽公共语义、补 `model` 测试；**只有 P1 之后才评估 model 惰性化** | 无直接收益 | — | — | — | 中 | 大 |

**P0 明细（每项都有测量证据）**

1. `loadCached` 把已解出的 `layers` 传给 `maybeMerge`，别再 `cache.Scan` 一遍——100k −35 ms（pprof：Scan 调用 54% 来自 maybeMerge）。
2. `make(map[[20]byte]cache.Record, len(oids))`——100k −43 ms（51.8 → 9.2 ms）。
3. `FoldEdges` 去掉 `sort.SliceStable`：折叠规则可以逐 `(pair, slot)` 比较（先比 rank、再比时间），不需要全局排序——100k −60 ms（pprof 行级：排序占折边 65%）。**这一项必须先用现有关系测试证明"逐声明比较"与"全局排序后折叠"等价，再逐字节回归。**

**P1 明细（主菜，也是唯一能改变真仓体验的一步）**

- 形态：每次真正跑过 `git log --format=%H`（默认序）或 `--author-date-order`（action log）之后，把输出原样存成 `enum-<hash>.oid`，`hash = sha1(格式版本 | 枚举种类 | HEAD | 失效因子)`。命中即零 git。
- 为什么是"存下 git 的输出"而不是"自己读 commit-graph"：成本 2.1 ms vs 11 ms，**顺序天然逐字节等于 git**，不需要复现走图语义（上一轮实测：单按时间排序在本仓第 163 行就分叉）。
- 失效因子（不跑 git 判定）：从文件系统读 `.git/HEAD`（含 worktree/符号引用/`packed-refs`/detached），加上 `shallow` 文件哈希；`refs/replace/*` 或 `info/grafts` 存在就直接放弃快照、回退 git。`.git` 走文件系统的先例已有（`commonDirFromFS`）。
- 只读仓 / 写失败：静默回退到"每次跑 git"，与今天一致。
- 风险：HEAD 解析（reftable 格式、`GIT_DIR` 环境、命名空间）、失效因子漏项、快照与 git 版本耦合。**任一项判不准就不命中**——宁可多跑一次 git。
- 验收：垫片计数显示热读 **0 次 git**；六命令 × 冷/热/--no-cache × 四规模的输出逐字节一致；HEAD 前进/回退/amend/rebase/worktree 切换/只读仓各一条测试。

**P2 明细**

- `kiln commit` 之后 HEAD 变化会让快照失效，于是"提交后第一次读"仍要一次全量枚举（真仓 52 ms、100k 212 ms）。但提交时知道新 HEAD、也知道父提交就是旧 HEAD ⇒ 新列表 = `[新 HEAD] + 旧列表`，**不需要跑 git**。这能把"写—读"循环里的最后一次 git 调用也消掉。
- `path --all --json` 在 100k 要输出 31.5 MB，P0/P1 之后剩下的 ~250 ms 几乎全在渲染/拼接；目标砍一半（用预算好的 buffer/流式写，别再走带缩进的 `json.Encoder`）。

### 3. 目标与止损

- **目标**：真仓热读 ≤50 ms（现 96）；提交后第一次读 ≤60 ms；100k `graph` ≤170 ms、`action log` ≤150 ms、`list` ≤210 ms（现 507 / 845 / 407）。
- **止损**：P1 若在"六命令 × 冷/热/--no-cache × 四规模 + worktree/replace/shallow"矩阵里做不到逐字节一致，就停——保留 P0，把原因写进文档。**正确性优先于这 40 ms。**
- **每步的度量协议固定**：真仓 + 3k/10k/100k；`min of 3`；进程内探针测自身 CPU、垫片测 git 调用次数与时长；改动前后跑同一套。

### 4. 明确不做

- daemon / 常驻进程 / 并发读 / 索引（SQLite 或别的存储）——见上一节讨论；
- 自己读 packfile（只可能读 commit-graph，且已被"存枚举"取代）；
- 二进制瘦身（−2 ms）、`--version` 的 20 ms（顺手可改，但不值得占一个动作）；
- 为"整齐"而重构 `trailer` / `cache` 的编码格式。

### 5. 一点判断

P1 是唯一"改形态"的改动，也是唯一能让真仓从 96 ms 掉到 50 ms 以下的。它换来的东西很清楚：**把 git 从热路径上拿掉，但仍然完全依赖 git 得出一致的结果**——快照就是 git 的输出，不重写语义。代价是多一份与 HEAD 绑定的可变文件，和一套"判不准就回退"的规则。

如果只想拿低风险收益，P0 大约能用 40 行换 100k 上 27%；但那对真仓用户几乎不可见。**我的建议：P0 立刻做，P1 单独立项、按上面的验收矩阵推进，P2/P3 等 P1 的数字出来再定。**

## 落地（P0，2026-10-29）：三处热修

### 1. 改了什么

1. **热读只扫一遍层。** `persist` 现在返回它刚写的那个 `cache.Layer`；`loadCached` / `actionLogCached` 把它并进内存里的切片，`maybeMerge` 收 `[]cache.Layer` 而不是自己 `cache.Scan`。顺手也去掉了"重写信号"分支里的第三次扫描。pprof 复核：`cache.Scan` 的调用方只剩 `loadCached`（此前 54% 来自 `maybeMerge`）。
2. **index map 预分配。** `loadCached` 按 `len(oids)`、`actionLogCached` 按各层记录总数给容量。
3. **折边不再全量拷+反射排序。** `FoldEdges` 原来把 10 万个 `model.Action` 拷进 `[]item`（56 B/条，含 4 个 slice 头）再用 `sort.SliceStable`（内部走 `reflectlite.Swapper`，每次交换一次反射调用）。现在装 40 B 的 `foldItem{issue, *Issue, when int64, i}`，用 `slices.SortStableFunc` 做整数比较；每个动作的 `declared` map 复用（`clear`）而不是 10 万次分配。排序键与稳定性不变：`(date, issue)` 升序，相等保持追加序（= 每 issue 的动作序）。

## 落地（P1，2026-10-29）：枚举快照——热读不再启动 git

### 1. 形状

- 新文件 `internal/cli/enum.go`；快照落在 `<common>/kiln/enums/enum-<hash>.oid`。
- **键 = (格式版本, 枚举种类, HEAD, 失效因子)**，文件名是键的 SHA-1 ⇒ **没有失效逻辑**：新 HEAD 就是一份新文件，旧文件永远不会再被查到，由"写时保留最近 4 份"和 `kiln cache gc` 收敛。这与记录层的"内容寻址、只增不改、没有索引"是同一种思路。
- **内容 = 头部 + N×20 B OID + CRC32C**（Castagnoli，2 MB 上约 1 ms）。读时逐项校验 magic / 版本 / 种类 / HEAD / 失效因子 / 长度 / 校验和；任何一项不符就当没有，下次重建。
- **HEAD 从文件系统解，不跑 git**：`.git` 目录或 worktree 的 `.git` 文件 → `gitdir` → `HEAD`（`ref:` → 先松散 ref（worktree 目录再共享目录）→ `packed-refs`；detached 直接读 40 位 hex）。`shallow` 的内容进失效因子；一旦见到 `refs/replace/*`、`info/grafts`、`reftable`，或 `GIT_DIR` / `GIT_WORK_TREE` / `GIT_COMMON_DIR` / `GIT_REPLACE_REF_BASE` / `GIT_NO_REPLACE_OBJECTS` / `GIT_GRAFT_FILE` 任一在场，**整条退避**，按老办法每次问 git。
- 两条枚举各一份快照：默认序（全部读命令）与 author-date 序（`action log`）。
- **冷读顺手种下快照**：全扫已经拿到每个提交的 id，且顺序就是 git 的顺序；只有 `commits[0].ID == HEAD` 时才落盘，避免扫描期间有新提交把旧清单挂到新 HEAD 上。
- 写入前把 HEAD 再解一次，两次一致才落盘（枚举前后各一次）。
- `--no-cache` 仍然全线绕过；只读仓 / 写失败静默跳过；`kiln cache gc` 顺带按可达集清掉 HEAD 不可达的快照。

### 4. 代价与遗留

- **顺序信任 git**：快照是 git 的输出，所以升级 git 若改变默认落序，旧快照会与新 git 不一致——删掉 `.git/kiln` 即可。这是"存输出"而不是"复现走图"的固有取舍；换来的是顺序永远逐字节等于 git（上一轮实测过：自己按时间排序在本仓第 163 行就分叉）。
- `action log` 现在把枚举物化了（100k 2 MB），不再"边 walk 边渲染"；冷读 / `--no-cache` 仍走流式。
- `show` / `--limit` 仍要 git（取 diff / 按设计直连）。
- P2 还在：`kiln commit` 之后 HEAD 变了，下一次读仍要跑一次枚举（提交时知道新旧 HEAD，可以直接把新列表拼出来）。

## 结论（2026-10-29）

### 做到了什么

- **热读不再启动 git**（P1）：`status` / `list` / `check` / `graph` / `path` / `action log` 的 git 调用数实测 **0**（PATH 前置垫片计数）。
- **真仓**（408 提交）：读命令 **130 → 42.5 ms（−68%）**；其中 39 ms 是进程地板，kiln 自己的活只剩 ≈3 ms。
- **100k 提交**：`graph --json` **1,185 → 241 ms（−79%）**、`list` 1,162 → 219（−81%）、`action log --jsonl` 1,381 → 405（−71%）、`path --all --json` 1,308 → 360（−73%）。
- **契约不变**：六命令 × 四仓 × 热读/`--no-cache` 输出逐字节一致（含 31.5 MB 的 `path`）；11 条新测试里有一条把 PATH 指向空目录仍能读，同环境下 `--no-cache` 必须失败——两者合起来证明"git 真的没起、真的被需要"。

### 没做到的（诚实记一笔）

hypothesize 里写"提交后第一次读 ≤60 ms"，**实际 148.7 ms**（暖读 43.5 + 枚举 52 + 取新提交 45）。要压到 60 只能让 `kiln commit` 自己前插枚举，而那需要新提交的提交时间 + 一串守卫（`GIT_COMMITTER_DATE`、amend、merge、时钟回拨），漏一个就会改变输出顺序。**用"顺序可能错"换 52 ms 不划算**——这条目标作废，理由留在这里。

### P2 / P3 为什么不做（判断，不是拖延）

- **P2(a) 提交后追加枚举**：那 105 ms 是两个进程（枚举 52 + `cat-file` 45）。日期只能从 git 回读，所以"挪到提交"是零和；不挪就只能前插，见上。
- **P2(b) `path --all` 渲染**：100k 上剩约 80 ms 在编码 31.5 MB 输出（≈380 MB/s），而这份输出本身就是调用方要的字节。只对 100k 有意义。
- **P3 结构重构**：性能上已经没有它的位置（真仓 3.2 ms 自有开销；100k 剩下的 174 ms 是 O(提交数) 的建模，只有"惰性 model"能再压，且只利 100k+ 的窄命令）。结构债是真的，但它是维护性问题，另立 `refactor-structure`。

### 留给后续的触发条件

1. "提交后第一次读"在 agent 的"提交—读"循环里成为体感瓶颈 → 做 P2(a) 前插版，单独立项 + 顺序黄金测试。
2. 100k+ 仓，或 `show` / `path <单个 issue>` 成为常态 → 惰性 model（局部读）。
3. git 升级后输出与 `--no-cache` 不一致 → 删 `.git/kiln`；若频繁发生，考虑把 git 版本纳入快照键。

### 方法论收获（三条）

1. **三层口径缺一不可**：进程内探针测"自己的 CPU"，垫片测"git 调用数与时长"，端到端 harness 测"用户等多久"。只看端到端会把 39 ms 进程地板记到代码头上；只看进程内会漏掉"起进程"才是真瓶颈。
2. **先量再改，稳态 A/B**：两轮里预估值错了两次（map 收益高估 27 ms；提交后成本低估），都是靠"同进程跑 4 次取后 3 次最小"抓出来的。
3. **逐字节一致是最便宜的正确性网**：任何碰顺序/字段的改动，先跑"六命令 × 四仓 × 冷热 + `--no-cache`"矩阵，再谈快了多少。
