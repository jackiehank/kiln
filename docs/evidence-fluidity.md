# issue: evidence-fluidity — 动作「证据」可被改写 / 删除，与 kiln「记录」取向的张力

- **状态**：ask（进行中）
- **domain**：design
- **关联**：blocks `cli-necessity`

## 背景

`kiln` 的隐含前提是：**一个 issue 的动作历史 = 它求解过程的记录（证据）**。`path` 重建这条路径、`show` 展示每一步变更、`check` 校验其结构——都建立在"历史**可信且稳定**"之上。

但 `cli-necessity` 的后端实证（实验 3/4）表明，在 **jj** 上这个前提**不成立**：

- **改写**（`jj describe`）：动作的 `commit_id` **漂移**（`3a6a9ba`→`9b5185c`），后代自动 rebase；只有 `change_id` 稳定。
- **删除**（`jj abandon`）：一个动作**秒删**，kiln 视图立即少一步。
- **撤销**（`jj undo`）：又可原样恢复。
- `jj op log` 全程记录"哪一步做了什么"。

也就是说：**在 jj 上，任何一条动作证据都能被任意改写 / 删除 / 复原**。git 也有同类能力（`rebase` / `commit --amend`），只是**危险、显式、少见**；jj 把它变成了**日常操作**。

## 要回答的问题

1. **取向先定**：kiln 把动作历史当**不可变证据（记录）**，还是**可改写草稿**？这条不先答，其余都悬空。
2. **若当证据**：
   - 怎么**检测"被改写过"**？jj 有 **op log**（能直接说"describe / abandon 了哪条"）；git 只有 **reflog**（弱、本地、会过期）——两端能给的信号**不对等**。
   - 检测到之后**怎么表现**？`path` 给该动作标"⚠ 已重写"，还是让旧 id 显式失效？
3. **寻址稳定性**：kiln 现靠 `path` 里的**序号**寻址（`action-diff` 的决定）。历史一改，序号**重算但仍自洽**——这算"够用"，还是需要更硬的标识（`change_id`、内容哈希）？
4. **要不要"不可变"机制**：给动作加**内容哈希 / 签名**（内容一变就露馅），还是只立"**不改写已归档动作**"的社会约定（零机制）？
5. **git 后端是否同病**：`rebase` / `amend` 同样能改，只是不常见——规则该只针对 jj，还是两端一视同仁？

## 候选

| 方案 | 形态 | 代价 |
| --- | --- | --- |
| **A** 只立约定 | "已归档动作**不得改写**"，靠自觉 | 零机制；无法强制、无检测 |
| **B** 检测 + 提示 | 用 jj **op log**（git 用 reflog）标出"该动作被重写"，`path` 显示警告 | 只能事后提示；git 端信号弱 |
| **C** 不可变标识 | 动作提交里带**内容哈希**，内容一变即与声明不符 | 又加一个字段，且与 trailer"自述"同类问题 |
| **D** 承认是草稿 | 明确"kiln 只读当前态、不做证据保证"，**放弃**"记录"承诺 | 削弱 kiln 的核心卖点之一 |

> 倾向（待验证）：**A + B**——用约定兜底、用 op log 做**可选的**检测提示；C 过重、D 自弃。

## 为什么这会阻塞 cli-necessity

`cli-necessity` 要定的是"kiln 的 CLI 该留哪些能力"，其中"**动作路径 = 可信记录**"是一条重要的能力主张。若这条在 jj 上不成立，"留 `path` / `show`"的理由就要重新掂量。**先答清"证据到底可不可信"，才能定"要不要为它保留能力"**——故本 issue **`blocks` `cli-necessity`**。

## hypothesize：这与 kiln 的「原子化 + 涌现」理念是同一件事

> 用户给定 kiln 的三条理念：
> 1. **issue 原子化**——一个复杂 issue 由**不同的 issue 以不同类型的关系**组合表达；
> 2. **action 原子化**——一个 issue 的解决**没有固定流程**，从提出后可**按不同顺序**进行，**甚至自定义 action**（`.kiln.json`）；
> 3. **依据**：借鉴 **Unix 哲学**；更根本的是相信"**复杂性 / 优秀产品是涌现出来的，不是设计出来的**"。

### 1. 重新定性：这不是缺陷，是理念的**必然推论**

上一节的"张力"来自一个**外来的假设**——把 kiln 当成**审计账本**（不可变、可举证）。但这三条理念**恰恰否定**它：

> **自由 / 无序 / 可自定义地行动 ⇒ 不可能在审计意义上冻结行动记录。**"自由创作 + 不可变留痕"是一对**自相矛盾**的要求。

所以 evidence-fluidity **不是要修的问题，而是哲学的推论**；别扭感来自把"审计"当默认。这与 §4 的实测（jj 上随时可改写）**互相印证**，而非对立。

### 2. 统一的关键：把「耐久层」从**提交**挪到**关系**

| 层 | 是什么 | 可改性 |
| --- | --- | --- |
| **语义层（耐久）** | issue 的**当前组合** + **已声明的 relation**（derived-from / blocks / supersedes / …） | 应稳定、可重建 |
| **底座层（流体）** | 承载这些声明的那串提交（action） | 可自由改写 / 删除（jj），少见改写（git） |

关键认识：**kiln 的"记录"不是那串提交，而是"当前这套组合"**——而 `path` / `graph` / `status` 本来就在**从现存提交重算当前组合**。

于是：**丢 / 改一条 action 是允许的**，只要当前组合仍描述得清；反过来，**若组合变了，就该留下声明**。

### 3. 改写要**声明**，不要**隐藏**——机制模型里已有

- **`supersedes` 就是官方写法**："我取代了旧物"。kiln 不擦除，而是**用关系记录替换**。
- 于是 fluidity 被**收纳进模型**：**原子可以换，但"换了"这件事必须出现在关系里**。
- **缺口（诚实地记下）**：`supersedes` 目前是 **issue 级**；**action 级没有**——因为 action 不具**稳定身份**（正是当年 `object` 退役留下的那件事）。这可能是**刻意的**：kiln **只保证 issue 级组合可重建，不保证 action 级编辑留痕**。哲学上自洽——action 是**过程里的步子**，不是**要被引用的实体**。

### 4. 顺带解掉它对 cli-necessity 的阻塞

- 旧说法是"`path` = **可信记录**"，要**改成**：`path` = **从现存提交重建「当前组合」**——它是一个**视图，不是契约**。
- 换说法后，kiln 的必要性**反而更硬**：**"把散落的提交重建成 issue / action / relation 的语义组合"是 git 给不了的**——与"能不能保证不可变"无关。
- → 本 issue 解掉后，`cli-necessity` 的"证据"顾虑随之消解（此处留痕，供其 conclude 引用）。

### 5. Unix / 涌现的印证

- **不可变账本** = 自上而下的**设计 + 控制**（Jira / 审计）；**可变、可组合的底座** = 自下而上的**涌现**。kiln 押"涌现" ⇒ **可变是正确默认**，冻结才是需要论证的例外。
- Unix 味道：issue / action 都是**小工具**，用**关系**组合；**确定性落在组合规则**（关系语义 + `check` 不变量），**不落在每条记录的不变性**。

### 6. 下限：涌现仍需**最小稳定核**

若什么都可改，就只剩噪声。故必须钉死一件：**已声明的 relation 与当前组合 = 耐久层**；其余（提交本身）可流体。
若还想留**痕迹**，用底座自己的日志（jj **op log** / git reflog）**作为可选提示**，而**不**当作模型保证——呼应前面 test 的"op log 是设计钩子"。

### 7. 对"证据"的新定义（一句话）

> **证据 = 当前自洽的组合 + 已声明的关系，由现存提交重建**；而不是"从未被改过的提交"。

## hypothesize（续）：issue 层 vs action 层的改写，靠什么区分？

> 先接受你的观察：**在改写难度上，两者没有区别**。

### 0. 难度维度上确实无差别

issue 与 action **都只是提交**：重命名一个 issue = 批量改它所有提交的 `issue:` trailer；改写一个 action = 改一条提交。在 jj 上两者**一样容易**（git 上同样可能，只是更麻烦）。

→ 所以**不能用"能不能改"或"改写难度"来区分两层**。底座**不会告诉你**你改的是哪一层。

### 1. 真正的区别：**可寻址性**（名字 vs 实例）

| | **issue** | **action** |
| --- | --- | --- |
| 是什么 | 一个**名字**（`issue:` 标签），**复制**在它所有提交上 | 一个**匿名实例**（一条提交） |
| 能否被引用 | **能**——关系键（derived-from / blocks / supersedes）**只指向 issue 名** | **不能**——没有任何键能指向某条 action |
| 身份来自 | 人给的名字（可重建的聚合） | 该提交本身（hash / change-id / `path` 序号） |

**区别不在"能不能改"，在"改的是什么类型的对象"**：**issue 是可被引用的名字，action 是不可被引用的实例。**

### 2. 由此得到判据：看**关系图上的名字 / 边有没有变**

> - 改动涉及 **`issue:` 标签**或**关系键**（derived-from / blocks / supersedes / …）→ **issue 层**（**可声明、也应声明**）
> - 改动只涉及**某个实例的内容或存在**（`action:` 种类、title、正文、diff、某条提交被删改）→ **action 层**（**不可声明**，属底座）
>
> 一句话：**关系图上的名字或边变了 → issue 层；没变 → action 层。**

### 3. 为什么 action 层的改写**无法声明**——这是**刻意的**

- 关系键的**两端永远是 issue 名**；模型里**没有位置**写"我取代了哪条 action"。
- 历史上 kiln **确实试过**给 action 起名（`object: q1`），用它做 action 级依赖——**后来退役了**（`retire-object`）。→ 即**决定"不让 action 可寻址"**，于是 action 层改写**天生不可声明**。
- 反过来说：**只有 issue 层能"声明"改写**（`supersedes: 旧名`），因为**只有名字可被指向**。

### 4. 想记录 action 级修正怎么办？——**追加**，而不是声明

- 若要留痕，就**再落一条 action**（说明 / 修正 / 推翻），让 `path` **变长**——即**用「追加」表达 action 级修正**。
- 这与"关系只连名字"自洽：**action 级的变化通过路径增长体现，而非通过关系**。

### 5. 一致性推论

- **`check` 只能校验 issue 层**（名字 / 关系 / 终点结构）；它**永远无法知道某条 action 被改写过**——那是底座的事，与前面 test 的结论一致。
- 于是上一轮那句"**耐久层 = 已声明的 relation + 当前组合**"**精确地**落在 **issue 层**；**action 层整体是流体的底座**。
- 这也回收了缺口：不是"`supersedes` 忘了做 action 级"，而是"**action 层本就不该有 `supersedes`**"。

### 待定

- 是否在**约定 / 文档**里明确："改 `issue:` 或关系键 = issue 级、需声明；只改实例 = action 级、可不声明"？
- "追加式修正"要不要给个正式 action 名（如 `retract`）？——本 issue 不动词表。

## hypothesize（再续）：尊重用户当前意图——kiln 不是审计工具，一般视图呈现「当前态」

> 先回应：**我理解你的理念**，并且它把前面两轮往前推了一步——尤其**修正了我那句"改写要声明"**。

### 0. 我理解到的理念（复述）

1. **用户主权**：用户**当前的判断**就是权威——他新建又撤销一个 issue，那"撤销"本身有意义，工具应当**尊重并体现**它。
2. **kiln 不是审计工具**：因此**不承担"留痕 / 举证"的义务**；在 `status` 等一般视图里，**issue 可以改写、issue 的关系也可以改写**。
3. **改写史视图**：要不要有，是**另一件事**，可以再议——但**不属于**一般视图。

### 1. 这条修正了什么

- 上一轮我说"**改写要声明，不要隐藏**"——**太重了**，那是**软审计**口吻。
- 现在改成：**声明是可选礼节，不是义务**。默认就是**直接改**；只有当你**想让读者知道"换过"**时，才用 `supersedes` 之类的声明。
- 上上轮"耐久层 = 当前组合 + 已声明的关系"**不受影响**——只是那一层**可自由编辑**。

### 2. 由此得到清晰的视图分工

| 视图 | 语义 | 内容 |
| --- | --- | --- |
| **一般视图**（`status` / `graph` / `path` / `show`） | **当前态** | 从「现存提交」重建；**改写不留痕、不需声明、不作解释** |
| **改写史视图**（可选，未定） | **溯源** | 底层日志（jj **op log** / git reflog），**明示可选**、**不属一般视图** |

> 一句话：**一般视图只回答"现在是什么样"；历史属于另一个可选视图。**

### 3. "撤销"作为一等公民

- 用户撤掉一个 issue / 一条关系 → **一般视图里它就是不在**（不在现存声明里）。
- 实现上两条等价路径：① **改底座**（jj `abandon` / 重写提交）→ 重建时自然消失；② 提交还在、但**不再声明** → 也不显示。
- **不需要**为"撤销"专门记一笔——除非用户**主动想留痕**（那就落到改写史视图，或**追加**一条 action）。
- 与上轮 §4（"追加表达 action 级修正"）一致：**想留痕就追加；不想留痕就直接改。**

### 4. 边界（诚实标注）

- 代价：**读者默认信任"当前态"**。两个协作者各自改写、互不知情时，会看到不同"现实"。
- 这是**自觉的取舍**：kiln 押"**信任用户 + 涌现**"，不押"**审计 + 控制**"。要溯源的，用**可选**的改写史视图。

### 5. 与前几轮的一致性检查

- 与"理念同源"一致：可变是默认、冻结才需论证——**本轮把"声明"也从义务降为可选**，更彻底。
- 与"可寻址性区分两层"一致：issue 层（名字 / 关系）与 action 层（实例）**都可编辑、都属当前态、都无需声明**。
- 与 `check` 一致：`check` 校验**当前态**的结构，**与历史无关**。
